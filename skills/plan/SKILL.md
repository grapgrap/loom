# Plan

문제와 원하는 결과를 확인하고 현재 구현을 조사한다. 구현 방안과 그 영향을 사용자와 검토한다. 검토한 변경안에서 실행할 작업과 검증 가능한 결과, 의존관계를 도출한다.

**plan은 변경안을 검토하고 문서화한다. 구현하지 않는다.**

## Step 0: 컨텍스트 로드

1. 작업 대상 프로젝트의 `.loom/index.md`를 읽어 도메인 전체 지도를 파악한다.
2. 입력 맥락에서 좁은 검색어를 만들고 `aeira search -s {프로젝트의 .loom 경로} "{검색어}"`로 관련 concept과 flow 후보를 찾는다. 결과가 비면 표현을 바꿔 재시도한다.
3. 후보 노드에 `aeira graph neighbors -s {프로젝트의 .loom 경로} --direction=outgoing "{노드}"`를 실행해 연결된 concept과 flow를 확장한다. 노드는 `.loom` 기준 경로 형식이다.
4. 후보 문서를 읽고 입력 맥락에 맞는 concept과 flow만 선별해 변경이 닿는 도메인과 흐름을 파악한다.
5. decision은 이 단계에서 일괄로 읽지 않는다. 구현 방안과 영향을 검토하면서 설계 의도나 이전 결정을 확인할 필요가 생긴 시점에만 해당 맥락으로 `aeira search -s {프로젝트의 .loom 경로} "{검색어}"`를 실행한다. 관련 concept이나 flow가 있으면 `aeira graph neighbors -s {프로젝트의 .loom 경로} --direction=incoming "{노드}"`로 이를 참조하는 decision 후보를 보강한다. 맥락에 맞는 decision만 읽는다. 같은 사안이 충돌하면 decision concept의 최신 우선 규칙에 따라 순번이 큰 decision을 따른다.

shape에서 넘어온 경우, shape summary를 입력으로 사용한다.
triage에서 바로 넘어오거나 사용자가 직접 요청한 경우, 원본 요구사항을 입력으로 사용한다.
실행 중 재검토로 진입한 경우, 기존 plan과 예상에서 벗어난 사실을 입력으로 사용한다. 영향받는 변경안과 작업을 검토하며 유효한 부분은 유지한다.

## Step 1: 문서 작성 가이드 로드

`../../references/document-authoring-guide.md`를 읽는다.

plan 초안을 작성하거나 decision을 기록하기 전에 가이드를 로드한다. 이후 plan을 작성하거나 검증할 때 이 가이드를 적용한다.

## Step 2: 룰 카탈로그 로드

`.loom/rules/index.md`를 읽어 어떤 룰과 컨벤션이 있는지 카탈로그를 인지한다.

rule은 이 프로젝트에서 항상 지켜져야 하는 강제적 합의, convention은 강하게 권장되지만 대체 가능한 형태이다. 인덱스를 통해 항목 목록과 각 항목의 호출 상황을 파악한다. 본문은 활용 시점에 필요한 항목을 골라낸 뒤 로드한다.

## Step 3: 현재 구현과 문제 파악

사용자가 해결하려는 문제와 변경 후 성립해야 할 결과를 확인한다. 관련 코드와 문서, 테스트를 읽고 현재 동작을 추적한다. 구현이 아직 없는 대상은 연결될 기존 구조와 새로 만들어야 할 부분을 구분한다.

- 문제와 관련된 진입점, 호출 관계, 상태와 실패 처리를 필요한 범위에서 따라간다.
- 현재 흐름에서 문제가 발생하는 이유를 코드 근거와 함께 설명한다.
- 확인한 사실과 아직 확인하지 못한 가정을 구분한다.

현재의 문제 이해와 잠정 변경 방향, 더 확인할 쟁점을 짧게 공유한다. 조사와 변경안 전체를 완성할 때까지 최초 피드백을 미루지 않는다.

## Step 4: 구현 방안과 영향 검토

문제와 원하는 결과를 기준으로 구현 방안을 제안한다. 구현 방안은 코드의 어느 부분을 어떤 구조나 동작으로 바꿀지에 대한 제안이다. 변경안은 구현 방안과 예상 영향, 필요한 대응을 포함한다.

현재 구현은 문제 이해와 영향 분석의 대상이다. 기존 구조를 유지할지는 검토를 통해 판단한다. 구조 자체가 원인이면 재구성하거나 제거하는 방안도 검토한다. 변경 후 동작을 따라가며 관련 코드와 기존 사용처에 미치는 영향을 확인한다.

- 변경 전후에 같은 상황을 어떻게 처리하는지 설명하고, 그 차이가 문제를 해결하는 이유를 확인한다.
- 호출하는 곳과 호출받는 곳, 상태 변경과 실패 경로 등 영향받는 동작을 검토한다. 예상 부작용과 필요한 대응을 드러낸다.
- 선택에 따라 동작이나 구조가 달라지면 대안과 영향을 사용자와 검토한다. 에이전트가 중요하다고 분류한 결정 목록만으로 변경 흐름의 설명을 대신하지 않는다.
- 판단을 바꿀 발견이나 선택이 생기는 시점에 근거와 잠정 방향을 공유한다. 사용자의 피드백에 따라 변경안을 조정하고 필요한 코드를 더 확인한다.

### 구체화 수준

사용자가 변경의 타당성과 영향을 판단할 수 있는 만큼 구체화한다. 파일, 함수, 데이터 구조나 수도코드가 판단에 필요하면 다룬다. 모든 구현을 미리 명세하지는 않지만 주요 선택을 구현 세부로 취급하여 task까지 미루지 않는다.

아직 확인할 수 없는 사항은 어떤 가정에 의존하며 무엇을 확인해야 하는지 남긴다. 결과에 따라 변경 방향이나 영향 판단이 달라질 사항은 그 판단에 의존하는 실행 전에 다시 검토한다. 합의한 방향과 영향 판단을 유지하는 구현 세부는 task에서 정할 수 있다.

### shape와의 경계

concept이나 flow의 의미 또는 경계를 바꿔야 하면 해당 설계를 shape에서 재검토하도록 사용자와 합의한다. 구현 방안이 구체적이라는 이유만으로 shape로 돌아가지 않는다. shape에서 결정한 결과를 받으면 영향받는 변경안의 검토를 이어간다.

### 룰 카탈로그 활용

변경안을 검토할 때 수행하려는 행동에 적용되는 rule·convention을 카탈로그에서 고르고 본문을 읽는다. 구현 방안, 부작용 대응과 검증에 반영한다.

### 결정 기록

사용자가 대안 중 하나를 선택하고 그 선택이 설계나 구현의 형태에 영향을 주면 문서 작성 가이드와 decision concept에 따라 `.loom/decisions/`에 기록한다. 템플릿은 `../../templates/decision.md`를 사용하고 파일 이름은 `{NNNN}-{결정-제목}.md`로 한다. 기존 decision은 수정하지 않는다.

plan에는 실행에 필요한 선택의 결과와 제약을 반영한다. 선택의 근거는 decision에 보존한다. 작업 순서나 자명한 선택은 decision으로 만들지 않는다.

## Step 5: 실행 작업과 초안 구성

검토한 변경안에서 실행할 작업을 도출한다. 최종 결과에 필요한 중간 결과와 부작용 대응이 작업에 포함되는지 확인한다.

각 태스크에는 목적, 수행할 변화, 완료 결과와 검증 방법을 기술한다. 범위로 오해할 만한 인접 작업이 있으면 제외를 명시한다. 수행할 변화는 검토한 구현 방안과 해당 태스크가 지켜야 할 주의점을 이어받는다.

작업은 실행과 검증에 유용한 단위로 나눈다. 서로 다른 선행 결과가 필요하거나, 독립적으로 실행·검증하는 것이 유용하거나, 한 결과가 다른 결과의 전제이면 분해를 고려한다. 단일 작업도 변경 영향 검토가 필요하면 정상적인 plan이다.

선행 결과가 후속 작업의 전제가 될 때만 결과 의존을 만든다. 해당 결과와 후속 작업이 그 결과를 필요로 하는 이유를 명시한다. 단순한 작성 순서는 결과 의존으로 기록하지 않는다.

### 초안 작성

`../../templates/plan.md`를 읽고 `.loom/plans/{plan-제목}.md`에 초안을 작성한다. 재검토 중이면 기존 plan의 영향받는 위치를 갱신한다.

실행에 필요한 현재 동작의 요약과 코드 근거, 구현 방안과 예상 영향, 미확인 사항, 작업과 검증을 남긴다. 탐색 과정 전체, 사용자와 나눈 확인 대화나 코드의 현재 상태를 복제하지 않는다. 이미 합의한 내용과 미확인 사항을 구분한다.

초안 작성 시 임시 핸드오프를 만들지 않는다. 실행 중 사용자가 명시적으로 요청한 경우에만 task가 현재 미완료 태스크에 작성한다.

## Step 6: 검증과 확정

다음 기준으로 변경안과 실행 작업을 대조한다.

- 현재 동작에 대한 설명이 실제 구현에 근거하며 가정과 구분되는가?
- 구현 방안이 문제를 해결하고 원하는 결과를 만드는가? 기존 구조의 유지 여부를 그 기준으로 판단했는가?
- 영향받는 기존 동작과 부작용에 필요한 대응이 있는가?
- 사용자가 주요 선택을 판단할 만큼 구현 방안과 영향이 드러나는가?
- 작업의 목적·변화·완료 결과·검증이 변경안과 연결되는가? 필요한 변경이나 부작용 대응이 누락되지 않았는가?
- 결과 의존이 구체적인 선행 결과와 후속 전제를 연결하는가? 누락, 고아 결과나 순환 의존이 없는가?
- 미확인 사항의 확인 방법이 명확하며, 그 결과에 의존하는 실행 전에 재검토할 수 있는가?

사용자와 변경안 및 그로부터 도출한 실행 범위를 확인한다. 앞선 논의에서 확인한 내용을 반복해서 합의할 필요는 없다. 새 쟁점이나 달라진 판단을 설명하고 함께 검토한다. 에이전트의 단독 점검이나 완성된 작업 목록의 확인만으로 Step 3·4의 대화를 대체하지 않는다.

문제가 드러나면 관련 구현을 다시 조사하거나 변경안과 작업을 교정한다. 사용자가 변경안과 실행 범위에 동의하면 이번에 생성·수정한 Loom 문서를 문서 작성 가이드에 따라 검증한다. 교정으로 합의한 판단이 바뀌면 사용자와 다시 검토한다.

검증을 통과한 plan을 현재 실행할 변경안으로 확정한다. 확정 뒤에도 실행 중 발견에 따라 갱신한다.

### 그래프 갱신

`.loom/` 문서를 생성·수정한 작업을 마칠 때 `aeira sync -s {프로젝트의 .loom 경로}`를 실행한다. 중간에 shape로 전환하여 작업을 마칠 때에도 작성한 decision이 있으면 검증한 뒤 동기화한다.

## Summary

plan 완료 시 다음 형식으로 정리한다:

```
## Plan Summary
- 목적: [해결할 문제와 최종 결과]
- 변경안: [현재 동작과 변경 후 동작의 차이]
- 영향: [예상 영향과 필요한 대응]
- 실행 작업: [태스크와 결과 의존 요약]
- 검증: [사용자 확인과 문서 검증 상태]
- 미확인 사항: [확인할 내용과 시점, 없으면 생략]
- Decisions: [기록한 decision, 없으면 생략]
```
