# Plan

확정된 설계를 검증 가능한 결과를 가진 태스크와 결과 간 의존관계로 구조화한다.

**plan은 산출물이다. 구현하지 않는다.**

## Step 0: 컨텍스트 로드

1. 작업 대상 프로젝트의 `.loom/index.md`를 읽어 도메인 전체 지도를 파악한다.
2. 입력 맥락에서 좁은 검색어를 만들고 `aeira search -s {프로젝트의 .loom 경로} "{검색어}"`로 관련 concept과 flow 후보를 찾는다. 결과가 비면 표현을 바꿔 재시도한다.
3. 후보 노드에 `aeira graph neighbors -s {프로젝트의 .loom 경로} --direction=outgoing "{노드}"`를 실행해 연결된 concept과 flow를 확장한다. 노드는 `.loom` 기준 경로 형식이다.
4. 후보 문서를 읽고 입력 맥락에 맞는 concept과 flow만 선별해 분해의 도메인 구성을 파악한다.
5. decision은 이 단계에서 일괄로 읽지 않는다. 결과를 구성하면서 설계 의도나 이전 결정을 확인할 필요가 생긴 시점에만 해당 맥락으로 `aeira search -s {프로젝트의 .loom 경로} "{검색어}"`를 실행한다. 관련 concept이나 flow가 있으면 `aeira graph neighbors -s {프로젝트의 .loom 경로} --direction=incoming "{노드}"`로 이를 참조하는 decision 후보를 보강한다. 맥락에 맞는 decision만 읽는다. 같은 사안이 충돌하면 decision concept의 최신 우선 규칙에 따라 순번이 큰 decision을 따른다.

shape에서 넘어온 경우, shape summary를 입력으로 사용한다.
triage에서 바로 넘어온 경우, 원본 요구사항을 입력으로 사용한다.

## Step 1: 문서 작성 가이드 로드

`../../references/document-authoring-guide.md`를 읽는다.

plan 초안을 처음 작성하기 전에 가이드를 로드한다. 이후 plan을 작성하거나 검증할 때 이 가이드를 적용한다.

## Step 2: 룰 카탈로그 로드

`.loom/rules/index.md`를 읽어 어떤 룰과 컨벤션이 있는지 카탈로그를 인지한다.

rule은 이 프로젝트에서 항상 지켜져야 하는 강제적 합의, convention은 강하게 권장되지만 대체 가능한 형태이다. 인덱스를 통해 항목 목록과 각 항목의 호출 상황을 파악한다. 본문은 활용 시점에 필요한 항목을 골라낸 뒤 로드한다.

## Step 3: 결과 사슬 구성

concept과 flow에서 최종적으로 성립해야 하는 결과를 찾는다. 최종 결과에서 역방향으로, 그 결과에 필요한 중간 결과를 식별한다.

각 중간 결과를 독립적으로 실행하고 검증할 수 있는 태스크로 구성한다. 태스크 결과는 확정된 설계를 실체화하거나 후속 태스크의 전제가 되는 상태, 산출물 또는 능력이어야 한다.

각 태스크는 다음 내용을 기술한다.

- 목적: 이 태스크가 전체 결과에 기여하는 이유를 기술한다.
- 수행할 변화: 현재 상태에서 무엇을 바꿀지 기술한다.
- 제외: 범위로 오해할 만한 인접 작업이 있을 때, 이번 태스크에서 바꾸지 않을 대상을 기술한다. 오해할 인접 작업이 없으면 생략한다.
- 완료 결과: 태스크가 끝난 뒤 성립해야 하는 검증 가능한 상태, 산출물 또는 능력을 기술한다.
- 검증: 완료 결과가 성립했는지 확인할 방법을 기술한다.

다음 조건 중 하나를 충족하면 결과를 여러 태스크로 나눈다.

- 각 결과가 서로 다른 선행 결과를 요구한다.
- 각 결과를 서로 독립적으로 검증할 수 있다.
- 한 결과가 다른 결과의 전제가 된다.

복잡도를 균일하게 만들거나 파일별 작업 목록을 작성하기 위해 태스크를 나누지 않는다. 결과를 만드는 구현 방법은 task가 작업 직전에 사용자와 합의한다.

### 룰 카탈로그 활용

분해 시, 인지한 룰 카탈로그를 도구 선택 절차로 활용한다:

1. 지금 수행하려는 행동을 의식적으로 명시한다
2. 카탈로그에서 그 행동에 적용될 가능성 있는 항목을 골라낸다
3. 골라낸 항목의 본문 파일을 로드해 적용 방식을 파악한다
4. 본문에 따라 태스크를 분해한다

## Step 4: 결과 의존 식별

각 태스크의 완료 결과가 어떤 후속 태스크의 전제가 되는지 확인한다. 선행 결과와 후속 전제가 직접 연결될 때에만 결과 의존을 만든다.

- 각 결과 의존에는 선행 태스크가 만드는 결과와 후속 태스크가 그 결과를 필요로 하는 이유를 명시한다.
- 단순한 작성 순서나 선호하는 실행 순서는 결과 의존으로 기록하지 않는다.
- 서로의 결과를 요구하지 않는 태스크는 각 태스크의 선행 결과가 성립한 뒤 병렬로 실행할 수 있다.
- 확정된 설계나 후속 태스크로 이어지지 않는 결과는 제거하거나 목적을 다시 확인한다.
- 필요한 선행 결과가 없는 태스크가 있으면 결과 사슬에 태스크를 추가하거나 기존 태스크의 결과를 교정한다.
- 순환하는 결과 의존이 있으면 각 결과의 경계를 다시 나눈다.

최종 결과와 중간 결과의 연결을 요약하여 전체 결과 사슬을 제시한다.

## Step 5: 초안 산출

문서 작성 가이드에 따라 `.loom/plans/`에 plan 초안을 작성한다.

이 산출물은 Step 6의 검증과 교정을 거치는 초안이다. 검증에서 태스크의 결과나 결과 의존이 바뀌면 초안을 직접 고친다. Step 6에서 확정하고 그래프를 갱신하므로 이 단계에서는 `aeira sync`를 실행하지 않는다.

초안은 구현 방법을 미리 확정하지 않아도 된다. 그러나 각 태스크가 만드는 결과와 검증 방법은 사용자가 완료 여부를 판단할 수 있을 만큼 명확해야 한다.

템플릿: `../../templates/plan.md`를 읽어 사용한다.

plan 초안을 작성할 때에는 임시 핸드오프를 만들지 않는다. 실행 중 사용자가 명시적으로 요청한 경우에만 task가 현재 미완료 태스크에 임시 핸드오프를 작성한다.

### 파일 이름 규칙

`{plan-제목}.md` (예: `user-auth-implementation.md`)

## Step 6: 검증

초안의 각 태스크와 전체 결과 사슬을 사용자와 함께 검증한다. 사용자는 각 태스크가 바꾸는 범위와 완료 결과를 확인하고 변경이 옳은지 판단한다. 에이전트의 단독 점검은 사용자 검증을 대체하지 않는다.

### 검증의 단위와 깊이

모든 태스크에 다음 질문을 적용한다.

- 목적, 수행할 변화, 완료 결과와 검증 방법이 서로 같은 결과를 가리키는가?
- 완료 결과가 확정된 설계나 후속 태스크의 전제로 추적되는가?
- 변경할 코드나 구조가 실제로 존재하고 접근 가능한가?
- 제외가 실제로 오해할 만한 인접 작업만 한정하는가?

전체 결과 사슬에 다음 질문을 적용한다.

- 모든 결과 의존이 구체적인 선행 결과와 후속 전제를 연결하는가?
- 중간 결과가 최종 결과까지 끊기지 않고 이어지는가?
- 필요한 선행 결과의 누락, 후속 전제가 없는 고아 결과 또는 순환 의존이 있는가?
- 결과 의존이 없는 태스크를 병렬로 실행할 수 있는가?

검증의 깊이는 결과와 결과 사슬의 거시적인 실행 가능성을 확인하는 수준에 머문다. task는 작업 직전에 결과를 만드는 구현 방법을 사용자와 합의한다.

### 불명확성 라우팅

불명확한 부분이 무엇을 바꾸도록 요구하는지에 따라 처리한다.

- concept이나 flow의 의미를 바꿔야 결과를 정할 수 있으면 shape로 돌아간다.
- concept과 flow의 의미를 유지하면서 태스크 결과, 검증 또는 결과 의존을 바꿔야 하면 plan 초안을 교정한다.
- 태스크 결과를 유지하면서 구현 방법만 정하면 task에 남긴다. 구현 방법이 열려 있다는 이유만으로 태스크를 shape로 보내지 않는다.

### 교정 루프

검증에서 결과의 불명확성, 변경할 코드나 구조의 부재, 결과 의존의 단절 또는 변경 범위의 부당함이 드러나면 Step 3이나 Step 4로 돌아간다. 초안을 교정한 뒤 사용자와 다시 검증한다.

### 검증과 확정

검증과 교정은 plan 초안을 직접 갱신한다. 사용자와 나눈 확인 대화는 plan에 기록하지 않는다.

사용자가 각 태스크의 변화, 완료 결과와 결과 의존에 동의하면 교정된 plan을 문서 작성 가이드에 따라 검증한다. 가이드를 충족하지 못한 plan은 교정하고 다시 검증한다. 교정으로 태스크의 결과나 결과 의존이 바뀌면 사용자 검증으로 돌아간다. 문서 책임 배치나 의미 표현만 바뀌면 가이드에 따라 교정된 결과를 다시 검증한다.

사용자 검증과 문서 작성 가이드 검증을 모두 통과한 plan을 최종본으로 확정한다.

### 그래프 갱신

확정 직후, `.loom/` 내 생성·수정된 문서에 대해 `aeira sync -s {프로젝트의 .loom 경로}` 를 한 번 실행한다.

## Summary

plan 완료 시 다음 형식으로 정리한다:

```
## Plan Summary
- 목적: [이 plan이 성립시킬 최종 결과]
- 태스크 수: [N개 태스크]
- 결과 사슬: [선행 결과에서 최종 결과까지 이어지는 의존관계]
- 검증: [사용자 검증과 문서 작성 가이드 검증의 상태]
- 열린 질문: [해소되지 않은 것들]
```
