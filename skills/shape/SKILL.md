# Shape

요구사항을 도메인(concept)과 흐름(flow) 수준의 설계로 구체화한다. 분해(도메인의 경계)와 조합(도메인 간 흐름)을 함께 산출한다.

shape의 How는 방향성 수준이다 — 접근 전략, 제약, 트레이드오프.
구체적 기술 선택, 파일 구조, 함수 시그니처는 shape의 범위가 아니다.

## Step 0 — Triage

입력의 추상화 수준을 판단한다.

shape는 기능/시스템 단위뿐 아니라 plan 태스크 단위에서도 호출될 수 있다.
plan이나 task에서 concept·flow의 의미 또는 경계를 바꿔야 한다고 발견하면 해당 설계를 shape에서 재검토한다. 구현 방안이나 변경 영향의 미확인은 plan에서 검토한다.

1. 작업 대상 프로젝트의 `.loom/index.md`를 읽어 도메인 전체 지도를 파악한다.
2. 입력 맥락에서 좁은 검색어를 만들고 `aeira search -s {프로젝트의 .loom 경로} "{검색어}"`로 관련 concept과 flow 후보를 찾는다. 결과가 비면 표현을 바꿔 재시도한다.
3. 후보 노드에 `aeira graph neighbors -s {프로젝트의 .loom 경로} --direction=outgoing "{노드}"`를 실행해 연결된 concept과 flow를 확장한다. 노드는 `.loom` 기준 경로 형식이다.
4. 후보 문서를 읽고 입력 맥락에 맞는 concept과 flow만 선별해 도메인 구성을 파악한다.
5. decision은 이 단계에서 일괄로 읽지 않는다. 이후 전제·제약 재평가처럼 이전 결정을 확인하거나 제안을 평가할 필요가 생긴 시점에만 해당 맥락으로 `aeira search -s {프로젝트의 .loom 경로} "{검색어}"`를 실행한다. 관련 concept이나 flow가 있으면 `aeira graph neighbors -s {프로젝트의 .loom 경로} --direction=incoming "{노드}"`로 이를 참조하는 decision 후보를 보강한다. 맥락에 맞는 decision만 읽고, 같은 사안이 충돌하면 순번이 큰 것을 따른다 — decision concept의 최신 우선 규칙이다.
6. 입력을 다음 기준으로 분류한다:

| 수준               | 신호                                                                                | 행동                                                                                         |
| ------------------ | ----------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| 개념적 설계가 명확 | concept·flow의 의미와 경계는 정해졌고, 문제를 해결할 구현 방안과 영향을 검토해야 함 | **plan으로 라우팅** |
| 방향은 있으나 모호 | 무엇을 원하는지는 알지만, 경계나 접근법이 불명확                                    | shape 프로세스 진행                                                                          |
| 비전 수준          | 한 줄의 아이디어, 넓은 목표                                                         | shape 프로세스 진행 (분해부터 시작)                                                          |

변경 방향과 영향까지 명확한 기계적 작업은 별도 plan 없이 실행으로 안내할 수 있다. 작업 수만으로 판단하지 않는다. 기존 plan이나 task에서 진입했다면 개념적 설계를 확인한 뒤 영향받는 변경안을 plan에서 재검토한다. 기존 변경안이 그대로 유효하면 task의 실행 요약과 확인으로 이어간다.

triage 결과를 사용자에게 알리고 동의를 구한다.

## Step 1 — 문서 작성 가이드 로드

`../../references/document-authoring-guide.md`를 읽는다.

Shape가 concept, flow, decision 또는 index를 처음 변경하기 전에 가이드를 로드한다. 이후 Loom 문서를 작성하거나 검증할 때 이 가이드를 적용한다.

## Step 2 — 룰 카탈로그 로드

`.loom/rules/index.md`를 읽어 어떤 룰과 컨벤션이 있는지 카탈로그를 인지한다.

rule은 이 프로젝트에서 항상 지켜져야 하는 강제적 합의, convention은 강하게 권장되지만 대체 가능한 형태이다. 인덱스를 통해 항목 목록과 각 항목의 호출 상황을 파악한다. 본문은 활용 시점에 필요한 항목을 골라낸 뒤 로드한다.

## Step 3 — 요구사항 구체화

입력의 요구사항을 대화로 구체화한다.

- 달성하고자 하는 것은 무엇인가?
- 어떤 상호작용이 일어나는가? 누가 언제 무엇을 하는가?
- 어떤 제약이 있는가? 반드시 지켜야 할 조건은?

이 단계의 초점은 요구사항 자체의 구체화이다. concept이 자연스럽게 언급될 수 있으나, 구체적 파일 구조, 함수 시그니처, 라이브러리 선택 같은 구현 수준 질문은 삼간다. 요구사항이 충분히 구체화되면 Step 4로 넘어간다.

plan이나 task에서 진입한 경우, 변경안과 새로 확인한 사실을 요구사항의 맥락으로 삼는다. 어떤 사실 때문에 도메인의 의미나 경계를 다시 검토해야 하는지 확인한다.

## Step 4 — 흐름과 경계 수립

구체화된 요구사항에서 흐름을 도출하고, 그 흐름이 가로지르는 도메인의 경계를 함께 식별하는 과정을 반복한다. 흐름(조합)과 경계(분해)는 서로를 교정하며 함께 빚어진다.

### 흐름과 경계의 반복 사이클

1. **흐름 도출**: 요구사항에서 "무슨 일이 어떤 도메인들을 거쳐 어떻게 조합되는가"를 트리거에서 결과까지 도메인 간 경로로 도출한다.

2. **경계 식별**: 각 단계가 어느 도메인의 책임인지 짚으면 도메인 경계가 식별된다. 한 단계가 두 도메인에 어색하게 걸치면 경계가 잘못 그어진 신호다.

3. **괴리 조정**:
   - 흐름의 어떤 단계를 맡을 도메인이 없으면 -> 빠진 concept이 있다는 신호다.
   - 한 단계가 두 도메인에 걸치거나 한 도메인이 여러 단계를 떠안으면 -> 경계를 다시 그어야 한다는 신호다.

   흐름을 도출하는 일과 경계를 식별하는 일은 서로의 빈틈을 드러낸다. 한쪽을 고치면 다른 쪽으로 돌아가 다시 맞추며, 충분해질 때까지 1과 2를 오간다.

4. **반복 종료**: 목적, 책임과 도메인 간 조합에 합의하면 Step 5로 넘어간다. 구현의 코드 구조·주요 인터페이스·핵심 로직은 plan에서 초안으로 검토한다. 구현 수준의 질문이 나왔다는 이유만으로 미해결된 도메인 경계를 확정하지 않는다.

흐름을 도출하는 일은 경계를 확인하는 수단이다 — 흐름을 그려봄으로써 한 단계가 두 도메인에 걸치거나 맡을 도메인 없는 빈 단계가 드러나면, 경계가 잘못 그어진 것이다. 가르는 질문 하나로 판별한다 — 이 대상이 여러 도메인을 불러 조합하면 flow, 한 도메인 안의 동작이나 여러 입력을 한 결과로 닫는 계산이면 concept이다. 조합의 형태는 순서만이 아니라 병렬·분기·되먹임을 포함한다. 명명 가능성은 판별 근거가 아니다 — 조합에 이름이 붙어도 그것을 concept 노드로 만들지 않으며, 오케스트레이션은 concept에 흡수되지 않고 flow에 남는다. 여러 도메인을 조율하면서 자기 상태도 가진 조정자는 상태와 조율을 가른다 — 상태는 concept, 조율은 flow다. 상태를 가진다고 조율까지 concept이 되지는 않는다. 흐름은 불변 수준에 머문다 — 도메인을 부르는 조합까지만 담고, 제어 상세(종료 판정, 재시도 등)는 코드로, 그 근거는 decision으로 내린다.

### 감지 관점 (반복 전 과정에 상시)

흐름과 경계 판단을 하면서 다음 극단에 대한 감지를 유지한다:

- **분화 부족**: 분화해야 하는데 기존 concept에 덧붙이거나(비대화), 예외나 단서로 감싸거나(의미 흐려짐), 삭제해야 하는데 방치(데드 concept)
- **과잉 분화**: 분화가 불필요한데 쪼갬. 이 분화가 지금 실제로 필요한 쓰임을 가지는지 묻는다 — 옵션 가치가 충분하지 않으면 미루는 편이 낫다

### 전제·제약 재평가

흐름과 경계 판단을 하면서 기존 concept이나 flow나 decision의 전제 또는 제약에 무효화 정황이 드러났는지 수시로 감지한다.

- 무효화가 드러나면 사용자에게 재설계 또는 유지 판단을 요청한다
- 유지 판단은 사용자의 영역이다 — 에이전트는 감지하고 근거를 수집한다
- 유지 선택 시 Step 5에서 "유지 decision"을 생산한다
- 재설계 선택 시 이 Step 안에서 방향을 다시 수립한다

### 룰 카탈로그 활용

흐름과 경계 판단 시, 인지한 룰 카탈로그를 도구 선택 절차로 활용한다:

1. 지금 수행하려는 행동을 의식적으로 명시한다
2. 카탈로그에서 그 행동에 적용될 가능성 있는 항목을 골라낸다
3. 골라낸 항목의 본문 파일을 로드해 적용 방식을 파악한다
4. 본문에 따라 설계를 진행한다

적용된 rule을 만족하지 못하는 설계 방향이 발견되면 사용자에게 보고한다.

### 결정 기록

대화 중 결정이 발생하면 문서 작성 가이드에 따라 즉시 `.loom/decisions/`에 기록한다.
결정의 신호: 대안이 제시되었고, 사용자가 하나를 선택했으며, 그 선택에 근거가 있을 때.
발견 즉시 기록하여 맥락 유실을 방지한다.

## Step 5 — 산출물 작성

concept, flow, decision과 index를 생성하거나 갱신할 때 문서 작성 가이드를 적용한다.

### Concept 생성/수정

새로운 도메인이 식별되면 `.loom/concepts/`에 파일을 생성한다. 기존 concept이 변경되면 해당 파일을 수정한다.

concept에는 목적·책임·정책·경계를 기술한다 — 도메인이 무엇을 위해 존재하고(목적), 무엇을 달성하며(책임), 어떤 규칙을 지키고(정책), 무엇을 하지 않는지(경계). 도메인 간 흐름과 시점 종속 항목은 다음으로 라우팅한다:

- 여러 도메인을 불러 조합하는 오케스트레이션 -> flow에 기록
- concept의 형태에 영향을 준 보류 -> decision에 기록 (보류 결정)
- 나중에 해야 할 작업 -> plan의 태스크로 이동

템플릿: `../../templates/concept.md`를 읽어 사용한다.

### Flow 생성/수정

여러 도메인을 불러 조합하는 오케스트레이션일 때 `.loom/flows/`에 flow 파일을 생성한다. 한 도메인 내부의 동작이거나 여러 입력을 받아 한 결과로 닫히는 계산이면 concept의 몫이므로 flow를 만들지 않는다. 명명 가능성은 판별 근거가 아니다 — 오케스트레이션은 concept에 흡수되지 않고 flow에 남는다. 조합이 논의의 대상이 아닐 때는 flow를 만들지 않는다. 기존 흐름이 변경되면 해당 파일을 수정한다.

flow에는 목적과 단계를 기술한다. 각 단계는 한 도메인(또는 하위 흐름)을 부르는 마디이며, 조합의 형태는 순서·병렬·분기·되먹임을 포함한다. 분기·순회의 조건은 이름(가드)으로 적고, 그 조건을 판정하는 규칙은 concept이나 코드에 둔다. 불변 수준에 머문다 — 도메인을 부르는 조합까지만 담고, 제어 상세는 코드로 내린다. 변이는 별도 항목이 아니라 하위 흐름으로 표현한다.

템플릿: `../../templates/flow.md`를 읽어 사용한다.

### Decision 기록

설계 과정에서 concept이나 flow나 구현의 형태에 영향을 준 결정을 `.loom/decisions/`에 기록한다.

기록할 것:

- concept이나 flow의 구조적 방향을 결정하는 선택 (아키텍처, 접근 전략, 기술 선택)
- 구현(스킬 등)의 동작 범위를 결정하는 선택
- 대안이 존재했고, 선택이 concept이나 flow나 구현의 형태에 영향을 준 것
- concept이나 flow의 범위를 한정하는 보류 결정 (예: "비동기 모델을 지금 결정하지 않는다")
- **유지 decision** — 전제 또는 제약에 무효화 정황이 드러났는데도 기존 concept이나 결정을 유지한 경우. 무효화된 전제·제약, 유지 근거, 유지 결정의 유효 기한을 기록한다. 변화 정황이 없으면 기록하지 않는다

기록하지 않을 것:

- 버그 픽스 — 의도된 동작으로의 복원이므로 설계 결정이 아니다
- plan의 스코프 조정 (예: "이 작업을 후속으로 미룬다")
- 작업 순서나 우선순위
- 자명한 선택 (예: 네이밍)

decision 기록 규칙:

- append-only로 기록한다 — 옛 decision의 본문은 수정·삭제하지 않고, 새 결정을 새 순번으로 덧붙인다.
- 각 decision은 자기완결적이다 — 다른 decision을 참조하더라도 참조된 것을 읽지 않고 맥락이 자기 안에서 닫혀야 한다. 참조 유형은 구분하지 않는다.

템플릿: `../../templates/decision.md`를 읽어 사용한다.

### Index 갱신

concept이나 flow를 생성/수정한 경우, `.loom/index.md`의 갱신이 필요한지 판단한다.
갱신이 필요한 경우: 새 도메인이나 흐름 추가, 항목 간 관계 변경, 기존 항목의 책임 변경.
index는 프로젝트 탐색의 지도 역할을 하므로, 항목 목록과 관계도를 최신 상태로 유지한다.

### 파일 이름 규칙

- concept: `{도메인-이름}.md` (예: `user-authentication.md`)
- flow: `{흐름-이름}.md` (예: `checkout-flow.md`)
- decision: `{NNNN}-{결정-제목}.md` (예: `0001-session-based-auth.md`)

decision은 순번을 부여하여 시간순을 보존한다.

### 작성 결과 검증

이번 shape에서 생성하거나 수정한 모든 Loom 문서를 문서 작성 가이드에 따라 검증한다. 가이드를 충족하지 못한 문서는 교정하고 다시 검증한다. 모든 문서가 검증을 통과한 뒤 그래프를 갱신한다.

### 그래프 갱신

`.loom/` 내 문서를 생성하거나 수정한 후 `aeira sync -s {프로젝트의 .loom 경로}` 를 실행한다.

## Summary

shape 완료 시 다음 형식으로 정리한다:

```
## Shape Summary
- 입력: [원래 요구사항 한 줄 요약]
- Concepts: [생성/수정된 concept 파일 목록]
- Flows: [생성/수정된 flow 파일 목록]
- Decisions: [기록된 decision 파일 목록]
- 다음 단계: [plan 진행 여부와 범위]
```

## 완료 후 라우팅

shape 완료 시 다음 단계를 판단한다.

| 산출물 상태        | 신호                                                                            | 행동                                                               |
| ------------------ | ------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 변경 영향 검토가 필요 | 현재 구현에서 어디를 어떻게 바꿀지, 기존 동작에 어떤 영향을 줄지 검토해야 함 | **plan으로 진행** |
| 즉시 실행 가능 | 변경 방향과 영향이 명확한 기계적 작업 | **직접 실행** — "이 설계는 plan 없이 실행 가능합니다. 진행할까요?" |
| 추가 설계 필요     | shape 과정에서 새로운 모호함이 발견됨                                           | **shape 재진입**                                                   |

라우팅 결과를 사용자에게 알리고 동의를 구한다.
