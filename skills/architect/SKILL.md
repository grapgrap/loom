# Architect

컴포넌트가 무엇을 맡고 어떻게 협력할지 정한다. 각 컴포넌트의 입력과 출력이 연결되어 전체 사용 흐름이 성립하도록 설계를 구체화한다.

설계만 맡았다면 제안을 반환한다. 구현도 맡았다면 이번 범위, 구현 계약과 검증 조건을 [work](../work/SKILL.md)에 전달한다. 작은 변경은 관련된 기존 모델과 계약을 중심으로 다룬다. 조사 초기에 현재 이해, 잠정 방향과 남은 쟁점을 공유한다.

## 목적과 현재 상태를 확인한다

사용자가 얻을 결과와 완료 조건을 정하고 장기 목표와 이번 범위를 구분한다. 실제 사용 사례에서 필요한 판단, 실행과 상태 보관의 책임을 찾는다. [understand](../understand/SKILL.md)로 현재 모델과 호출자, 그 구조가 만들어진 이유를 확인한다.

접근 방법이나 적용 전제가 불명확하면 [explore](../explore/SKILL.md)로 레퍼런스의 작동 원리와 선택 조건을 조사한다. 기존 탐색 결과가 있으면 출처, 성립 조건과 현재 시스템의 차이를 재사용하고 설계안을 가르는 미확인 전제만 더 조사한다. 탐색에서 제시한 후보는 책임과 계약을 비교한 뒤 채택한다. 문제 재정의나 판단 유보가 필요하면 해당 설계 판단을 미확정으로 남기고 work에 범위와 다음 행동을 전달한다.

## 책임과 협력 관계를 정한다

같은 개념과 책임에는 같은 용어를 사용한다. 의미와 규칙, 변경 이유가 함께 움직이는 책임은 모으고 독립적으로 판단하거나 변경해야 하는 책임은 나눈다. 각 컴포넌트가 소유할 판단과 상태, 보장할 조건, 다른 컴포넌트에 맡길 일을 밝힌다.

기존 경계와 분리안을 비교해 분리가 보호할 규칙과 줄일 결합을 설명한다. 논리적인 컴포넌트가 반드시 하나의 폴더나 배포 단위가 되어야 한다고 가정하지 않는다.

현재 구조와 목표 구조에서 누가 누구를 호출하고 어떤 정보를 주고받는지 표시한다. 의존 방향과 값의 변환을 맡을 위치도 정한다. 여러 컴포넌트를 거치는 흐름은 실행 순서와 부분 실패의 처리를 누가 책임지는지 밝힌다. 탐색에서 얻은 방식을 채택할 때는 그 성립 조건이 선택한 설계에서도 유지되는지 확인한다. 관찰로 판단할 수 있는 쟁점은 [verify](../verify/SKILL.md)를 통해 작은 실험으로 확인한다.

## 구현에 필요한 계약을 구체화한다

합의한 경계 안에서 각 호출의 입력, 결과, 상태 변화, 실패와 호출 순서의 조건을 정한다. 입력을 제공하는 쪽과 결과를 소비하는 쪽을 연결하고, 구현에 필요한 타입과 시그니처를 스케치한다.

호출자가 내부 구현을 추측하지 않고 협력할 수 있고, 구현자가 다른 책임의 정책을 대신 정할 필요가 없으며, 검증 사례를 만들 수 있으면 세분화를 마친다. 남은 내부 선택은 구현에 맡긴다.

## 전체 흐름과 전환을 확인한다

대표 사용 사례를 따라 계약을 연결하고 전체 흐름과 책임 경계를 도식으로 보여준다. 상태와 전이가 중심이면 상태흐름도, 처리 순서와 분기가 중심이면 플로우차트를 사용한다. 대화에서는 Mermaid를 우선하며, 작은 변경은 영향을 받는 경계와 흐름만 그린다.

도식에는 다음을 포함한다.

- 흐름의 시작과 종료, 주요 상태나 처리 단계, 전이와 분기 조건
- 각 판단과 상태를 소유하는 컴포넌트, 경계를 넘는 입력과 결과
- 정상 경로와 중요한 실패에서 남는 상태, 다음 행동, 대기나 재시도의 재개 및 종료 조건

그룹이나 소유자 표기로 책임을 구분한다. 전체 관계를 먼저 보여주고 한 도식에서 읽기 어려운 세부 흐름은 해당 컴포넌트나 단계에 연결해 따로 그린다. 도식과 계약에서 같은 이름을 사용하며 앞 단계의 결과가 다음 단계의 입력 조건을 충족하는지 대조한다. 모순이 있으면 관련 계약을 수정한다. 이 논리 검토를 실행 검증으로 보고하지 않는다.

이번에 바꿀 부분과 유지할 구현, 목표까지 남는 차이와 해소 조건을 정한다. 작업은 관찰 가능한 결과와 선행 계약에 따라 나눈다. 첫 사용 경로와 통합 검증을 포함하고 구현 전에 확인할 기대값을 전달한다.

## 설계를 전달하고 합의 범위를 지킨다

설계는 현재에서 목표로 달라지는 관계를 보여주는 도식을 중심으로 대화에서 전달한다. 선택 이유, 도식에 담기 어려운 계약, 전환 순서, 흐름 대조 결과와 미확인 사항을 설명한다. 여러 세션에 걸친 실행에 추가 문서가 필요할 때만 [실행 계획](../../templates/execution-plan.md)을 사용한다. 실행 업무의 소유자(owner)가 채택한 범위 변경을 [work revise](../work/references/context-work.md)로 반영한다. 설계만 맡았다면 업무 상태를 변경하지 않는다.

새 근거가 합의한 목적, 모델 경계나 보장을 바꾸면 전제와 영향을 먼저 공유하고 관련 판단을 다시 한다. 도메인의 의미, 제품 정책, 사용자 경험이나 외부 계약에 관해 사람의 선택이 남아 있거나 사용자가 구현 전 확인을 요청했다면 그 선택에 의존하는 구현을 기다린다. 그 밖의 내부 구체화는 반복 승인 없이 진행한다.
