# Architect

## 사용자가 고칠 수 있는 장면을 만든다

사용자의 말에서 시작 조건, 행동, 보이는 결과를 뽑는다. 해석이 둘이면 같은 조건에서 결과가 어떻게 갈리는지 보여준다. 예시 자체도 고칠 수 있게 한다. 기존 제품을 바꿀 때는 실제 경로와 호출자가 의존하는 계약을 `$loom:understand`로 확인한다. 미완성 코드에서 읽은 현재 동작과 새로 합의할 목표를 구분한다.

## 도메인의 의미와 경계를 TypeScript로 검증한다

장면에 등장하는 대상을 무엇으로 구별하며 서로 어떤 관계인지 정한다. 역할마다 어떤 판단을 맡고, 이를 위해 어느 역할에서 어떤 정보를 받아, 누구에게 어떤 결과를 주는지 보여준다. 데이터의 세부 항목은 값의 차이가 판단을 바꿀 때 설명한다. 기존 역할이 독립적으로 변하는 두 규칙을 떠맡거나 같은 판단이 여러 곳으로 흩어지면, 실제 변경 하나를 대입해 경계를 비교한다.

제품의 구현 언어와 관계없이 도메인 모델을 TypeScript로 표현한다. 전략적 설계에서는 각 바운디드 컨텍스트의 용어, 판단 주체와 경계에서 번역되는 의미를 타입으로 나타낸다. 같은 장면에서 허용할 조합과 혼동하기 쉬운 두 개념을 예로 들어 `tsc --strict --noEmit`으로 검사한다. 사용자가 사례를 고치면 해당 타입과 검사를 함께 갱신한다.

## 업무 흐름을 TLA+로 검증한다

상태를 바꾸는 주체, 사건, 전이 조건과 그 뒤의 상태를 정한다. 사용자가 중간 상태를 볼 수 있는지가 쟁점이면 조회도 모델의 행동에 넣는다. 두 역할이 정보를 얻는 경로나 읽기의 일관성처럼 아직 정하지 않은 선택에 따라 보이는 상태가 달라지면, 각 선택에서 달라지는 전이를 짚는다. 한 설계안을 검사했으면 결과와 그림에 그 전제를 명시한다. 사건 순서·실패·재개 중 결과가 갈리는 경로를 골라 역할 관계는 도식으로, 상태 변화는 전이표나 상태도로 보여준다. 대화에서는 Mermaid를 우선한다.

같은 도메인 용어로 초기 상태, 주체별로 가능한 행동과 지켜야 할 성질을 TLA+에 적는다. TLC로 도달 가능한 상태에서 불변식을 검사한다. ‘언젠가 처리된다’가 약속이면 진행에 필요한 가정과 시간적 성질도 검사한다. 반례가 나오면 해당 사건 순서를 사용자와 대조해 합의나 모델을 고치고 다시 실행한다.

검사한 모델에서 사람이 읽을 그림을 얻거나 그림의 전이를 모델과 대조한다. 검사한 성질, 탐색 한도, 진행에 필요한 가정과 결과를 함께 설명한다. 예컨대 두 번의 재시도까지 탐색한 사실만으로 횟수 제한은 정해지지 않는다.

## 검증 근거를 보며 합의한다

검토할 합의서에 경계와 대표 사례의 기대 결과를 적고, 각 사례를 확인한 TypeScript 모델과 TLA+ 명세·TLC 설정, 재실행 방법, 결과와 가정을 연결한다. 실행하지 못한 검증은 미확인으로 남기고 설계 판단에 미치는 영향을 밝힌다. 사용자가 선택한 약속, 위임한 선택, 열린 질문을 구별한다. 합의가 바뀌면 영향을 받은 모델을 다시 검사한다. 합의한 장면과 위반을 드러낼 관찰을 `$loom:implement`에 전달한다.
