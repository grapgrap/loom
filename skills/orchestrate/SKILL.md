# Orchestrate

조율자는 전체 업무와 하위 업무의 소유자(owner)로서 계획, 배정, 기록 저장과 결과 수락을 맡는다. 작업자는 [work](../work/SKILL.md)로 맡은 범위를 수행하고 근거를 조율자에게 반환한다. 작업자는 CLI를 읽기 전용으로 사용하며, `tidy prepare`를 포함한 저장 작업은 조율자만 실행한다. 설명과 문서에는 [write](../write/SKILL.md)를 적용한다.

## 전체 목표와 하위 업무를 정한다

[작업 맥락](../work/references/context.md)에서 현재 목표, 권한과 진행 상태를 확인한다. 사용자와 프로젝트가 정한 위임 범위와 모델을 따르고, 모델이 미정일 때만 먼저 확인한다. 모든 작업자에게 같은 워크트리의 절대 경로를 전달하고 그 경로에서 실행한다. 같은 워크트리에서 실행할 수 없다면 제약을 알리고 다른 체크아웃으로 임의 이동하지 않는다.

작업자를 실행하기 전에 다음을 정한다.

1. 사용자가 얻을 결과와 유지할 계약을 전체 완료 조건으로 정하고, 실제 사용 경로와 기대값에 연결한다.
2. 각 하위 업무의 기여 조건, 산출물, 수정 범위와 선행 결과를 정한다. 컴포넌트나 작업자 수에 맞춰 업무를 나누지 않는다.
3. 작업자가 확인할 입력, 환경과 기대 결과, 제출할 근거를 정한다. 첫 구현 전에 [verify](../verify/SKILL.md)로 검증 수단을 준비하도록 배치한다.
4. 선행 결과를 확인할 시점, 공통 검증 수단과 통합 담당자를 정한다. 하위 결과만으로 확인할 수 없는 전체 연결 동작도 담당자를 배정한다.

책임 경계를 바꾸는 구현에는 [architect](../architect/SKILL.md)에서 정한 책임과 입출력 계약을 전달한다. 설계 자체를 위임할 때는 합의한 경계와 아직 정하지 않은 계약을 구분한다.

[업무 계약](../work/references/context-work.md)과 [위임 상태 전이](../work/references/work-delegation.md)에 따라 `create`와 `assign`으로 업무를 정의하고 배정한다. 목표, 관계와 진행은 CLI에 기록하며 작은 작업에 별도 계획 문서를 만들지 않는다. 담당자나 조건이 바뀌면 영향을 받는 검증, 제출과 후속 업무를 다시 확인한다.

## 수정 범위를 나누고 명세를 전달한다

독립적인 조사는 병렬로 진행할 수 있다. 수정 작업은 같은 파일을 동시에 쓰지 않도록 나누며 선행 계약이 필요한 작업은 순서대로 진행한다. 공통 계약이나 범위가 충돌하면 영향을 받는 수정을 멈추고 조정한다. 조율자가 실행 중인 작업자의 영역을 직접 수정하지 않는다. 전체 포맷, 의존성 갱신, 브랜치와 커밋 작업은 수행자와 시점을 정하고 승인된 범위에서 맡긴다.

새 작업자에게 다음 내용을 직접 전달한다. 조율자의 기록을 작업자가 자동으로 공유한다고 가정하지 않는다.

- `work` 스킬의 실제 절대 경로, 전체 목표와 이번 업무가 기여할 완료 조건
- 같은 워크트리의 경로, 업무 ID와 worker ID, 조회할 CLI와 데이터 루트
- 맡긴 결과와 수정 범위, 다른 작업자의 영역과 선행 결과
- 합의한 계약과 제약, 정확한 원본 ref, 미결정 사항과 조건별 검증 방법
- 중간 보고 시점, 즉시 알려야 할 막힘과 전제 변경, CLI 읽기 전용 및 조율자 보고 절차
- 반환할 업무와 명세 ref, 변경한 경로, 조건별 관찰과 근거, 남은 일

작업자는 [위임 수행 지침](../work/references/delegated-work.md)에 따라 명세를 읽고 이해한 목표와 검증 방법을 짧게 설명한다. 누락이나 모순이 있으면 알리되, 명세가 충분하면 별도의 이해 확인 승인을 기다리지 않고 착수한다. 범위 변경이나 추가 위임은 조율자에게 요청한다.

## 진행 상황과 제출을 대조한다

`work show --work <전체-id> --tree`의 현재 조건을 호스트 도구가 보여주는 실행 상태와 대조한다. `ready`만 보고 실행 중인 업무를 중복 배정하지 않는다. `pending`은 아직 정리하지 않은 원본을 뜻한다. 작업자의 실행 종료, 결과 제출과 검토 수락은 서로 다른 상태다. 호스트의 대기와 알림 도구를 사용하고 상태 확인만을 위해 작업자를 다시 실행하지 않는다.

작업자의 보고를 현재 명세와 대조해 `report`에 저장한다. 실제 보고자와 산출물을 출처로 연결하며, 작업자의 완료 선언을 실제 검증으로 대신하지 않는다. 조건, 담당자나 의존 관계가 바뀌면 조율자가 명세에 반영하고 영향을 받는 작업자에게 알린다. 목표나 권한을 바꾸는 결정은 사용자에게 따른다.

결과가 준비되면 `submit`으로 고정하고 [review](../review/SKILL.md)와 [verify](../verify/SKILL.md)에 따라 실제 산출물을 검토한다. 현재 제출이 완료 조건을 충족하면 `accept`한다. 보완이 필요하면 해당 조건 ID와 근거를 명시해 `request-changes`한다. 오래된 제출을 수락하거나 완료 기준을 낮추지 않는다. 범위 밖의 제안만으로 수락을 막지 않으며, 새 변경으로 무효화되지 않은 검증은 재사용한다.

## 전체 결과를 확인하고 마무리한다

작업 전환과 짧은 요청 뒤에는 [재개 규약](../work/references/context.md#미완료-업무를-확인하고-재개한다)에 따라 전체 목표와 남은 통합 작업을 확인한다. 보류와 취소는 사용자 지시를 따른다. 막힌 부분은 원인과 재개 조건을 남기고 독립적으로 가능한 작업은 계속한다.

모든 하위 업무의 상태를 확인하고 담당자가 없는 일이 남았는지 살핀다. 합쳐진 결과를 실제 사용 경로에서 검증하고 전체 완료 조건별 관찰과 근거를 저장한 뒤 `complete`한다. 조율자가 [tidy](../tidy/SKILL.md)로 필요한 맥락을 정리한다. 최종 보고에는 전체 결과와 근거, 수락한 하위 결과, 남은 실패와 미확인 사항을 연결한다.
