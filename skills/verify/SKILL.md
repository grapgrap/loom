# Verify

주장한 결과를 실제 산출물에서 관찰한다. 독립적으로 호출되면 검증과 보고가 범위이며, 발견한 문제를 고치는 작업까지 자동으로 확대하지 않는다.

## 증명할 사실을 정한다

사용자가 얻어야 할 결과와 유지해야 할 동작을 관찰 가능한 조건으로 바꾼다. 버그라면 원래의 재현 조건, 리팩터링이라면 변경 전 동작, 성능이라면 변경 전 측정치를 기준으로 삼는다. 프로젝트의 기존 실행·검증 수단을 먼저 사용한다.

## 실제 경로를 확인한다

변경과 같은 표면을 사용한다. CLI는 실제 명령, UI는 실행 중인 앱의 경로, 라이브러리는 공개 API의 호출 결과, 저장은 읽어낸 결과, 파서나 마이그레이션은 실제 입력, 성능은 같은 조건의 전후 측정으로 확인한다. 문서·설정·스킬은 원본 내용·형식·참조와 소비 경로를 확인한다. 스킬의 판단이나 실행 효과를 주장하려면 실제 작업에서 사용한 과정과 결과를 관찰해야 한다.

검사가 실제 산출물을 실행하고 관찰 가능한 결과를 판정한다면 그 증거를 재사용한다. 컴파일, 모의 객체의 호출 횟수 또는 에이전트의 자기 보고를 실제 동작의 증거로 바꾸어 말하지 않는다. 저렴한 회귀 경로가 있다면 실패 조건을 고정하는 검사를 사용하되, 변경한 문장이나 내부 구현을 그대로 되풀이하는 테스트는 만들지 않는다.

설정, 계정, 기기 또는 외부 시스템 때문에 같은 표면을 사용할 수 없다면 닿을 수 있는 범위까지 확인하고 한계를 명시한다. 실행하지 못한 검증을 통과로 보고하지 않는다. 검증용 인스턴스와 임시 상태는 사용자 데이터와 격리하고 자신이 만든 것만 정리한다.

기존 수단으로 결과를 확인하기 어렵다면 관찰 방법부터 점검한다. 재현 가능성이 중요한 비교나 복잡한 검사는 일회성 작업이어도 최소 스크립트로 실행 가능하게 만든다. 실행 준비와 행동을 설명할 필요가 있으면 [검증 절차 템플릿](../../templates/verification-recipe.md)을 사용한다. 기능 지도나 하네스 전체를 자동 생성하지 않는다. 만든 검사나 절차는 실제로 한 번 실행하고, 계속 사용할 경우 갱신할 근거와 방법을 정한다.

## 결과를 보고한다

각 조건에 대해 실행한 명령·행동, 관찰한 결과와 근거, 판정을 연결한다. 판정은 확인됨, 실패, 미확인으로 구분한다. 실패나 미확인이 남으면 완료라고 선언하지 않는다. 불확실성이 검증 수단 때문인지 구현 때문인지도 구분한다.
