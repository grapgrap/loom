# Verify

무엇을 어떤 방법으로 확인할지 정하고, 필요한 검증 수단을 실행해 실제 결과를 관찰한다. 독립적으로 호출되면 요청받은 검증 준비 또는 실행과 보고를 맡는다. 준비에는 테스트나 임시 도구의 작성과 시험 실행이 포함된다. 제품 구현이나 발견한 결함의 수정은 별도로 맡은 범위가 있을 때 수행한다.

## 검증 기준을 정한다

사용자 목표, 유지할 동작과 선택한 설계의 조건을 관찰 가능한 기준으로 바꾼다. 조건별 입력, 환경, 기대 결과와 판정 근거를 정하고 프로젝트에 있는 실행 수단과 검사를 확인한다. 필수 검사, 이번 완료 조건과 사용자가 정한 허용 수준을 유지한다. 등록된 업무라면 [업무 CLI](../work/references/context-work.md)에서 현재 조건 ID와 확인 방법을 먼저 읽는다.

책임 배치나 외부 계약을 바꾼다면 [architect](../architect/SKILL.md)에서 정한 이번 범위의 책임과 계약, 전환 단계별 보존 조건을 검증한다. 장기 목표 전체의 달성과 이번 완료 조건의 충족은 구분한다.

## 변경 전에 실행 수단을 준비한다

첫 변경 전에 필요한 검사와 도구를 준비한다. 작업 중 새 사례를 발견하면 그 조건을 확인할 수단을 보강한다.

1. 기존 테스트, 재현 명령과 측정 도구를 재사용하고 부족한 부분만 보완한다. 계속 사용할 회귀 검사는 기존 테스트 체계에 추가한다. 일회성 비교에는 임시 도구를 쓸 수 있지만, 재현이 중요한 비교나 복잡한 관찰은 최소 스크립트로 다시 실행할 수 있게 한다. 기능 지도나 하네스 전체를 자동 생성하지 않는다.
2. 결함은 원래 재현 조건의 실패를, 동작 보존형 재구성은 변경 전 동작을 기준으로 확보한다. 성능 개선은 같은 입력과 환경에서 측정한 값을 기준으로 삼는다.
3. 준비한 검사나 도구를 실제로 실행해 의도한 실패나 변경 전 기준값을 관찰한다. 환경 오류를 기대한 실패와 구분한다. 실행할 수 없다면 제약과 가능한 대체 관찰을 설명하고 확인하지 못한 범위를 남긴다.
4. 도구의 위치, 실행 명령, 입력과 환경, 판정 기준, 증거를 남길 위치를 기록한다. 작업 중과 완료 후에도 같은 조건으로 실행할 수 있게 하며 기존의 유효한 실행 근거는 재사용한다.

임시 도구와 검증 데이터는 사용자 데이터와 분리한다. 준비만 맡았다면 다음 실행자에게 도구와 명령을 인계한다. 실제 검증과 인계가 끝난 일회성 도구와 임시 상태는 자신이 만든 것만 정리한다. 계속 사용할 검사에는 갱신할 근거와 방법을 정한다.

실행 준비와 절차를 별도로 설명해야 하면 [검증 절차 템플릿](../../templates/verification-recipe.md)을 사용한다. 실행 가능한 검사만으로 전달할 수 있는 작은 작업에는 별도 문서를 만들지 않는다.

## 실제 사용 경로에서 확인한다

변경된 산출물을 실제로 사용하는 경로에서 검증한다. CLI는 명령 실행, UI는 실행 중인 앱의 사용자 경로, 라이브러리는 공개 API의 결과를 확인한다. 저장은 다시 읽어낸 값으로, 파서와 마이그레이션은 실제 입력으로, 성능은 같은 조건의 전후 측정으로 확인한다.

문서, 설정과 스킬은 원본 내용, 형식, 참조와 소비 경로를 확인한다. 스킬이 판단이나 실행을 개선한다고 주장하려면 실제 작업에서 사용한 과정과 결과를 관찰해야 한다.

책임을 옮기거나 계약을 교체했다면 실제 호출과 상태 전이에서 구현과 호출자의 사용이 설계한 책임 및 계약에 맞는지 확인한다. 호출자 전환과 구 경로의 잔존은 이번 전환 단계의 조건에 비추어 판단한다. 레퍼런스의 보장을 근거로 삼았다면 이번 구현에서도 그 전제가 성립하고 결과가 관찰되는지 확인한다.

실제 산출물을 실행해 결과를 판정하는 검사가 있다면 그 증거를 재사용한다. 컴파일 성공, 모의 객체의 호출 횟수나 에이전트의 자기 보고를 실제 동작의 증거로 대신하지 않는다. 저렴하게 회귀를 확인할 수 있으면 실패 조건을 고정하는 검사를 사용한다. 변경한 문장이나 내부 구현을 그대로 되풀이하는 테스트는 만들지 않는다.

설정, 계정, 기기나 외부 시스템의 제약으로 같은 경로를 사용할 수 없다면 확인 가능한 범위와 한계를 밝힌다. 실행하지 못한 검증을 통과로 보고하지 않는다.

## 조건별 결과를 기록하고 전달한다

등록된 업무의 조건 ID에 실제 관찰을 연결한다. 단독 수행자나 조율자가 `report`에 판정(verdict), 관찰(observation)과 근거(evidence)를 저장한다. 위임받은 작업자는 CLI를 읽기 전용으로 사용하고 조건별 결과를 조율자에게 반환한다. 검증만 맡았다면 업무를 임의로 완료하거나 위임 결과를 수락하지 않는다. 기존 보고나 CLI 상태 전이의 성공을 실제 동작의 증명으로 대신하지 않는다.

조건마다 실행한 명령이나 행동, 관찰 결과, 근거와 판정을 연결한다. 판정은 확인됨, 실패와 미확인으로 구분한다. 필수 검사나 이번 완료 조건에 실패 또는 미확인이 남으면 충족했다고 보고하지 않는다. 불확실성의 원인이 구현인지 검증 수단인지도 구분한다.

준비만 맡았다면 도구와 실행 방법, 변경 전 관찰과 남은 제약을 전달한다. 검증 준비의 완료와 제품 동작의 검증 완료를 구분한다. 장기 목표까지 남은 차이나 미룬 문제도 이번 완료 조건의 판정과 나누어 설명한다.
