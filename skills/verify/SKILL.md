# Verify

검증 기준과 실행 수단을 정하고 실제 결과로 판정한다. 독립적인 요청에서는 맡은 범위에 따라 검증 수단을 준비하거나 검증을 실행하고 결과를 보고한다. 준비에는 테스트나 임시 도구의 작성과 시험 실행이 포함된다. 제품 구현이나 발견한 결함의 수정은 별도로 맡은 범위가 있을 때 수행한다. 절차와 결과 설명에는 [write](../write/SKILL.md)를 적용한다.

## 검증할 결과와 사례를 정한다

이미 합의한 완료 조건과 확인 방법을 읽고, 사용자 목표와 유지할 동작을 관찰 가능한 결과로 바꾼다. 조건별 입력, 환경과 기대 결과를 정하고 이를 확인하는 기존 검사를 찾는다. 프로젝트의 필수 검사와 사용자가 정한 허용 수준을 유지한다.

자동 테스트를 구성할 때는 완료 조건을 가장 직접적으로 확인하는 테스트 하나를 고르고, 필요한 흐름마다 테스트 하나를 둔다. 각 테스트의 조건과 기대 결과를 한 문장으로 설명할 수 있어야 한다. 같은 조건과 결과를 반복하는 검사, 변경한 문장이나 내부 구현을 그대로 되풀이하는 검사와 프레임워크 자체의 검사는 추가하지 않는다.

책임 배치나 외부 계약을 바꾼다면 [architect](../architect/SKILL.md)에서 정한 책임과 계약을 지나는 사용 경로에 사례를 연결한다. 전환 단계별 보존 조건을 확인하되 장기 목표 전체의 달성과 이번 완료 조건의 충족은 구분한다.

## 변경 전에 실행 수단을 준비한다

선택한 사례를 첫 변경 전에 실행할 수 있도록 기존 테스트, 재현 명령과 측정 도구를 재사용하고 부족한 부분만 보완한다. 회귀 검사는 기존 테스트 체계에 추가한다. 자동 테스트의 외부 서비스는 모킹해 가용성과 데이터에 의존하지 않게 하고, 무거운 외부 연동 검증은 별도 스크립트로 분리한다.

코드의 새 동작과 결함 수정은 `Red → Green → Refactor` 순서로 검증한다. 먼저 기대한 결과를 확인하는 테스트를 실행해 의도한 실패를 확보한다. 동작 보존형 재구성은 변경 전 동작을, 성능 개선은 같은 입력과 환경에서 측정한 값을 기준으로 확보한다. 환경 오류를 기대한 실패로 취급하지 않는다.

도구의 위치, 실행 명령, 입력과 환경, 판정 기준과 근거를 남길 위치를 기록해 변경 후에도 같은 조건으로 실행할 수 있게 한다. 일회성 비교에는 임시 도구를 쓸 수 있지만, 재현이 중요한 비교나 복잡한 관찰은 최소 스크립트로 남긴다. 기능 지도나 하네스 전체를 자동 생성하지 않는다. 실행할 수 없는 검사는 제약과 대체 관찰, 미확인 범위를 명시한다.

임시 도구와 검증 데이터는 사용자 데이터와 분리한다. 준비만 맡았다면 다음 실행자에게 도구와 명령을 인계한다. 검증과 인계가 끝나면 자신이 만든 일회성 도구와 임시 상태를 정리한다. 계속 사용할 검사는 어떤 변화가 생기면 어떻게 갱신할지 정한다.

실행 준비와 절차를 별도로 설명해야 하면 [검증 절차 템플릿](../../templates/verification-recipe.md)을 사용한다. 실행 가능한 검사만으로 전달할 수 있는 작은 작업에는 별도 문서를 만들지 않는다.

## 실제 사용 경로에서 확인한다

코드의 새 동작과 결함 수정에서는 변경 전 실패했던 테스트를 다시 실행해 통과하는지 확인한다. 통과 후 구조를 정리하는 동안에도 같은 결과가 유지되는지 검사한다.

변경된 산출물을 실제로 사용하는 경로에서 검증한다. CLI는 명령 실행, UI는 실행 중인 앱의 사용자 경로, 라이브러리는 공개 API의 결과를 확인한다. 저장은 다시 읽어낸 값으로, 파서와 마이그레이션은 실제 입력으로, 성능은 같은 조건의 전후 측정으로 확인한다.

문서, 설정과 스킬은 원본 내용, 형식, 참조와 실제 사용 경로를 확인한다. 스킬이 판단이나 실행을 개선한다고 주장하려면 실제 작업에서 사용한 과정과 결과를 관찰해야 한다.

책임을 옮기거나 계약을 교체했다면 실제 호출과 상태 전이가 설계한 책임과 계약에 맞는지 확인한다. 호출자를 옮겼는지, 이전 경로를 남겨도 되는지는 이번 전환 단계의 조건에 따라 판단한다. 레퍼런스의 보장을 근거로 삼았다면 이번 구현에서도 그 전제가 성립하고 기대한 결과가 나타나는지 확인한다.

실제 산출물을 실행한 유효한 검증 근거는 재사용하고, 새 사례나 변경으로 영향을 받은 검사를 보강한다. 컴파일 성공, 모의 객체의 호출 횟수나 에이전트의 자기 보고만으로 동작을 증명하지 않는다. 모킹한 테스트가 확인한 결과와 실제 외부 연동을 실행해 확인한 결과를 구분한다.

설정, 계정, 기기나 외부 시스템의 제약으로 같은 경로를 사용할 수 없다면 확인 가능한 범위와 한계를 밝힌다. 실행하지 못한 검증을 통과로 보고하지 않는다.

## 조건별 결과를 기록하고 전달한다

맡은 범위의 완료 조건마다 실행한 명령이나 행동, 관찰 결과와 검증 근거를 연결하고 확인됨, 실패와 미확인으로 판정한다. 제품 변경은 모든 테스트와 필수 검사를 통과하고 완료 조건을 충족해야 완료로 판정한다. 실패나 미확인이 남으면 그 원인이 구현인지 검증 수단인지 구분하고 영향을 설명한다.

위임받은 작업자는 조건별 결과를 조율자에게 반환한다. 검증만 맡았다면 전체 작업의 완료나 위임 결과의 수락을 임의로 결정하지 않는다.

검증 준비만 맡았다면 의도한 실패나 변경 전 기준을 확인한 결과, 도구와 실행 방법, 남은 제약을 전달한다. 의도한 테스트 실패를 확인한 것은 준비의 완료 근거이며 제품 변경의 완료 근거가 아니다. 장기 목표까지 남은 차이나 미룬 문제도 이번 완료 조건의 판정과 나누어 설명한다.
