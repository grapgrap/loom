# Propose

프로젝트의 공유 어휘로 문제와 해결의 방향을 제안하는 자기완결적 proposal을 작성한다.

**propose는 proposal만 산출한다. concept·flow·decision·plan 등 다른 loom 문서를 만들지 않는다.**

**proposal은 자기완결적이다. loom 문서를 참조하지 않으며, 외부 독자가 문서 하나만으로 이해할 수 있어야 한다.**

## Step 0 — 격리된 논의의 시작

propose는 다른 loom 스킬과 달리 `.loom/`의 문서를 로드하지 않는다. proposal은 영속 문서 생태계 바깥의 자기완결 문서이므로, 컨텍스트를 영속 문서에서 끌어오지 않는다.

프로젝트의 공유 어휘는 대화에서 오간다. 사용자가 쓰는 어휘를 그대로 받아 proposal의 언어로 삼는다. 어휘의 뜻이 대화에서 확정되지 않으면 사용자에게 물어 문서 안에서 닫는다.

무엇을 발제하려는지 사용자와 확인한다.

## Step 1 — 문제 구체화

무엇이 문제이고, 왜 지금 풀어야 하는지를 대화로 구체화한다.

- 무엇이 문제인가? 그 문제가 누구에게 어떤 영향을 주는가?
- 왜 지금인가? 이 문제를 지금 다루어야 하는 근거는 무엇인가?
- 뒷받침할 데이터나 사실이 있는가?

## Step 2 — 방향과 경계 구체화

문제의 해결을 방향성 수준에서 구체화하고, 그 범위의 경계를 함께 정한다.

- 접근 방식: 문제를 어떤 방향으로 풀 것인가? 방향성 수준에 머문다 — 구체적 태스크와 순서는 채택 후 plan의 몫이다.
- 기대 효과: 문제 해결로 무엇을 얻는가?
- 하지 않을 것: 이번 범위에서 다루지 않을 것은 무엇인가?

접근 방식이 구현 상세로 내려가려 하면 방향성 수준으로 되돌린다. proposal은 방향과 경계를 정하고, 구체적 해법은 채택 후 shape에 맡긴다.

## Step 3 — proposal 작성

구체화한 내용을 자기완결적 proposal로 작성한다.

- 템플릿: `../../templates/proposal.md`를 읽어 사용한다. 요약, 문제 정의, 접근 방식, 기대 효과, 하지 않을 것의 다섯 섹션으로 구성한다.
- 요약을 맨 앞에 둔다 — 외부 독자가 문서 전체를 한눈에 파악할 수 있어야 한다.
- 저장 위치: `.loom/proposals/{제안-이름}.md`.
- 작성에는 문서 작성 가이드(`../../references/document-authoring-guide.md`)의 기술문서 작성 기준을 적용한다 — 사실과 양태, 용어와 관계, 문장과 문단, 목록과 반복. 명확성과 정확성의 일반 기준은 외부 공유 문서에도 유효하다.
- 위키링크와 문서 간 내용 라우팅은 적용하지 않는다 — proposal은 loom 문서를 참조하지 않는 자기완결 문서이기 때문이다.

## Step 4 — 팀 공유

작성한 proposal을 팀이 확인할 수 있도록 공유한다. 공유 형태는 사용자와 합의한다 — 파일을 그대로 전달하거나, 외부에서 열람 가능한 형태로 발행한다.

proposal은 다른 loom 문서를 만들지 않고 여기서 닫힌다.

## Summary

proposal 작성 완료 시 다음 형식으로 정리한다:

```
## Propose Summary
- 제안: [제안 제목]
- 문제: [문제 한 줄 요약]
- 접근 방식: [해결 방향 한 줄]
- 파일: [생성된 proposal 파일 경로]
- 다음 단계: [팀 확인 요청, 채택 시 shape 진행]
```

## 완료 후 라우팅

proposal은 팀의 확인을 받는 문서다. 확인 결과에 따라 다음이 갈린다.

- **채택**: proposal을 준거로 삼아 `shape`로 진행한다. proposal의 문제와 방향을 입력으로 삼아 도메인과 흐름을 세분화한다.
- **보류**: proposal은 `.loom/proposals/`에 그대로 남아 재논의를 기다린다.

라우팅은 팀의 확인 이후의 일이므로, propose 세션 안에서 강제하지 않는다.
