# Write

## 독자가 무엇을 판단해야 하는가

독자가 접한 맥락과 이 글로 내려야 할 판단을 정한다. 독립적으로 읽히는 글은 처음 보는 사람도 이해할 만큼 배경을 담고, 교정·요약은 원문의 뜻과 요청한 범위를 보존한다. 빠진 사실이 결론을 바꾸면 원본이나 실행 근거를 확인한다. 작성과 교정에는 [명확한 표현](references/clarity.md)을, 문제와 판단 근거를 엮을 때는 [문서 프레이밍](references/framing.md)을 적용한다.

## 설계에서 쓴 장면으로 결과를 전달한다

PR이나 리뷰 결과는 어떤 상황에서 누구에게 무엇이 달라지는지로 시작한다. 중요한 경계가 있다면 어느 역할이 무슨 정보를 받아 무엇을 판단하는지 쓴다. 설계, 테스트, 구현 보고에 같은 역할 이름을 써서 합의와 관찰을 줄 단위 코드를 읽지 않고도 대조할 수 있게 한다.

사용자가 선택한 규칙, 설계 모델에서 검사한 속성과 가정, 실제 구현에서 실행한 조건과 결과를 근거에 맞게 표현한다. 예를 들어 검사 범위가 시도 두 번까지였으면 그 범위를 적는다. 제품의 최대 횟수나 운영 환경의 동작을 말하려면 각각에 맞는 근거가 있어야 한다. 기존 PR 템플릿이 있으면 그 형식에 맞추고 테스트·코드·재현 방법을 필요한 주장에 연결한다.

인계문은 이전 대화를 볼 수 없는 독자가 남은 결정과 다음 장면을 찾을 수 있게 쓴다. 결과 보고는 결론과 근거, 판단에 영향을 주는 미확인 사항을 한 페이지 안에 묶는다. 완성된 글을 맡았으면 독자용 본문을, 검토를 맡았으면 영향과 고칠 방향을 전한다. 다른 스킬에서 넘긴 결정이나 완료 상태는 확인된 범위 안에서 기술하고 외부 전달은 맡은 범위에서 진행한다.
