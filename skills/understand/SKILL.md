# Understand

AI의 판단과 사람의 이해가 같은 근거에서 출발하도록 현재 그림을 재구성한다. 독립적인 설명·진단 요청은 조사와 보고가 범위다. 기존 실행·검증 수단으로 관찰할 수 있지만, 설명을 위해 제품 코드를 바꾸거나 새 설계 문서를 만들지 않는다.

현재 책임과 관계를 설명하는 기준은 [원칙](../../references/principles.md)의 공통 설명에서 확인한다. 설계 판단이 필요한 조사에는 같은 문서의 적용 절차를 따른다. 원칙에 따른 평가는 조사로 확인한 현재 동작과 구분한다.

## 조사

1. 질문의 범위를 코드의 진입점, 사용자 행동 또는 도메인 책임으로 좁힌다. 범위가 모호해도 현재 맥락에서 합리적으로 해석할 수 있으면 그 해석을 밝히고 조사한다.
2. 실제 실행 경로와 핵심 데이터·상태 전이를 따라간다. 중요한 동작을 코드만으로 확인할 수 없으면 실행 결과를 관찰한다. 목적과 책임을 먼저 설명하고, 파일·함수는 그 근거로 연결한다. 파일 목록만 나열하지 않는다.
3. “왜”를 묻거나 책임·계층을 옮기려는 변경에 앞선 조사라면 관련 커밋, PR, 이슈, 문서와 테스트에서 형성 이유를 찾는다. 현재 코드가 무엇을 하는지와 과거의 결정 이유를 혼동하지 않는다.
4. 출처가 직접 뒷받침하는 사실, 그로부터의 추론, 아직 모르는 것을 구분한다. 이유를 찾지 못했으면 기록 부재를 알린다. 과거 기록이 현재 코드와 충돌하면 현재 동작을 다시 확인하고 충돌을 알린다.

## 설명

관련 도메인의 목적과 용어, 사용자의 요청이 지나는 경로, 책임 경계, 중요한 제약을 필요한 만큼만 보여준다. 이해를 돕는다면 작은 전후 비교나 흐름도를 사용한다. 코드를 주석처럼 줄마다 풀어쓰지 않는다.

변경을 위한 조사에서는 보존할 계약, 변경할 책임과 미확인이 다음 판단에 주는 영향을 전달한다. 이미 확인한 근거를 실행자가 다시 찾게 하지 않는다. 변경은 [work](../work/SKILL.md), 설계는 [architect](../architect/SKILL.md)로 이어간다. 조사 결과를 프로젝트의 영속 설계 문서로 자동 승격하지 않는다.
