# Task

이번 태스크에서 실행할 내용을 요약하고 사용자의 확인을 받은 뒤 plan의 변경안을 구현하고 검증한다.

**각 태스크는 실행 요약을 제시하고 사용자의 확인을 받은 뒤 구현한다. 이미 같은 실행 내용을 확인받았다면 확인을 반복하지 않는다.**

**plan은 살아있는 문서다. 실행 중 plan이 현실과 어긋나면 plan을 맹신하지 말고 갱신한다.**

## Step 0: 컨텍스트 로드

1. 작업 대상 프로젝트의 `.loom/index.md`를 읽어 도메인 전체 지도를 파악한다.
2. 대상 plan 파일을 읽어 Plan의 목적, 현재 동작과 변경안, 예상 영향과 미확인 사항, 전체 결과 의존과 태스크별 진행 상태를 파악한다.
3. 대상 태스크의 목적, 수행할 변화, 제외, 완료 결과, 검증과 선행 결과를 구현 입력으로 읽는다. 제외가 없으면 별도 제약을 추론하지 않는다.
4. 대상 태스크가 요구하는 선행 결과가 성립했는지 확인한다. 선행 결과가 성립하지 않았으면 구현을 시작하지 않고 먼저 실행할 태스크를 제안한다.
5. 대상 태스크와 Plan의 목적에서 좁은 검색어를 만들고 `aeira search -s {프로젝트의 .loom 경로} "{검색어}"`로 관련 concept과 flow 후보를 찾는다. 결과가 비면 표현을 바꿔 재시도한다.
6. 후보 노드에 `aeira graph neighbors -s {프로젝트의 .loom 경로} --direction=outgoing "{노드}"`를 실행해 연결된 concept과 flow를 확장한다. 노드는 `.loom` 기준 경로 형식이다.
7. 후보 문서를 읽고 대상 태스크에 맞는 concept과 flow만 선별하여 구현의 도메인 구성을 파악한다.
8. decision은 이 단계에서 일괄로 읽지 않는다. 실행 중 발견을 처리하거나 구현 대안을 평가할 때 이전 결정을 확인해야 하는 경우에만 해당 맥락으로 `aeira search -s {프로젝트의 .loom 경로} "{검색어}"`를 실행한다. 관련 concept이나 flow가 있으면 `aeira graph neighbors -s {프로젝트의 .loom 경로} --direction=incoming "{노드}"`로 이를 참조하는 decision 후보를 보강한다. 맥락에 맞는 decision만 읽는다. 같은 사안이 충돌하면 decision concept의 최신 우선 규칙에 따라 순번이 큰 decision을 따른다.

사용자가 특정 태스크를 지정한 경우 해당 태스크에 집중한다.
지정하지 않은 경우, 선행 결과가 모두 성립한 미완료 태스크 중 다음으로 실행할 태스크를 제안한다.

## Step 1: 문서 작성 가이드 로드

`../../references/document-authoring-guide.md`를 읽는다.

decision을 기록하거나 plan을 처음 갱신하기 전에 가이드를 로드한다. 이후 task가 Loom 문서를 작성하거나 검증할 때 이 가이드를 적용한다.

## Step 2: 룰 카탈로그 로드

`.loom/rules/index.md`를 읽어 어떤 룰과 컨벤션이 있는지 카탈로그를 인지한다.

rule은 이 프로젝트에서 항상 지켜져야 하는 강제적 합의, convention은 강하게 권장되지만 대체 가능한 형태이다. 인덱스를 통해 항목 목록과 각 항목의 호출 상황을 파악한다. 본문은 활용 시점에 필요한 항목을 골라낸 뒤 로드한다.

## Step 3: 실행 요약과 사용자 확인

구현 전에 이번 단계에서 실행할 내용을 요약한다. plan에서 합의한 변경안을 이어받으며, 관련 코드와 선행 실행 결과를 확인하여 현재 상태에서도 유효한지 대조한다.

### 실행 요약

- 전체 변경안에서 이번 태스크가 맡는 부분
- 바꿀 내용과 예상되는 동작 변화
- plan에서 합의한 주의점과 이번 태스크의 검증 방법
- 선행 실행 결과와 새로 확인한 사실이 이번 실행에 미치는 영향

합의된 내용과 새로운 판단이 필요한 사항을 구분한다. 이미 검토한 구현 방향을 처음부터 다시 설계하거나 모든 태스크에 수도코드를 요구하지 않는다. 사용자가 판단하는 데 필요한 구체성은 유지한다.

사용자가 실행 요약을 확인하고 실행에 동의하면 구현한다. 같은 실행 내용을 앞선 대화에서 이미 확인받았다면 그 합의를 이어받는다. plan 전체의 합의만으로 개별 태스크의 실행 확인을 대신하지 않는다.

### 실행 전·중 발견의 처리

예상과 다른 사실은 합의한 변경 방향과 영향 판단을 바꾸는지로 분류한다. 단순한 변경량이나 현재·후속 태스크의 구분으로 판단하지 않는다.

- 합의한 방향, 예상 동작, 변경 범위와 다른 작업의 전제가 유지되면 구현 세부는 작업 중 해결할 수 있다.
- 새로운 부작용이나 선택으로 주요 판단 또는 다른 작업의 전제가 달라지면 해당 판단에 의존하는 구현을 멈춘다. 달라진 사실, 영향과 대안을 사용자에게 설명하고 plan에서 관련 변경안과 작업을 다시 검토한다. plan 전체를 다시 만들 필요는 없다.
- concept이나 flow의 의미 또는 경계를 바꿔야 하면 shape에서 해당 설계를 재검토하도록 사용자와 합의한다. task는 concept·flow·index를 직접 변경하지 않는다.

기존 합의에 없던 선택도 같은 기준으로 검토한다. 도메인 책임, 외부 동작, 변경 범위나 후속 작업의 전제를 정하는 선택을 구현 세부로 취급하지 않는다. 미확인 사항은 plan에서 정한 시점에 확인하고, 그 결과가 변경 방향이나 영향 판단을 바꾸면 의존하는 실행 전에 다시 검토한다.

사용자와 재검토한 뒤 영향받는 변경안·태스크·검증·결과 의존을 갱신한다. 현재 태스크의 완료 결과나 제외를 사용자와 다시 합의하지 않고 바꾸지 않는다. 후속 작업도 주요 판단이 바뀌면 갱신 후 통보하는 것으로 확인을 대신하지 않는다.

비자명한 선택이 설계나 구현의 형태를 바꾸면 사용자의 선택 후 decision에 근거를 기록한다. 템플릿은 `../../templates/decision.md`이며 파일 이름은 `{NNNN}-{결정-제목}.md`다. plan에는 실행에 필요한 선택의 결과와 제약을 반영한다.

합의를 바꾸지 않는 기술적 사실도 남은 실행에 필요하면 영향받는 plan 위치에 반영한다. 실행 중 발견을 시간순으로 누적하거나 남은 실행에 필요하지 않은 코드 상세를 중복하지 않는다.

### 임시 핸드오프

사용자가 명시적으로 요청하고 현재 태스크가 완료되지 않았으면 현재 태스크에 임시 핸드오프를 작성한다. 사용자가 요청하지 않으면 task가 필요성을 추론하여 작성하지 않는다.

임시 핸드오프에는 다음 실행자가 이어서 수행할 재개 지점과 아직 끝나지 않은 작업만 기록한다. 태스크 실행을 재개하거나 태스크를 완료하면 임시 핸드오프를 제거한다.

## Step 4: 구현

합의한 구현 방안에 따라 코드나 문서를 변경한다.

### 구현 방식

사용자의 기호에 따라 실제 파일을 변경하거나 대화에서 초안을 제시한다. 기존 코드와 문서의 컨벤션을 따르되, 사용자의 선호를 우선한다.

### 룰 카탈로그 활용

구현할 때 인지한 룰 카탈로그를 도구 선택 절차로 활용한다:

1. 지금 수행하려는 행동을 의식적으로 명시한다
2. 카탈로그에서 그 행동에 적용될 가능성 있는 항목을 골라낸다
3. 골라낸 항목의 본문 파일을 로드해 적용 방식을 파악한다
4. 본문에 따라 코드나 문서를 변경한다

### 반복

사용자의 피드백에 따라 구현을 교정한다. 구현 중 새로운 사실이 드러나면 Step 3의 "실행 전·중 발견의 처리"를 즉시 적용한다. Plan 갱신을 구현 완료 시점까지 미루지 않는다.

## Step 5: 결과 검증과 완료

Plan에 명시된 검증과 변경 유형에 맞는 검사를 실행한다. 예상한 동작 변화와 부작용 대응이 구현에 반영되었는지 확인한다. 검증 결과를 완료 결과와 대조하고 제외한 범위가 바뀌지 않았는지 확인한다.

검증이 실패하거나 완료 결과가 성립하지 않았으면 태스크를 완료 처리하지 않는다. 작업을 중단할 때 사용자가 명시적으로 요청하면 Step 3에 따라 임시 핸드오프를 작성한다.

완료 결과가 성립하면 실행 중 발견이 변경안과 남은 작업에 빠짐없이 반영되었는지 확인한다. 반영할 사실이 없으면 태스크의 결과 계약과 결과 의존을 유지한다. 확인을 마친 뒤 진행 상태를 완료로 갱신하고 현재 태스크의 임시 핸드오프를 제거한다.

### 작성 결과 검증

Plan의 완료 처리를 마친 뒤 이번 task에서 생성하거나 수정한 모든 Loom 문서를 문서 작성 가이드에 따라 검증한다. 가이드를 충족하지 못한 문서는 교정하고 다시 검증한다. 모든 문서가 검증을 통과한 뒤 그래프를 갱신한다.

### 그래프 갱신

`.loom/` 내 문서를 생성하거나 수정한 후 `aeira sync -s {프로젝트의 .loom 경로}` 를 실행한다.

## Summary

태스크 구현 완료 시 다음 형식으로 정리한다:

```
## Task Summary
- 태스크: [수행한 태스크 요약]
- 방향성: [합의된 접근 방식 한 줄]
- 완료 결과: [구현으로 성립한 결과]
- 검증: [실행한 검증과 결과]
- 산출물: [생성/수정된 파일 목록]
- Decisions: [기록된 decision 파일 목록, 없으면 생략]
- Plan 상태: [완료 처리한 태스크와 실행 중 갱신한 변경안과 남은 작업]
```
