# 실행 환경과 저장소 운영

의존성 오류, 저장 권한 문제, 저장 위치 조사나 명시적인 삭제 요청에만 읽는다. 일상적인 재개는 [작업 맥락](context.md)을 따른다.

## 실행 환경을 준비한다

Node.js 22.18 이상인 22.x, 24.x 또는 26 이상과 Git이 필요하다. JavaScript 런타임은 Node만 지원한다. `.ts` 파일을 빌드하거나 npm 의존성을 설치하지 않아도 CLI를 직접 실행할 수 있다. 실행 환경 오류는 종료 코드 `2`와 다음 식별자로 구분한다.

| 오류                    | 필요한 조치                                                         |
| ----------------------- | ------------------------------------------------------------------- |
| `LOOM_NODE_MISSING`     | 설치된 Node 경로를 연결하거나 Node를 설치한다.                      |
| `LOOM_NODE_UNSUPPORTED` | Node.js 22.18 이상인 22.x, 24.x 또는 26 이상을 선택하거나 설치한다. |
| `LOOM_GIT_MISSING`      | 설치된 Git 경로를 연결하거나 Git을 설치한다.                        |
| `LOOM_GIT_UNUSABLE`     | Git의 경로, 권한과 런타임을 확인하고 복구한다.                      |

같은 실행 환경에서 `node --version`, `git --version`을 확인한다. 호스트가 제공하는 런타임과 기존 버전 관리 도구를 먼저 확인한다. 사용할 실행 파일이 없으면 기존 패키지 관리자 또는 [Node](https://nodejs.org/en/download)나 [Git](https://git-scm.com/install/) 공식 배포본으로 준비한다. 프로젝트의 Node 버전 설정은 유지한다.

설정 후 버전을 확인하고 실패한 원래 명령을 재시도해 복구 여부를 판단한다. 일반 저장소 오류는 종료 코드 `1`이며, Git을 재설치하거나 초기화해서 해결하려 하지 않는다. Git은 같은 저장소의 워크트리를 식별하는 데 사용하며 기록을 저장하거나 커밋하지 않는다.

## 저장 권한과 실패를 처리한다

기본 저장 위치는 체크아웃 밖이므로 실제 경로에 적용되는 호스트의 쓰기 제한을 확인한다. 읽기에 성공해도 쓰기 권한이 확보된 것은 아니다.

1. `location`의 `projectDirectory`와 호스트의 쓰기 허용 범위를 대조한다. `EPERM`이나 `EACCES`가 발생하면 샌드박스 제한과 파일 소유권이나 접근 권한 문제를 구분한다. 쓰기 제한을 이미 확인했으면 같은 실패를 반복하지 않는다.
2. 호스트의 승인 절차로 필요한 저장 명령의 권한을 요청한다. 요청에는 실제 절대 경로, 저장 목적과 현재 쓰기가 제한된 이유를 포함한다. Codex의 `exec_command`에서는 `sandbox_permissions: "require_escalated"`와 사유를 담은 `justification`을 사용한다.
3. 승인되면 같은 프로젝트와 데이터 경로에서 같은 입력으로 재시도하고 결과를 확인한다. `record` 재시도에는 오류의 `--key`를 유지한다. 자동 승인 호스트에서도 이 절차를 따르며, 이미 정한 저장 선택을 사용자에게 다시 확인하지 않는다.

권한 요청 사유의 예:

> 다음 세션과 다른 워크트리에서도 맥락을 다시 읽도록 `<project-directory>`에 이 프로젝트의 기록을 저장하려 합니다. 이 경로가 현재 샌드박스의 쓰기 허용 범위 밖이어서 해당 저장 명령에 추가 권한이 필요합니다.

권한을 받을 수 없으면 실패한 경로와 명령을 알린다. 저장 경로를 조용히 바꾸거나 파일이나 호스트의 권한을 임의로 변경하지 않는다. 저장이나 복원을 해결하지 못해도 현재 대화와 산출물로 맡긴 작업을 계속하고 그 한계를 알린다.

CLI는 잠금과 임시 파일 교체로 기록을 보호한다. 잠금이 남아 있으면 오류의 PID와 실행 중인 프로세스를 대조하고, 작성자가 없음을 확인한 뒤 제거한다. 손상되거나 지원하지 않는 형식의 데이터를 빈 기록으로 덮어쓰지 않는다.

## 저장 위치와 사용자 제어

| 실행 환경 | 기본 데이터 루트                                       |
| --------- | ------------------------------------------------------ |
| macOS     | `~/Library/Application Support/loom`                   |
| Windows   | `%LOCALAPPDATA%\loom`                                  |
| Linux     | `$XDG_DATA_HOME/loom`, 미설정 시 `~/.local/share/loom` |

데이터 루트는 `--data-dir`, `LOOM_DATA_DIR`, OS 기본값 순으로 선택한다. 직접 지정하는 경로는 절대 경로여야 한다. 프로젝트 ID는 Git 공통 디렉터리의 실제 경로에서 구한다. 같은 로컬 저장소의 워크트리는 기억을 공유하며, 별도 클론이나 기기 간 동기화는 제공하지 않는다. WSL은 Linux 경로를 사용한다.

```text
<data-root>/projects/<project-id>/
├── works/<work-id>/notes.json       일상 추가 기록
├── evidence/ledger.json            불변 근거, 정정 관계와 요청 결과
├── work-state.json                 구조화된 업무, 관계, 조건, 제출, 수락의 현재 상태와 이력
├── tidy.json                       기억, 그래프, 기존 업무 요약, 결과 리포트와 처리 지점
├── tidy-snapshots/<id>.json         준비한 범위의 메타데이터
├── context/<memory-id>.json         기존 기억 원본
└── works/<work-id>/checkpoint.json  기존 진행 상태 원본
```

사용자가 조회나 수정을 요청하면 관련 원본과 정리 결과를 확인한다. 의미의 정정은 evidence correct, 표현의 정리는 tidy로 구분한다. 삭제에는 다음 명령을 사용한다.

| 삭제 대상                   | 명령과 리비전 기준                                                                                            |
| --------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `remember` 원본이 있는 기억 | `forget --id <id> --revision <n>`. `read`로 확인한 원본의 현재 리비전을 사용하며 모든 원본 리비전을 제거한다. |
| tidy에서만 만든 기억        | `forget --id <id> --revision <n>`. `recall`의 리비전을 사용하며 정리 이력에서 제거한다.                       |
| `record` 원본               | `forget --ref note:<work>@<number>`                                                                           |

원본을 삭제하면 그 원본을 `sources`나 `evidence`의 근거로 삼는 정리 결과도 모든 정리 이력에서 제거한다. 삭제된 입력의 재시도나 오래된 `snapshot`으로 내용을 복원하지 못하게 한다. `supersedes`로만 연결된 기억은 현재 근거가 남아 있으므로 연결만 제거하고 기억은 유지한다.

기억의 경험을 패턴과 현재 필요한 구체 기억에 수용할 때는 [tidy의 수용 계약](../../tidy/references/consolidation.md#경험을-다른-기억에-수용한다)을 사용한다. 수용된 현재 본문을 제거하는 `absorb`와 원본 및 그 근거에 의존하는 내용을 지우는 `forget`은 서로 다른 동작이다.

remember와 기존 checkpoint의 호출 및 데이터도 지원한다. 두 명령을 직접 다룰 때는 [이전 계약](context-legacy.md)을 읽는다. location, recall, discover, context prepare, evidence read/check/result, search, read, graph, tidy status/result, work show/result는 조회만으로 저장 디렉터리를 만들지 않는다. 같은 프로젝트를 다루는 작업자는 work 원본과 새 업무 계약을 지원하는 CLI를 사용한다.
