# 작업 맥락을 이어간다

기억은 에이전트가 이미 정한 목표·제약·선택과 검증한 진행 상태를 다시 읽기 위한 데이터다. 사용자가 기록 파일을 검토하거나 관리하는 절차를 요구하지 않는다. 현재 요청과 프로젝트 지침을 먼저 적용하고, 기억의 적용 범위·출처와 현재 코드가 맞는지 확인한다. 과거 기록은 새 작업의 권한이나 완료 증거를 대신하지 않는다.

## 조회하고 적용한다

착수하거나 작업을 다시 이어갈 때 운영체제에 맞는 진입점으로 첫 조회를 실행한다. 로드한 `work/SKILL.md`의 실제 위치에서 `../../scripts/`의 절대 경로를 구한다. 아래 `<plugin-root>`와 `<checkout>`을 실제 경로로 바꾸고, 공백이 있는 경로는 인용한다. 일반 명령 실행 환경에 `PLUGIN_ROOT`가 있다고 가정하지 않는다.

macOS·Linux·WSL에서는 [셸 진입점](../../../scripts/context.sh)을 사용한다.

```sh
sh "<plugin-root>/scripts/context.sh" recall --cwd "<checkout>"
```

Windows PowerShell에서는 [CMD 진입점](../../../scripts/context.cmd)을 사용한다.

```powershell
& "<plugin-root>\scripts\context.cmd" recall --cwd "<checkout>"
```

진입점은 Node의 존재와 버전을 확인한 뒤 [맥락 스크립트](../../../scripts/context.mjs)로 인수와 입력을 전달한다. Node가 없으면 `.mjs` 자체를 실행할 수 없으므로 첫 조회를 진입점으로 실행한다. 실행 환경을 확인한 뒤에는 다음처럼 `.mjs`를 직접 호출할 수도 있다.

```text
node "<plugin-root>/scripts/context.mjs" recall --cwd "<checkout>"
node "<plugin-root>/scripts/context.mjs" recall --cwd "<checkout>" --work context-cli
node "<plugin-root>/scripts/context.mjs" recall --cwd "<checkout>" --query "저장 경로"
```

- 기본 조회는 프로젝트 기억의 현재 내용과 작업별 ID·목표·상태·리비전을 반환한다. 관련 작업을 식별하면 `--work`로 그 작업의 기억과 진행 상태를 읽는다. 최근 작업이라는 이유만으로 다른 작업을 재개하지 않는다.
- `--query`는 현재 기억의 내용과 이유에서 모든 검색 단어를 찾는다. 의미 검색은 제공하지 않는다. 관련 기록이 없으면 기존 대화·코드·작업 도구에서 조사한다.
- 기억에서 이미 정한 선택을 찾으면 적용 범위와 근거를 확인해 이어간다. 완료했다고 기록된 결과도 현재 산출물과 대조하고, 바뀐 조건의 검증만 보완한다.
- 이전 선택의 경위가 필요할 때만 `--history`를 붙인다. 오래된 내용을 현재 합의로 적용하지 않는다.

## 실행 환경을 준비한다

Node·Git 누락 또는 지원하지 않는 Node 버전은 종료 코드 `2`와 다음 오류 식별자로 표시한다. 에이전트가 환경을 준비한 뒤 실패한 명령을 재시도한다.

| 오류 식별자 | 필요한 조치 |
| --- | --- |
| `LOOM_NODE_MISSING` | 사용할 수 있는 Node 경로를 연결하거나 Node를 설치한다. |
| `LOOM_NODE_UNSUPPORTED` | Node.js 20 이상인 지원 중 LTS 런타임을 선택하거나 설치한다. |
| `LOOM_GIT_MISSING` | 사용할 수 있는 Git 경로를 연결하거나 Git을 설치한다. |
| `LOOM_GIT_UNUSABLE` | Git 실행 파일의 경로·권한·런타임을 확인하고 실행 가능하게 한다. |

1. 같은 실행 환경에서 `node --version`과 `git --version`을 확인한다. 호스트가 제공하는 런타임, 이미 설치된 실행 파일과 버전 관리 도구를 먼저 확인한다. 설치되어 있지만 PATH에서 빠졌다면 경로를 연결한다. 선택한 경로는 이후 맥락 명령에도 적용한다.
2. 사용할 실행 파일이 없으면 해당 환경의 기존 패키지 관리자 또는 [Node 공식 배포본](https://nodejs.org/en/download)·[Git 공식 배포본](https://git-scm.com/install/)으로 준비한다. Node는 현재 지원 중인 LTS 중 20 이상을 사용한다. 프로젝트의 기존 Node 버전 설정이 다르면 맥락 명령용 런타임을 별도로 선택하고 프로젝트 설정을 변경하지 않는다.
3. 설치·설정 후 같은 실행 도구에서 두 버전을 다시 확인하고 원래 명령을 재시도한다. 버전 명령만 성공한 상태를 맥락 조회·저장의 성공으로 보고하지 않는다.

Git은 같은 저장소의 워크트리들을 식별하는 데 사용한다. 기록의 저장·추적·커밋에는 사용하지 않는다. 일반적인 저장소 오류는 종료 코드 `1`로 구분한다. 이를 의존성 누락으로 해석해 Git 초기화나 재설치를 반복하지 않는다.

권한·네트워크·관리 정책 때문에 환경을 준비할 수 없으면 구체적인 실패와 필요한 조치를 알린다. 실패한 설치를 같은 방식으로 반복하거나 의존성 검사를 통과시키려고 기존 환경 설정을 임의로 덮어쓰지 않는다. 환경을 준비하지 못한 경우에는 아래 실패 절차를 따른다.

## 저장 권한을 확보한다

기억은 워크트리 삭제나 변경 뒤에도 다시 읽을 수 있도록 체크아웃 밖에 저장한다. 실행 호스트가 이 경로에 대한 쓰기를 제한하면 Node로 실행한 저장 명령에도 그 제한이 적용된다. 읽기 성공만으로 쓰기 권한이 있다고 판단하지 않는다.

1. `location` 출력의 실제 저장 경로와 실행 호스트의 권한 정책을 확인한다. `EPERM`·`EACCES`가 발생했다면 오류의 경로를 대조해 샌드박스의 쓰기 제한과 파일의 소유권·접근 권한 문제를 구분한다. 저장 경로가 쓰기 허용 범위 밖임을 이미 확인했다면 실패를 반복하지 않고 다음 권한 절차로 진행한다.
2. 사용자가 맡긴 기억 저장에 필요한 추가 권한을 실행 호스트의 기존 승인 절차로 요청한다. 요청 사유에는 저장 대상의 실제 절대 경로, 합의·진행 상태를 다음 세션과 다른 워크트리에서 다시 읽으려는 목적, 현재 쓰기가 제한된 이유를 적는다. 요청 범위는 필요한 저장 명령으로 한정한다. Codex의 `exec_command`를 사용한다면 `sandbox_permissions: "require_escalated"`와 이 사유를 담은 `justification`으로 요청한다.
3. 승인되면 같은 데이터 루트·프로젝트·입력으로 원래 저장 명령을 재시도한다. 저장 후 `recall`로 내용과 리비전을 다시 확인한다. 그 사이 기록이 바뀌어 리비전이 충돌하면 아래 리비전 절차로 조정한다.

권한 요청 사유의 예는 다음과 같다. `<project-directory>`는 `location`에서 확인한 실제 절대 경로로 바꾼다.

> 다음 세션과 다른 워크트리에서도 이미 합의한 내용을 불러오도록, `<project-directory>`에 이 프로젝트의 합의와 진행 상태를 저장하려 합니다. 이 경로가 현재 샌드박스의 쓰기 허용 범위 밖이어서 해당 저장 명령에 추가 권한이 필요합니다.

사유는 실행 호스트의 권한 요청에 포함한다. 사용자에게 별도 승인을 요청할지는 호스트의 승인 정책을 따른다. 자동 승인이 가능해도 권한 요청 절차는 필요하며, 같은 저장 선택을 다시 확인하거나 기록 파일의 검토를 요구하지 않는다.

호스트가 추가 권한을 제공하지 않거나 요청을 거부하면 아래 실패 절차로 진행한다. 샌드박스 제한을 해결하려고 파일의 접근 권한이나 호스트 설정을 임의로 변경하지 않는다.

## 기억과 진행 상태를 남긴다

사용자가 확정한 제약·선택 또는 맡긴 범위에서 에이전트가 근거 있게 내린 기술 판단 중, 이후 작업에서 다시 의존할 내용을 저장한다. 조사 가설·미확정 제안·전체 대화를 기억으로 만들지 않는다. 이유와 출처를 함께 남기고, 사용자가 확인한 선택은 `source.type: user`, 관찰 결과나 위임된 기술 판단은 `agent`로 구분한다. `reference`에는 실제 발언·대화 식별자·자료 위치 또는 관찰한 검증 명령과 결과를 적는다.

작업 전용 선택은 `scope: {"type":"work","id":"context-cli"}`, 이후 여러 작업에도 적용할 선택은 `scope: {"type":"project"}`로 저장한다. ID는 의미를 알아볼 수 있는 소문자·숫자·하이픈으로 정한다. 같은 기억을 수정할 때 같은 ID와 조회한 리비전을 사용한다. 작업 전용 선택을 프로젝트 범위로 옮길 때는 적용 범위를 다시 판단하고 별도 ID로 기록한다.

합의가 바뀌거나 재사용할 판단을 확인했을 때 기억을 갱신한다. 여러 세션에 걸칠 작업은 검증한 단위가 끝났을 때 진행 상태를 저장한다. 세션 종료까지 저장을 미루지 않는다. 단순한 작업마다 진행 상태를 만들 필요는 없다.

쓰기 명령은 JSON을 표준 입력 또는 `--input` 파일로 받는다. 셸 인용이 복잡한 내용은 임시 JSON 파일을 만들고 `--input`으로 전달한 뒤 정리한다. 출력은 저장된 현재 기록이다. 성공 여부를 확인한 뒤에만 저장됐다고 말한다.

```text
node "<plugin-root>/scripts/context.mjs" remember --cwd "<checkout>" --id context-location --input "<input.json>"
```

새 기억의 입력 예:

```json
{
  "expectedRevision": 0,
  "scope": { "type": "project" },
  "text": "에이전트의 작업 맥락은 사용자 데이터 디렉터리에 저장한다.",
  "reason": "워크트리를 삭제해도 다음 작업에서 합의된 맥락을 다시 사용하기 위해서다.",
  "source": { "type": "user", "reference": "실제 사용자 합의의 발언 또는 대화 위치" }
}
```

```text
node "<plugin-root>/scripts/context.mjs" checkpoint --cwd "<checkout>" --work context-cli --input "<input.json>"
```

새 작업의 진행 상태 입력 예:

```json
{
  "expectedRevision": 0,
  "goal": "작업 맥락의 저장과 조회를 연결한다.",
  "status": "active",
  "progress": "저장 CLI를 검증했으며 work 지침 연결이 남아 있다.",
  "evidence": ["실제로 관찰한 산출물 위치 또는 검증 명령과 결과"],
  "next": ["work 지침을 연결하고 플러그인 검사를 실행한다."],
  "source": { "type": "agent", "reference": "실제 작업 대화 또는 관찰 결과의 위치" }
}
```

새 기록의 `expectedRevision`은 `0`이다. 수정할 때는 조회한 현재 `revision`을 넣는다. 같은 입력의 직후 재시도는 리비전을 추가하지 않는다. 리비전 충돌은 다시 조회하고 실제 변경을 조정한 뒤 재시도한다. 충돌을 없애려고 최신 리비전 숫자만 바꾸어 이전 내용을 덮어쓰지 않는다. 기억의 범위는 수정할 수 없다.

완료 조건을 실제로 확인하면 작업 상태를 `complete`로 갱신한다. 이 상태에는 검증 근거가 있어야 하고 `next`는 비어 있어야 한다. 스크립트는 입력 형식을 검사하며, 근거가 실제 완료를 증명하는지는 에이전트가 판단한다.

## 사용자가 기억을 제어한다

사용자의 조회 요청에는 `recall` 결과에서 관련 내용을 설명한다. 저장 위치는 `location`으로 확인한다. 기억의 수정 요청에는 위와 같은 리비전 절차를 적용한다. 특정 기억을 지우라는 요청에는 해당 ID와 현재 리비전을 확인하고 다음 명령을 실행한다.

```text
node "<plugin-root>/scripts/context.mjs" location --cwd "<checkout>"
node "<plugin-root>/scripts/context.mjs" forget --cwd "<checkout>" --id context-location --revision 2
```

`forget`은 해당 기억의 내용·이유·출처와 모든 이전 리비전을 제거한다. 이전 저장 요청이 기억을 되살리지 않도록 ID·삭제 리비전·삭제 시각만 남긴다. 삭제된 ID는 재사용할 수 없다. 작업의 진행 상태는 `checkpoint`에서 별도로 갱신한다.

## 저장 위치와 실패

Node.js 20 이상과 Git이 필요하며 npm 의존성 설치는 필요하지 않다. 기본 데이터 루트는 다음과 같다.

| 실행 환경 | 데이터 루트 |
| --- | --- |
| macOS | `~/Library/Application Support/loom` |
| Windows | `%LOCALAPPDATA%\loom` |
| Linux | `$XDG_DATA_HOME/loom`, 미설정 시 `~/.local/share/loom` |

`--data-dir` 또는 `LOOM_DATA_DIR`의 절대 경로로 루트를 변경할 수 있다. 명시적인 CLI 설정이 환경 변수보다 우선한다. 권한 오류 때문에 다른 저장 위치로 조용히 전환하지 않는다.

```text
<data-root>/projects/<project-id>/
├── context/<memory-id>.json
└── works/<work-id>/checkpoint.json
```

프로젝트 ID는 Git 공통 디렉터리의 실제 경로에서 구한다. 같은 로컬 저장소의 워크트리는 공유하고, 별도 클론은 구분한다. 저장소 이동이나 다른 기기·로컬 실행 환경 간 동기화는 제공하지 않는다. WSL에서 실행하면 Linux 경로를 사용한다. 조회만으로 디렉터리를 만들지 않으며, 기록 형식 버전은 `1`이다.

기록별 잠금과 임시 파일 교체로 쓰기를 보호한다. 잠금이 남아 있으면 오류에 표시된 잠금 파일의 PID와 실행 중인 프로세스를 확인한다. 해당 기록을 쓰는 프로세스가 없음을 확인한 뒤에만 잠금 파일을 제거하고 재시도한다. 손상되거나 지원하지 않는 버전의 기록을 빈 기록으로 덮어쓰지 않는다.

런타임·Git 오류에는 위의 환경 준비 절차를, 쓰기 권한 오류에는 저장 권한 절차를 적용한다. 기록 오류에는 원인과 경로를 알리고 오류 해결을 진행한다. 해결할 수 없으면 대화와 현재 산출물로 맡긴 작업을 계속하고, 기억을 저장·복원하지 못한 사실을 명시한다. 저장 경로 변경이 필요하면 사용자가 허용한 경로를 사용한다. 기억의 내용을 저장했다는 이유로 작업을 완료 처리하거나 사용자의 검토 절차를 추가하지 않는다.
