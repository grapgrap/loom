# 작업 맥락을 이어간다

이미 확인한 합의·제약·결과를 다음 작업에서 재사용하도록 에이전트가 맥락을 기록한다. 현재 요청과 프로젝트 지침을 먼저 적용하고, 불러온 기억을 현재 코드와 실행 상태에 대조한다. 과거 기록은 새 작업의 권한이나 완료 증거를 대신하지 않는다. 사용자에게 기억 파일의 검토·관리를 요구하지 않는다.

재사용할 합의·관찰·추론은 [증거 계약](context-evidence.md)의 `evidence append`로, 기존 판단의 변경·채택·철회는 `evidence correct`로 명시한다. 단순 작업 일지는 호환 명령인 `record`를 쓸 수 있지만 구조화된 현재 근거로 자동 승격하지 않는다. 새 업무는 [공통 업무 CLI](context-work.md)로 정의하고 진행·조건별 검증·제출·수락·완료를 즉시 저장한다. [tidy](../../tidy/SKILL.md)는 그 원본을 대조해 기억과 그래프를 갱신하며 managed 업무의 현재 상태를 변경하지 않는다. 기존 checkpoint 업무와 ref도 보존한다.

단독 업무에서는 수행자가 기록과 상태 변경을 맡는다. 위임된 서브 에이전트는 CLI를 읽기 전용으로 사용하고, 아래 기록 및 저장 절차는 조율자가 수행한다. 작업자는 읽은 명세와 근거에서 이해한 목표와 보존할 계약, 조건별 관찰과 남은 일을 호스트로 보고한다. 조율자가 실제 보고자와 근거를 연결해 기록하며 이해완료 상태는 추가하지 않는다.

## 조회하고 적용한다

로드한 `work/SKILL.md`가 있는 폴더를 기준으로 `../../scripts/context/`의 절대 경로를 구한다. 아래 `<plugin-root>`는 그 플러그인의 루트이고, `<checkout>`은 현재 저장소의 체크아웃 또는 워크트리 경로다. 예시의 경로를 실제 값으로 바꾸고 공백이 있는 경로는 인용한다.

업무 CLI로 관리하는 현재 맡긴 전체 업무를 알면 `work show --work <전체-id> --tree`로 현재 정의, 하위 업무, 선행 상태와 남은 조건을 확인한다. 판단에 필요한 기억과 원본은 선택한 업무 범위에서 보충한다. 소속 업무나 중단 뒤 복귀할 업무를 찾지 못하면 `recall`로 프로젝트의 미완료, 미검토와 결과 검토 대기 후보를 확인하고 현재 요청의 범위와 원문에 대조한다. 기존 checkpoint 업무의 조회는 [이전 계약](context-legacy.md)을 따른다.

macOS, Linux와 WSL에서 현재 전체 업무를 조회하는 예:

```sh
sh "<plugin-root>/scripts/context/cli.sh" work show --cwd "<checkout>" --work "<전체-id>" --tree
```

Windows PowerShell에서 같은 업무를 조회하는 예:

```powershell
& "<plugin-root>\scripts\context\cli.cmd" work show --cwd "<checkout>" --work "<전체-id>" --tree
```

[셸](../../../scripts/context/cli.sh)과 [CMD](../../../scripts/context/cli.cmd) 진입점은 Node의 존재와 버전을 확인한 뒤 [CLI](../../../scripts/context/cli.ts)에 인수와 stdin을 전달한다. 실행 환경을 확인한 뒤에는 `.ts`를 직접 호출할 수 있다. 다음은 선택한 업무의 기억을 보충하는 예다.

```sh
node "<plugin-root>/scripts/context/cli.ts" recall --cwd "<checkout>" --work context-cli
```

기본 `recall`은 현재 압축 맥락, 지정한 업무의 상태, 미처리 원본과 업무 탐색 요약을 반환한다. `--work`를 지정하면 탐색 목록도 해당 업무로 한정한다. 업무를 모를 때는 `--work` 없이 후보를 찾고 `work show`로 상세 상태를 읽는다. 현재 요청에 필요한 기억을 보충할 때는 `--work`로 그 업무의 범위를 선택한다. 관련 업무나 근거를 모르면 목적에 맞는 `search`로 후보를 찾는다. 최근 기록이라는 이유만으로 다른 업무를 재개하지 않는다. 한 세션에서 업무를 계속하거나 여러 세션에서 서로 다른 업무를 다룰 수 있으므로, 세션과 업무를 일대일로 대응시키지 않는다. 새 업무의 목표와 맡긴 범위는 첫 기록에 남긴다.

전체 업무 목록과 그래프, 미완료와 검토 대기 업무의 상세 본문이 필요하면 `recall --full`을 사용한다. 이때 탐색 목록은 `--work`와 관계없이 프로젝트 전체를 대상으로 한다. 이때 `works`와 `worksRemaining`, `graph`가 추가되며 기본 응답에는 세 필드가 없다. 업무 목록에는 ID, 목표, 상태와 `firstNote`, `latestNote`의 첫 기록과 최근 기록 ref 및 발췌가 있다. 정리 전에는 목표와 상태가 `null`일 수 있으므로 발췌로 관련 업무를 식별하고 필요한 본문은 `read --ref`로 확인한다.

- `pending`은 조회 범위의 미처리 원본이다. 정리된 기억·업무 상태와 함께 읽는다.
- `--limit`은 각 목록에 적용하며 기본 50, 최대 200이다. `memoriesRemaining`과 `pendingRemaining`, `--full`의 `worksRemaining`은 각 목록의 다음 페이지에 남은 항목 수다. 필요한 항목이 남으면 `--offset`을 limit만큼 늘려 같은 조건으로 조회하거나 검색과 원본 조회로 보충한다. 선택한 업무의 전체 상태인 `work`는 페이지와 무관하게 반환한다.
- `unresolved`는 미확정 판단이다. 업무에 한정된 사실은 해당 범위에서 적용하고, 완료로 기록된 결과도 현재 산출물과 대조한다.
- `unfinishedWorks`는 `active`·`blocked`·`paused`·`submitted` 업무의 ID, 목표, 상태와 원본 발췌다. 진행과 다음 행동의 상세 본문은 `work show` 또는 `recall --full`로 읽는다. submitted는 결과 검토 대기이며 작업자가 자동 재실행하지 않는다. 전체 업무 목록과 별도로 페이지를 나누므로 최근 완료 업무에 가려지지 않는다.
- `unreviewedWorks`는 상태가 없는 기록이나 현재 상태 이후 검토할 새 기록이 있는 업무다. 원문을 읽어 추가 요청·완료·보류·취소 여부를 판단한다. 목록에 있다는 이유만으로 작업을 실행하거나 재개하지 않는다.
- `awaitingReviewWorks`는 submitted 업무의 탐색 요약이다. 현재 제출과 reviewer는 `work show` 또는 `recall --full`로 읽는다. 결과 수락을 기다리는 업무이며 상태 확인용 unreviewedWorks와 구분한다. awaitingReviewWorksRemaining으로 다음 페이지를 확인한다.
- `unfinishedWorksRemaining`·`unreviewedWorksRemaining`은 각각 다음 페이지에 남은 항목 수다. 기본 목록은 `--work`로 범위를 좁히며 기억 검색어로는 좁히지 않는다. `--full`에서는 프로젝트 전체를 대상으로 한다. 현재 맡긴 업무를 식별하는 데 사용하며 다른 대화의 업무를 실행할 권한을 부여하지 않는다.
- `--query`를 붙이면 내용·이유에 모든 검색어가 포함된 현재 기억만 반환한다. 과거 원본을 조사할 때는 `search`를 사용한다.
- `--history`는 기억·업무 상태의 이전 리비전을 확인할 때 사용한다.
- 패턴에 수용된 기억은 `absorbed` 상태의 연결만 남고 현재 기억 목록에는 나오지 않는다. 수용 대상과 남겨 둔 구체 기억을 사용하며, 같은 ID로 옛 세부를 자동 복원하지 않는다. 시간 경과와 수용 여부를 혼동하지 않는다.

관계와 근거는 독립 `graph` 명령이나 `recall --full`의 `graph`에서 읽는다. 새 기록을 `pending`에서 함께 읽고 적용 범위, 미확정 상태와 조건을 확인한다. `recall`에서 `--entity`와 `--depth`는 `--full`을 함께 지정해야 한다. 관계를 더 조사하거나 `tidy`에서 진술을 구성할 때는 [그래프 계약](context-graph.md)을 읽는다.

## 미완료 업무를 확인하고 재개한다

독립적인 요청을 맡으면 `work ID`를 정하고 원래 사용자 목표를 `goal`에 보존한다. 조사나 문서 작성이 구현의 선행 단계라면 `progress`에 그 결과를, `next`에 남은 구현·검증을 둔다. 사용자와 범위를 바꾸지 않은 상태에서 구현 목표를 조사 목표로 축소해 완료하지 않는다. 짧은 질문에는 별도 업무를 만들 필요가 없으며, 작은 수정에 긴 계획 파일을 만들지 않는다.

새 업무는 [공통 업무 CLI 계약](context-work.md)에 따라 목표와 범위, 확인 가능한 criteria를 정의한다. 같은 계약으로 수행 중 진행과 다음 행동, 조건별 검증을 갱신한다. 업무 상태 변경의 입력과 리비전, 완료와 수락 조건은 해당 계약에서 확인한다. 다른 업무로 전환하기 전에는 검증한 진행과 복귀할 다음 행동을 보존한다. 처리 과정의 재사용할 판단과 출처는 `evidence append/correct`에 남긴다.

기존 managed 표시가 없는 업무는 [checkpoint 계약](context-legacy.md)을 유지한다. 계속 수행할 기존 업무는 현재 recall과 원문을 읽고 create의 adopt: true로 명세를 정의해 전환한다. 이전 ref는 보존하며 이전 완료 선언을 새 조건의 검증으로 간주하지 않는다.

| 상태        | 의미와 재개 판단                                                                                                                                    |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `active`    | 맡긴 목표가 남아 있다. 현재 범위와 실행 조건이 확인되면 별도 재지시를 기다리지 않고 계속한다.                                                       |
| `submitted` | 조율자가 수신한 작업 결과를 등록했다. 검토 근거를 확인해 수락하거나 조건별 보완을 요청한다. 작업자가 다시 수행하지 않는다.                          |
| `blocked`   | 권한·의사결정·외부 조건 때문에 진행할 수 없다. `progress`에 막힌 이유·해소 조건, `next`에 재개할 행동을 둔다. 조건이 해결됐는지 확인한 뒤 계속한다. |
| `paused`    | 사용자가 별도 지시 전까지 보류했다. 이유와 남은 행동을 보존하고 재개 지시를 기다린다.                                                               |
| `complete`  | 맡긴 목표를 검증한 근거가 있고 남은 행동이 없다. 하위 단계나 단기 요청의 완료와 전체 목표를 구분한다.                                               |
| `cancelled` | 사용자가 취소한 업무다. `progress`에 취소 근거를 보존하고 `next`를 비운다. 자동 재개하지 않는다.                                                    |

예를 들어 업무 CLI로 관리하는 기능 A를 구현하다 README 오타 수정 B를 먼저 처리하면, A의 현재 위치와 다음 행동을 보존하고 `active`를 유지한다. B를 마친 뒤 `work show --work A --tree`로 A의 남은 조건과 다음 행동을 확인해 계속한다. B의 완료만으로 전체 실행을 끝내지 않는다. 다른 업무를 잠깐 처리하는 것은 사용자 보류인 `paused`와 다르다.

짧은 요청을 마쳤을 때, 대화를 재개했을 때, 최종 응답 전에는 알고 있는 현재 맡긴 전체 업무의 `work show --work <전체-id> --tree`를 기본 점검으로 사용한다. 소속 업무나 중단 뒤 복귀할 업무를 찾지 못하면 `recall`의 미완료, 미검토와 결과 검토 대기 목록을 필요한 페이지까지 읽는다. 후보의 원문과 현재 상태, 선행 결과를 대조하고 현재 요청, 맡긴 범위와 우선순위에 따라 다음 업무를 고른다. 여러 후보의 우선순위나 권한을 알 수 없으면 해당 선택만 사용자에게 확인하고, 확인할 필요가 없는 업무는 계속한다. 다른 대화에 속한 업무는 원문과 권한을 확인하며 실행 중인 작업자에게 맡긴 업무는 중복 수행하지 않는다. 단순히 최근 기록이라는 이유로 다른 업무를 선택하지 않는다.

`pending`이 비었다는 것은 미처리 원본이 없다는 뜻이며, 미완료 업무가 없다는 뜻이 아니다. 현재 맡긴 범위의 미완료 업무를 이어가거나 실제 보류, 막힘과 취소를 확인한 뒤 실행을 마무리한다. CLI는 현재 상태와 근거를 반환하며, 다음 업무의 실행과 사용자 확인은 에이전트가 맡는다. 백그라운드 실행이나 새 세션을 자동으로 시작하지 않는다.

## 관련 업무와 적용 조건을 찾는다

업무 ID나 원본 ref가 없는 새 요청은 목적·제약·대상·조건을 검색어로 삼아 `discover --query "<검색어>"`를 실행한다. 원본과 정리본의 어휘를 함께 검색하며, 같은 원본의 리비전은 묶고 같은 업무의 독립 일지는 별개 후보로 유지한다. `next`가 있으면 같은 검색어·범위와 `--cursor`로 이어간다. 도중 원본이나 정리본이 바뀌면 cursor 충돌을 반환하므로 새 검색을 시작한다. 이미 알고 있는 유효한 근거가 있으면 처음부터 전체 검색을 반복하지 않는다.

선택할 업무와 쟁점이 정해지면 `context prepare`에 JSON을 전달한다.

```json
{ "work": "context-cli", "query": "요청 재시도 저장 결과", "refs": ["evidence:retry@1"] }
```

반환한 `work`, `candidates`, `originals`, `changes`, `gaps`를 읽는다. `changes`는 검색어·Top N·업무 필터와 별개로 후보 근거에 연결된 정정·철회를 따라간다. `basis`는 발견 범위·정정 확인·업무 ref를 묶은 재확인 기준이다. CLI는 어떤 근거가 지금 적용되는지 판정하지 않는다.

에이전트는 실제 대상과 버전·실행 조건을 대조해 적용할 근거, 역사적 배경, 미확정·미확인 근거를 구분한다. 현재 판단에 사용할 내용과 정확한 근거 ref, 적용 조건, 발견·정정 basis, 남은 공백을 함께 유지한다. 외부 locator는 읽었다는 증거가 아니다. 필요하면 원문에 접근해 실제로 읽은 위치·버전·범위를 기록한다. 연결이 없거나 접근하지 못한 근거를 검증 완료로 바꾸지 않는다.

`latest`는 원본의 최신 리비전, `active`는 정리본의 표시 상태다. 어느 것도 사실성이나 현재 적용 가능성을 보장하지 않는다. 서로 다른 코드 버전의 관찰은 동시에 맞을 수 있고, 제안은 채택되기 전까지 제안이다. 기존 note·memory·checkpoint·work 이력은 역사적 원본으로 읽으며 새 출처·적용 조건을 합성하지 않는다.

## 채택한 맥락을 다시 확인한다

중요한 판단 직전이나 논리적 작업 단위를 마친 경계에서 같은 쟁점과 채택한 refs, 직전 반환한 `basis`를 `prior`로 넣어 `context prepare`를 호출한다. `refresh.discovery`는 독립된 새 근거의 발견 범위, `refresh.corrections`는 연결된 정정, `refresh.work`는 업무 명세·진행의 변화를 구분한다. exact ref를 다시 읽는 것만으로 정정이나 새 독립 근거를 확인했다고 판단하지 않는다.

`changed`이면 영향받는 내용만 다시 읽고 적용 여부를 재판단한다. `unknown`, partial coverage, 조회 실패나 미열람 페이지가 있으면 그 공백을 유지한다. `unchanged`는 이번 조회 범위의 저장된 근거가 변하지 않았다는 뜻이며 외부 코드·문서까지 검증했다는 뜻이 아니다. 대상 버전이나 조건이 바뀌면 해당 외부 관찰을 다시 확인한다. 의미상 채택·정정이 필요하면 새 evidence 요청을 만들고, 단순 표현 정리는 tidy로 분리한다.

## 정리 시점을 판단한다

착수 시점, 검증한 단위의 경계와 작업 전환·마무리에서 `tidy status --work <id> --purpose resume`를 확인한다. 정리할 새 기록이나 현재 정리본을 검토할 필요가 있으면 [tidy](../../tidy/SKILL.md)를 실행한다. `due`는 미처리 수와 시간, 현재 표현의 크기 및 증가량에 따른 보조 신호이며 처리할 의미 있는 변경이 있다는 보장이 아니다. UTF-8 바이트 수는 검토 신호이며 토큰 수나 저장 한도가 아니다. 사용자의 명시적 정리 요청은 신호를 기다리지 않는다.

같은 입력·목적에서 이미 검토했고 변경할 것이 없다면 no-change receipt를 재사용해 종료한다. 호출마다 같은 정리본을 다시 쓰지 않는다. 선택한 범위 밖이나 새로 들어온 기록은 남은 범위로 표시한다. 여러 에이전트에서는 조율자만 기록·정리를 저장하고 작업자는 필요한 판단과 출처를 호스트로 보고한다. 백그라운드 타이머나 예약 실행은 설치하지 않는다.

## 새 내용을 짧게 기록한다

다음 판단이나 재개에 영향을 주는 합의·조건 변경·실패·검증 관찰을 확인했을 때 기록한다. 대화 전문·도구 출력 전체·추측으로 채운 필드는 넣지 않는다. 상태와 다음 행동은 work, 재사용할 주장과 실제 출처·적용 조건은 evidence, 표현의 압축·검색어 보완은 tidy가 소유한다.

[evidence 계약](context-evidence.md)에 따라 `kind`, `standing`, `scope`, `applies`, `source`, `capture`를 구분한다. 직접 확인한 관찰과 전달받은 주장, 모델 추론을 구별한다. 의미가 독립적인 판단은 별개 기록으로 남기고, 부분 정정이 필요할 주장은 `units` 또는 정확한 문자 범위로 식별한다. 출처와 조건을 모르면 현재 합의로 단정하지 않는다.

새 기록은 새 `requestKey`로 보내고 재시도에는 같은 키와 같은 입력을 쓴다. 성공 응답이나 `evidence result --key`로 확인한 뒤에만 저장됐다고 말한다. evidence 저장과 work report는 서로 다른 호출이다. 하나만 성공하면 그 결과를 보존하고 미완료 호출만 복구한다. 한 번의 의미 변경을 여러 저장소에 걸친 원자적 작업으로 가정하지 않는다.

## 필요한 원본을 검색한다

`discover`는 원본과 정리된 표현을 함께 찾는다. `search`는 이전 호환 원본 검색이며 BM25 점수 자체는 현재 타당성을 뜻하지 않는다. 영문·숫자 단어와 한글 단어·겹치는 두 글자 단위를 사용하며 의미 검색은 제공하지 않는다. 검색어를 나누고 필요한 페이지와 실제 원문을 확인한다.

`read --ref`는 `evidence:<id>@<revision>`, `memory:<id>@<revision>`, `checkpoint:<work>@<revision>`, `note:<work>@<number>`, `work:<id>@<revision>`을 읽는다. evidence에는 `evidence read --ref`도 사용할 수 있다. 정리본의 `sources`는 원본으로 연결되며, 정리본 revision·recordedAt은 원본 발언 시각이나 마지막 검증 시각이 아니다.

정리본을 읽은 뒤에도 중요한 판단에는 원본과 관련 정정을 확인한다. 기록 삭제와 의미상 철회는 다르며, `forget`은 기존 memory·note의 물리 삭제 경로다. 새 evidence의 철회는 `evidence correct`이고 원문을 보존한다. 물리 보관 정책은 이 의미 계약과 별도로 다룬다.

## 실행 환경을 준비한다

Node.js 22.18 이상인 22.x, 24.x 또는 26 이상과 Git이 필요하다. JavaScript 런타임은 Node만 지원한다. `.ts` 파일을 빌드하거나 npm 의존성을 설치하지 않아도 CLI를 직접 실행할 수 있다. 실행 환경 오류는 종료 코드 `2`와 다음 식별자로 구분한다.

| 오류                    | 필요한 조치                                                         |
| ----------------------- | ------------------------------------------------------------------- |
| `LOOM_NODE_MISSING`     | 설치된 Node 경로를 연결하거나 Node를 설치한다.                      |
| `LOOM_NODE_UNSUPPORTED` | Node.js 22.18 이상인 22.x, 24.x 또는 26 이상을 선택하거나 설치한다. |
| `LOOM_GIT_MISSING`      | 설치된 Git 경로를 연결하거나 Git을 설치한다.                        |
| `LOOM_GIT_UNUSABLE`     | Git의 경로·권한·런타임을 확인하고 복구한다.                         |

같은 실행 환경에서 `node --version`, `git --version`을 확인한다. 호스트가 제공하는 런타임과 기존 버전 관리 도구를 먼저 확인한다. 사용할 실행 파일이 없으면 기존 패키지 관리자 또는 [Node](https://nodejs.org/en/download)·[Git](https://git-scm.com/install/) 공식 배포본으로 준비한다. 프로젝트의 Node 버전 설정은 유지한다.

설정 후 버전을 확인하고 실패한 원래 명령을 재시도해 복구 여부를 판단한다. 일반 저장소 오류는 종료 코드 `1`이며, Git 재설치·초기화로 해결하려 하지 않는다. Git은 같은 저장소의 워크트리를 식별하는 데 사용하며 기록을 저장하거나 커밋하지 않는다.

## 저장 권한과 실패를 처리한다

기억은 체크아웃 밖에 저장하므로 호스트의 쓰기 제한을 확인한다. 읽기에 성공해도 쓰기 권한이 확보된 것은 아니다.

1. `location`의 `projectDirectory`와 호스트의 쓰기 허용 범위를 대조한다. `EPERM`·`EACCES`가 발생하면 샌드박스 제한과 파일 소유권·접근 권한 문제를 구분한다. 쓰기 제한을 이미 확인했으면 같은 실패를 반복하지 않는다.
2. 호스트의 승인 절차로 필요한 저장 명령의 권한을 요청한다. 요청에는 실제 절대 경로·저장 목적·현재 쓰기가 제한된 이유를 포함한다. Codex의 `exec_command`에서는 `sandbox_permissions: "require_escalated"`와 사유를 담은 `justification`을 사용한다.
3. 승인되면 같은 프로젝트·데이터 경로·입력으로 재시도하고 결과를 확인한다. `record` 재시도에는 오류의 `--key`를 유지한다. 자동 승인 호스트에서도 이 절차를 따르며, 이미 정한 저장 선택을 사용자에게 다시 확인하지 않는다.

권한 요청 사유의 예:

> 다음 세션과 다른 워크트리에서도 맥락을 다시 읽도록 `<project-directory>`에 이 프로젝트의 기록을 저장하려 합니다. 이 경로가 현재 샌드박스의 쓰기 허용 범위 밖이어서 해당 저장 명령에 추가 권한이 필요합니다.

권한을 받을 수 없으면 실패한 경로·명령을 알린다. 저장 경로를 조용히 바꾸거나 파일·호스트 권한을 임의로 변경하지 않는다. 저장·복원을 해결하지 못해도 현재 대화와 산출물로 맡긴 작업을 계속하고 그 한계를 알린다.

CLI는 잠금과 임시 파일 교체로 기록을 보호한다. 잠금이 남아 있으면 오류의 PID와 실행 중인 프로세스를 대조하고, 작성자가 없음을 확인한 뒤 제거한다. 손상되거나 지원하지 않는 형식의 데이터를 빈 기록으로 덮어쓰지 않는다.

## 저장 위치와 사용자 제어

| 실행 환경 | 기본 데이터 루트                                       |
| --------- | ------------------------------------------------------ |
| macOS     | `~/Library/Application Support/loom`                   |
| Windows   | `%LOCALAPPDATA%\loom`                                  |
| Linux     | `$XDG_DATA_HOME/loom`, 미설정 시 `~/.local/share/loom` |

데이터 루트는 `--data-dir`, `LOOM_DATA_DIR`, OS 기본값 순으로 선택한다. 직접 지정하는 경로는 절대 경로여야 한다. 프로젝트 ID는 Git 공통 디렉터리의 실제 경로에서 구한다. 같은 로컬 저장소의 워크트리는 기억을 공유하며, 별도 클론·기기 간 동기화는 제공하지 않는다. WSL은 Linux 경로를 사용한다.

```text
<data-root>/projects/<project-id>/
├── works/<work-id>/notes.json       일상 추가 기록
├── evidence/ledger.json            불변 근거·정정 관계와 요청 결과
├── work-state.json                 구조화된 업무·관계·조건·제출·수락의 현재 상태와 이력
├── tidy.json                       기억·그래프·기존 업무 요약·결과 리포트와 처리 지점
├── tidy-snapshots/<id>.json         준비한 범위의 메타데이터
├── context/<memory-id>.json         기존 기억 원본
└── works/<work-id>/checkpoint.json  기존 진행 상태 원본
```

사용자가 조회나 수정을 요청하면 관련 원본과 정리 결과를 확인한다. 의미의 정정은 evidence correct, 표현의 정리는 tidy로 구분한다. 삭제에는 다음 명령을 사용한다.

| 삭제 대상                   | 명령과 리비전 기준                                                                                            |
| --------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `remember` 원본이 있는 기억 | `forget --id <id> --revision <n>`. `read`로 확인한 원본의 현재 리비전을 사용하며 모든 원본 리비전을 제거한다. |
| tidy에서만 만든 기억        | `forget --id <id> --revision <n>`. `recall`의 리비전을 사용하며 정리 이력에서 제거한다.                       |
| `record` 원본               | `forget --ref note:<work>@<number>`                                                                           |

원본을 삭제하면 그 원본을 `sources`·`evidence`의 근거로 삼는 정리 결과도 모든 정리 이력에서 제거한다. 삭제된 입력의 재시도나 오래된 `snapshot`으로 내용을 복원하지 못하게 한다. `supersedes`로만 연결된 기억은 현재 근거가 남아 있으므로 연결만 제거하고 기억은 유지한다.

기억의 경험을 패턴과 현재 필요한 구체 기억에 수용할 때는 [tidy의 수용 계약](../../tidy/references/consolidation.md#경험을-다른-기억에-수용한다)을 사용한다. 수용된 현재 본문을 제거하는 `absorb`와 원본 및 그 근거에 의존하는 내용을 지우는 `forget`은 서로 다른 동작이다.

remember·기존 checkpoint 호출과 데이터도 지원한다. 두 명령을 직접 다룰 때는 [이전 계약](context-legacy.md)을 읽는다. location·recall·discover·context prepare·evidence read/check/result·search·read·graph·tidy status/result·work show/result는 조회만으로 저장 디렉터리를 만들지 않는다. 같은 프로젝트를 다루는 작업자는 work 원본과 새 업무 계약을 지원하는 CLI를 사용한다.
