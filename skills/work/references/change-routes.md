# 변경 경로

선택한 작업의 절을 적용한다. 이미 확보한 근거는 재사용한다. 생략하는 확인이 있다면 그 이유와 대체 근거를 남긴다. 실제 사용 경로와 완료 조건은 [verify](../../verify/SKILL.md)에서 확인한다.

## 결함 복구

1. 사용자가 겪는 조건에서 직접 재현한다. 재현이 어렵다면 입력과 환경을 좁히거나 관찰 수단을 보강한다. 재현하지 못했음을 결함이 없다는 증거로 쓰지 않는다.
2. 가능한 원인을 세우고 관찰로 배제한다. 코드의 실행 경로와 필요한 이력을 조사하고, 상태를 알 수 없으면 실행 중인 값을 확인한다. 수정 전에 살아남은 원인이 증상을 만드는 과정을 확인한다.
3. 확인한 원인을 바꾸는 최소 변경을 만든다. 책임·계약이 달라지면 먼저 설계한다. 로컬에서 저렴하게 실패를 고정할 수 있으면 수정 전에 실패하는 검사를 만든다. 큰 하네스나 불안정한 모의 객체가 필요하다면 실제 재현 명령을 근거로 사용한다.
4. 같은 재현 조건에서 실패가 사라졌는지 확인하고 영향을 받는 기존 동작도 검사한다. 실패 전후의 증거, 원인과 수정의 관계를 전달한다.

## 새 동작

1. 새로 얻을 결과와 유지할 계약을 정한다. 현재 진입점, 호출자와 관련 상태를 조사한다.
2. 사용자와 호출자의 사용 예를 먼저 만든다. 상태·규칙이 늘어난다면 이를 담을 데이터 형태를 정한다. 중요한 책임·계약 선택은 [architect](../../architect/SKILL.md)로 구체화한다.
3. 새 결과를 확인할 방법을 정하고, 검증 가능한 첫 단위부터 구현한다. 각 단위의 결과가 후속 구현의 전제가 되는지 확인한다.
4. 새 사용 경로와 보존할 동작을 실행한다. 저장·오류·재시도처럼 변경과 관련된 경로를 포함하고, 최종 diff를 정리한 뒤 다시 확인한다.

## 동작 보존형 재구성

1. 구조를 바꾸기 전에 보존할 동작을 실행 가능한 기준으로 고정한다. 기존 검사, 기록한 입출력, 특성 테스트 또는 동등성 비교를 사용한다. 타입 검사와 린트만으로 동작을 고정했다고 말하지 않는다.
2. 목표 책임·데이터 형태·호출 관계를 정한다. 어떤 분기, 중복 규칙, 불가능한 상태 또는 읽는 부담이 줄어드는지 설명한다. 이미 명확한 구조에 간접 계층을 추가하지 않는다.
3. 구 경로를 정리하고 작은 단위로 옮긴다. 각 단위가 기준을 유지하는지 확인한다. 내부 API를 바꾸면 호출자 이전과 구 API 삭제를 함께 처리한다.
4. 같은 입력과 실제 경로에서 전후 결과를 비교한다. 새 기능이나 별개의 버그가 드러나면 재구성의 범위와 구분한다. 이를 고치려고 동작 보존 조건을 조용히 바꾸지 않는다.

## 성능 개선

1. 입력·환경·측정 방법과 기준값을 확보한다. 체감만으로 병목을 정하지 않는다.
2. 프로파일이나 실행 중 관찰로 비용이 발생하는 곳을 찾는다. 결과를 바꿀 수 있는 가설 하나를 선택하고 그 가설을 확인할 지표를 정한다.
3. 측정한 원인을 바꾸고 같은 조건에서 전후를 비교한다. 결과를 개선하지 못한 실험 변경은 제거한다. 비교 조건이 다르면 비율로 개선을 주장하지 않는다.
4. 목표 지표와 기존 동작을 함께 확인한다. 효과, 받아들인 비용과 측정의 한계를 전달한다.
