# 변경 경로

요청에 맞는 절을 적용한다. 검증 수단의 준비와 실행은 [verify](../../verify/SKILL.md)를 따른다. 이미 확보한 유효한 근거는 재사용하고, 필요한 확인을 생략한다면 이유와 대체 근거를 남긴다.

## 결함 복구

1. 사용자가 겪는 조건에서 직접 재현한다. 재현이 어렵다면 입력과 환경을 좁히거나 관찰 수단을 보강한다. 재현하지 못했음을 결함이 없다는 증거로 쓰지 않는다.
2. 코드의 실행 경로, 상태와 필요한 이력으로 원인 가설을 좁힌다. 증상이 발생한 지점에서 입력과 상태의 출처를 따라가며 어떤 책임이나 계약이 깨졌는지 확인한다. 수정 전에 현재 구조가 그 실패를 허용하는 과정을 설명할 수 있어야 한다.
3. 책임이나 계약을 바꿔야 한다면 [architect](../../architect/SKILL.md)로 변경 범위를 먼저 정한다. 코드의 결함은 원래 조건에서 실패하는 테스트로 재현한 뒤 원인을 고치는 최소 변경으로 수정한다. 증상을 피하는 별도 경로를 덧붙여 원인을 남기지 않는다.
4. 같은 재현 조건에서 실패가 사라졌는지 확인하고 영향을 받는 기존 동작도 검사한다. 실패 전후의 증거, 원인과 수정의 관계를 전달한다.

## 새 동작

1. 새로 얻을 결과와 유지할 계약을 정한다. 현재 진입점, 호출자와 관련 상태를 조사한다.
2. 사용자와 호출자의 사용 예에서 필요한 규칙과 상태를 찾고, 기존 모델로 표현한다. 책임 배치나 외부 계약이 달라지면 [architect](../../architect/SKILL.md)로 변경할 경계와 입출력을 구체화한다.
3. 새 결과를 검증하는 테스트의 실패를 확인한 뒤 첫 사용 경로부터 구현한다. 각 단위의 결과가 후속 구현의 입력 조건을 충족하는지 확인하고, 아직 쓰이지 않는 확장은 추가하지 않는다.
4. 새 사용 경로와 보존할 동작을 실행한다. 저장, 오류 처리와 재시도처럼 변경과 관련된 경로를 포함하고, 최종 diff를 정리한 뒤 다시 확인한다.

## 동작 보존형 재구성

1. 구조를 바꾸기 전에 보존할 동작을 실행 가능한 기준으로 고정한다. 기존 검사, 기록한 입출력, 특성 테스트 또는 동등성 비교를 사용한다. 타입 검사와 린트만으로 동작을 고정했다고 말하지 않는다.
2. 줄일 중복과 분기, 막을 잘못된 상태 또는 이해하기 쉬워질 부분을 정하고, 이를 위한 책임 배치와 데이터 형태, 호출 관계를 구체화한다. 평행 상속 구조처럼 함께 바뀌는 코드에 숨은 중복도 확인한다. 이미 명확한 구조에 간접 계층을 추가하지 않는다.
3. 구 경로를 정리하고 작은 단위로 옮긴다. 각 단위가 기준을 유지하는지 확인한다. 내부 API를 바꾸면 호출자 이전과 구 API 삭제를 함께 처리한다.
4. 같은 입력과 실제 경로에서 전후 결과를 비교한다. 새 기능이나 별개의 버그가 드러나면 재구성의 범위와 구분한다. 이를 고치려고 동작 보존 조건을 조용히 바꾸지 않는다.

## 성능 개선

1. 실제로 문제가 된 사용 조건과 성능 지표를 확인한 뒤 입력, 환경과 측정 방법을 정해 기준값을 확보한다. 아직 발생하지 않은 비용을 예상해 최적화하거나 체감만으로 병목을 정하지 않는다.
2. 프로파일이나 실행 중 관찰로 비용이 발생하는 곳을 찾는다. 결과를 바꿀 수 있는 가설 하나를 선택하고 그 가설을 확인할 지표를 정한다.
3. 측정한 원인을 바꾸고 같은 조건에서 전후를 비교한다. 결과를 개선하지 못한 실험 변경은 제거한다. 비교 조건이 다르면 비율로 개선을 주장하지 않는다.
4. 목표 지표와 기존 동작을 함께 확인한다. 효과, 받아들인 비용과 측정의 한계를 전달한다.
