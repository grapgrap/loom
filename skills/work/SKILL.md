# Work

사용자 요청과 프로젝트 지침에 따라 맡은 결과를 완수한다. 구현을 요청받았다면 조사나 설계의 완료에서 멈추지 않는다. 설명과 문서 작성에는 [write](../write/SKILL.md)를 적용한다.

## 목표와 범위를 확인한다

현재 대화, 프로젝트 지침과 실제 산출물에서 사용자가 얻으려는 결과를 파악한다. 사용자가 제안한 방법이 그 결과를 만드는지, 요청의 전제가 실제 상태와 맞는지 확인한다. 전제가 다르면 근거와 대안을 설명하고 사용자와 함께 목적, 진행 여부와 접근 방법을 판단한다.

이번 범위에서 유지할 동작, 완료 조건과 전달 지점을 정해 대화에서 공유한다. 이미 합의한 목표와 권한은 다시 묻지 않는다. 대화만으로 이어가기 어려운 장기 작업에만 [계획 템플릿](../../templates/execution-plan.md)을 사용한다. 위임받은 작업자는 먼저 [위임 수행 지침](references/delegated-work.md)을 읽는다.

## 필요한 조사와 설계를 선택한다

현재 동작과 책임을 알아야 하면 [understand](../understand/SKILL.md)를 사용한다. 질문이나 접근 방법이 불명확하면 [explore](../explore/SKILL.md)로 조사할 질문과 적용 조건을 구체화한다. 탐색 대상이 정해지지 않았다면 현재 시스템 조사 없이 시작할 수 있다. 두 과정이 모두 필요하면 이미 확인한 근거를 재사용하며 남은 쟁점을 조사한다. 접근 방법과 적용 조건이 충분히 알려져 있다면 별도 탐색은 생략한다.

모델의 경계, 책임 배치나 외부 계약을 바꾸거나 중요한 제품 선택이 필요하면 [architect](../architect/SKILL.md)로 설계한다. 컴포넌트의 책임과 입출력 계약, 전환 순서와 검증 조건을 구체화한다. 기존 패턴을 조금 확장하는 작업은 필요한 변경 내용만 설명한다.

복잡한 작업은 조사 초기에 현재 이해, 잠정 방향과 남은 쟁점을 공유한다. 접근 방법은 목적을 충족하고 유지할 계약을 지키는지로 비교한다. 구현하기 쉽다는 이유로 일관성을 깨거나 정보를 이중으로 관리하거나 원천의 한계를 우회하는 방식을 택하지 않는다. 실행 전에는 선택 이유와 검증 단위를 설명하고, 중요한 확인을 생략했다면 이유를 밝힌다.

조사 결과로 문제를 다시 정의하거나 판단을 유보해야 한다면 목표와 제약에 미치는 영향을 설명하고 다음 행동을 정한다. 조사만 맡았다면 결과를 전달하고, 설계나 구현도 맡았다면 그 단계까지 이어간다.

관찰로 풀 수 있는 쟁점은 조사나 작은 실험으로 확인한다. 도메인의 의미, 제품 정책, 사용자 경험이나 외부 계약에 관해 사람의 선택이 남아 있으면 그 선택에 의존하는 구현을 기다린다. 사용자가 구현 전 확인을 요청한 경우에도 기다린다. 그 밖의 내부 선택은 설계를 공유한 뒤 진행한다. 새 근거가 합의한 목적이나 경계를 바꾸면 영향을 먼저 알리고 관련 설계와 조건을 갱신한다. 장기 방향에 대한 동의를 이번 범위의 확대로 해석하지 않는다.

## 변경하고 검증한다

관찰 가능한 결과를 작업 단위로 삼고 [변경 경로](references/change-routes.md)에서 요청에 맞는 절을 적용한다. 첫 변경 전에 [verify](../verify/SKILL.md)로 기대한 실패나 변경 전 기준을 확보한다. 여러 책임을 거치는 사용 경로를 포함하고, 같은 검증 수단으로 구현 중과 완료 후의 결과를 확인한다.

코드를 구현할 때는 검증되지 않은 외부 입력을 경계에서 검증해 타입으로 정의한 계약을 만족하는 값으로 변환한다. 내부에서는 그 계약을 신뢰하고 런타임에 다시 검증하지 않는다. 정한 실패 처리만 구현하며, 폴백이나 `try/catch`를 임의로 추가해 발생하지 않아야 할 오류를 숨기지 않는다.

동시성 문제를 다룰 때는 요청이 겹치는 경로와 상태 변화를 확인하고 멱등 처리로 해결한다. 같은 요청이 반복되거나 동시에 도착해도 상태 변경이나 외부 효과가 중복되지 않는지 검증한다. lock을 도입하려면 적용 이유와 영향을 설명하고 사용자 허락을 받는다.

검증을 통과한 단위는 동작을 유지하며 중복된 규칙과 불필요한 문법 요소, 클래스와 메서드를 줄인다. 구조만으로 드러나지 않는 중요한 의도와 제약은 코드 가까이에 설명하고, 정리한 뒤 같은 결과가 유지되는지 확인한다.

각 단위의 관찰과 근거를 완료 조건에 연결한다. 범위나 완료 조건이 바뀌면 변경 내용을 공유하고 영향을 받는 검증을 다시 확인한다. 검증이 실패하면 구현, 전제와 관찰 방법 중 원인을 찾아 수정한다. 새 근거로 잘못됐음이 확인된 자신의 변경은 되돌리고, 사용자나 다른 작업자의 변경은 보존한다.

## 남은 일과 완료 여부를 판단한다

작업을 전환할 때, 짧은 요청에 답한 뒤, 최종 응답 전에는 전체 목표와 남은 완료 조건을 확인한다. 새 메시지가 보완, 순서 변경, 별도 요청, 보류 또는 취소인지 구분한다. 상태 질문에는 짧게 답한 뒤 실행 가능한 원래 작업을 계속한다. 보류와 취소는 사용자 지시를 따르며, 다른 대화의 작업을 자동으로 재개하지 않는다.

결과를 전달하기 전에 자신의 diff를 읽고 보존할 계약, 무관한 변경과 실험 잔여물을 확인한다. 최종 검증에는 `verify`를 적용한다. 사용자가 검토를 요청했거나 변경이 위험하거나 논쟁적이면 [review](../review/SKILL.md)로 점검한다. 맡은 범위의 결함을 수정하고 영향을 받는 검사만 다시 실행한다.

단독 수행자는 전체 완료 조건을 충족하고 다음 행동이 없을 때 완료를 보고한다. 위임받은 작업자는 결과를 반환하고, 조율자가 실제 산출물과 근거를 검토해 수락한다. 완료 조건에 실패나 미확인이 남으면 완료로 보고하지 않고 영향과 재개 조건을 전달한다. 최종 보고에는 결과, 검증 근거와 중요한 한계를 연결한다.

커밋, 푸시, PR과 병합은 맡은 권한 안에서 수행한다. 되돌리기 어려운 외부 작업은 기존 승인 범위를 확인한다. 서브 에이전트는 사용자가 명시적으로 위임을 요청한 경우에만 사용하며, 모델이 지정되지 않았다면 먼저 확인한다.

## 문서를 선별한다

현재 상태와 변경안은 기본적으로 대화에서 설명한다. 이후에도 참조할 사용법, 외부 계약이나 검증 절차만 문서로 남기고, 어떤 변화가 생기면 갱신할지 정한다. PR, 커밋과 기존 `.loom/` 기록은 당시의 이력이며 현재 설계로 자동 채택하지 않는다.
