# Work

사용자 요청과 프로젝트 지침을 기준으로 맡긴 결과를 완수한다. 책임과 계약을 판단할 때 [원칙](../../references/principles.md), 코드를 설계하거나 변경할 때 [코드 규칙](../../references/rules.md)의 관련 본문을 적용한다. 설명과 문서에는 [write](../write/SKILL.md)를 사용한다.

## 범위와 경로를 정한다

1. 사용자가 얻을 결과, 유지할 동작, 이번 범위와 완료 조건, 맡긴 전달 지점을 확인한다. 구현 요청의 완료를 조사나 문서 작성으로 대체하지 않는다. 이미 정한 목표와 권한은 재사용한다.
2. [작업 맥락](references/context.md)으로 현재 업무와 필요한 근거를 확인한다. 다른 에이전트에게 위임받았다면 먼저 [위임 수행 지침](references/delegated-work.md)을 읽는다. 작업자는 CLI를 읽기 전용으로 사용하고 아래 저장 절차는 조율자가 수행한다.
3. [understand](../understand/SKILL.md)로 현재 동작과 책임을 확인하고 [변경 경로](references/change-routes.md)에서 필요한 절을 고른다. 설명과 진단은 읽기와 보고, 결함은 재현과 원인 복구, 새 동작은 계약 구현, 재구성은 동작 보존, 성능은 같은 조건의 전후 비교로 확인한다.

복잡한 요청은 조사 초기에 현재 이해, 근거에 따른 잠정 방향과 쟁점을 공유한다. 실행 전에는 선택한 경로와 검증 단위, 중요한 생략 이유를 밝힌다. [업무 CLI](references/context-work.md)에 목표와 범위, 완료 조건을 정의한다. 짧은 질문은 별도 업무가 필요하지 않으며, 대화와 CLI로 부족한 장기 실행에만 [계획 템플릿](../../templates/execution-plan.md)을 쓴다.

## 설계와 구현을 연결한다

모델 경계, 책임 배치나 외부 계약을 바꾸거나 중요한 제품 선택이 있으면 [architect](../architect/SKILL.md)를 적용한다. 전략 설계로 나눈 컴포넌트의 책임과 경계를 바탕으로 입출력 계약, 전환 순서와 검증 조건을 받는다. 기존 패턴의 작은 확장은 필요한 변경 그림만 설명한다. 작업 단위는 관찰 가능한 결과로 정하고 여러 책임을 통과하는 첫 사용 경로와 통합 검증을 포함한다.

관찰로 풀 쟁점은 조사나 작은 실험으로 확인한다. 도메인의 의미, 제품 정책, 사용자 경험이나 외부 계약에 관해 사람의 선택이 남거나 구현 전 확인을 요청받았다면 그 선택에 의존하는 구현을 기다린다. 그 밖에는 설계를 공유하고 진행한다. 새 근거가 합의한 목적이나 경계를 바꾸면 차이와 영향을 먼저 공유하고 관련 설계와 조건만 갱신한다. 내부 선택을 반복 승인받거나 장기 방향에 대한 동의를 범위 확대로 해석하지 않는다.

첫 변경 전에 [verify](../verify/SKILL.md)로 실패나 기준값을 확인할 수단을 준비하고 구현 중과 완료 후 재사용한다. 각 단위의 결과를 work report에 조건별 관찰과 근거로 연결한다. 범위나 완료 조건을 바꾸면 owner가 revise하고 영향받는 검증을 다시 확인한다. 검증 실패는 구현, 전제와 관찰 방법 중 원인을 찾아 복구하며 자신이 추가한 반증된 변경을 걷어낸다. 사용자가 직접 수정한 내용과 다른 작업에서 만든 변경은 보존한다.

## 중단과 완료를 판단한다

작업 전환, 짧은 요청 뒤와 최종 응답 전에는 [재개 규약](references/context.md#미완료-업무를-확인하고-재개한다)으로 맡긴 전체 업무의 남은 조건을 확인한다. 새 메시지는 보완, 순서 변경, 별도 요청, 보류와 취소를 구분한다. 상태 질문에는 짧게 답하고 실행 가능한 원래 업무를 계속한다.

전달 전 자신의 diff를 읽고 적용한 원칙과 보존할 계약, 무관한 변경 및 실험 잔여물을 확인한다. 최종 검증은 `verify`, 위험하거나 논쟁적인 변경과 요청받은 검토는 [review](../review/SKILL.md)를 적용한다. 확인한 범위 내 결함을 고치고 영향받는 검사만 다시 수행한다.

단독 수행자는 필수 하위 업무와 전체 완료 조건을 충족하고 남은 행동이 없을 때 `work complete`를 실행한다. 작업자는 결과를 호스트로 반환하고 조율자가 제출과 수락을 기록한다. 실패나 미확인이 남으면 완료로 표시하지 않고 영향과 재개 조건을 전달한다. 최종 보고에는 바뀐 결과와 실제 증거, 중요한 한계를 연결한다. 원칙의 이름은 선택에 영향을 준 경우에 밝힌다.

맡긴 전달 지점까지 수행하며 커밋, 푸시, PR과 병합 권한을 임의로 확대하지 않는다. 되돌리기 어려운 외부 작업은 기존 권한 범위를 확인한다. 서브 에이전트는 명시적 위임 요청이 있을 때만 사용하고, 요청에 모델 선택이 없으면 먼저 확인한다.

## 기록과 문서의 수명을 정한다

업무 상태는 work, 재사용할 판단과 실제 출처는 evidence, 원본에 근거한 파생 표현은 tidy에 둔다. 시점과 적용 조건은 [작업 맥락](references/context.md)을 따른다. 작업 경계와 마무리에는 [tidy](../tidy/SKILL.md)로 필요한 범위를 정리하며 정리 완료와 업무 완료를 구분한다.

기록 입력은 CLI stdin으로 전달한다. 저장용 입력 파일이나 기억 파일을 직접 편집하거나 사용자에게 관리하도록 요구하지 않는다. 현재와 변경 후 그림은 기본적으로 대화에 둔다. 반복 사용될 사용법, 외부 계약이나 검증 절차만 갱신 근거와 함께 살아 있는 문서로 만든다. PR, 커밋과 기존 `.loom/` 기록은 당시의 역사이며 현재 설계도로 자동 승격하지 않는다.
