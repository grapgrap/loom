# Work

사용자 요청과 프로젝트 지침에 따라 맡은 결과를 완수한다. 구현을 요청받았다면 조사나 설계의 완료에서 멈추지 않는다. 설명과 문서 작성에는 [write](../write/SKILL.md)를 적용한다.

## 목표와 범위를 확인한다

사용자가 얻을 결과, 유지할 동작, 이번 범위와 완료 조건을 확인한다. 어디까지 수행해 누구에게 전달할지도 정한다. 이미 합의한 목표와 권한은 다시 묻지 않는다.

[작업 맥락](references/context.md)에서 현재 업무와 근거를 확인한다. 위임받은 작업자는 먼저 [위임 수행 지침](references/delegated-work.md)을 읽는다. 작업자는 CLI를 읽기 전용으로 사용하고 결과를 조율자에게 보고한다. 기록 저장은 단독 수행자나 조율자가 맡는다.

독립 업무의 목표, 범위와 완료 조건은 [업무 CLI](references/context-work.md)에 정의한다. 짧은 질문에는 별도 업무를 만들지 않는다. 대화와 CLI만으로 이어가기 어려운 장기 작업에만 [계획 템플릿](../../templates/execution-plan.md)을 사용한다.

## 필요한 조사와 설계를 선택한다

현재 동작과 책임을 알아야 하면 [understand](../understand/SKILL.md)를 사용한다. 질문이나 접근 방법이 불명확하면 [explore](../explore/SKILL.md)로 조사할 질문과 적용 조건을 구체화한다. 탐색 대상이 정해지지 않았다면 현재 시스템 조사 없이 시작할 수 있다. 두 과정이 모두 필요하면 이미 확인한 근거를 재사용하며 남은 쟁점을 조사한다. 접근 방법과 적용 조건이 충분히 알려져 있다면 별도 탐색은 생략한다.

모델의 경계, 책임 배치나 외부 계약을 바꾸거나 중요한 제품 선택이 필요하면 [architect](../architect/SKILL.md)로 설계한다. 컴포넌트의 책임과 입출력 계약, 전환 순서와 검증 조건을 구체화한다. 기존 패턴을 조금 확장하는 작업은 필요한 변경 내용만 설명한다.

복잡한 작업은 조사 초기에 현재 이해, 잠정 방향과 남은 쟁점을 공유한다. 실행 전에는 선택한 접근과 검증 단위를 설명하고, 중요한 확인을 생략했다면 이유를 밝힌다. 탐색에서 문제를 다시 정의하거나 판단을 유보했다면 목표와 제약에 미치는 영향을 확인해 다음 행동을 정한다. 탐색만 맡았다면 결과를 전달하고, 설계나 구현도 맡았다면 그 단계까지 이어간다.

관찰로 풀 수 있는 쟁점은 조사나 작은 실험으로 확인한다. 도메인의 의미, 제품 정책, 사용자 경험이나 외부 계약에 관해 사람의 선택이 남아 있으면 그 선택에 의존하는 구현을 기다린다. 사용자가 구현 전 확인을 요청한 경우에도 기다린다. 그 밖의 내부 선택은 설계를 공유한 뒤 진행한다. 새 근거가 합의한 목적이나 경계를 바꾸면 영향을 먼저 알리고 관련 설계와 조건을 갱신한다. 장기 방향에 대한 동의를 이번 범위의 확대로 해석하지 않는다.

## 변경하고 검증한다

[변경 경로](references/change-routes.md)에서 맡은 작업에 해당하는 절을 적용한다. 설명과 진단은 조사 결과를 보고하고, 결함은 재현한 원인을 복구한다. 새 동작은 정한 계약을 구현하고, 재구성은 기존 동작을 보존하며, 성능 개선은 같은 조건에서 전후를 비교한다.

첫 변경 전에 [verify](../verify/SKILL.md)로 실패나 기준값을 확인할 수단을 준비한다. 관찰 가능한 결과를 작업 단위로 삼고, 여러 책임을 통과하는 첫 사용 경로와 통합 검증을 포함한다. 준비한 검증 수단은 구현 중과 완료 후에도 재사용한다.

각 단위의 관찰과 근거를 `work report`의 완료 조건에 연결한다. 범위나 완료 조건이 바뀌면 업무 소유자(owner)가 `work revise`로 반영하고 영향을 받는 검증을 다시 확인한다. 검증이 실패하면 구현, 전제와 관찰 방법 중 원인을 찾아 수정한다. 자신이 추가했으나 근거가 반박된 변경은 되돌리고, 사용자나 다른 작업자의 변경은 보존한다.

## 남은 일과 완료 여부를 판단한다

작업을 전환할 때, 짧은 요청에 답한 뒤, 최종 응답 전에는 [재개 규약](references/context.md#미완료-업무를-확인하고-재개한다)에 따라 전체 업무의 남은 조건을 확인한다. 새 메시지가 보완, 순서 변경, 별도 요청, 보류 또는 취소인지 구분한다. 상태 질문에는 짧게 답한 뒤 실행 가능한 원래 업무를 계속한다.

결과를 전달하기 전에 자신의 diff를 읽고 보존할 계약, 무관한 변경과 실험 잔여물을 확인한다. 최종 검증에는 `verify`를 적용한다. 사용자가 검토를 요청했거나 변경이 위험하거나 논쟁적이면 [review](../review/SKILL.md)로 점검한다. 맡은 범위의 결함을 수정하고 영향을 받는 검사만 다시 실행한다.

단독 수행자는 필수 하위 업무와 전체 완료 조건을 충족하고 다음 행동이 없을 때 `work complete`를 실행한다. 위임받은 작업자는 결과를 반환하고, 조율자가 제출과 수락을 기록한다. 실패나 미확인 사항이 남으면 완료로 표시하지 않고 영향과 재개 조건을 전달한다. 최종 보고에는 결과, 실제 증거와 중요한 한계를 연결한다.

커밋, 푸시, PR과 병합은 맡은 권한 안에서 수행한다. 되돌리기 어려운 외부 작업은 기존 승인 범위를 확인한다. 서브 에이전트는 사용자가 명시적으로 위임을 요청한 경우에만 사용하며, 모델이 지정되지 않았다면 먼저 확인한다.

## 기록을 남기고 정리한다

업무 상태는 work, 재사용할 판단과 출처는 evidence, 원본에서 정리한 재개 맥락은 tidy에 둔다. 시점과 적용 조건은 [작업 맥락](references/context.md)을 따른다. 작업 경계와 마무리에 [tidy](../tidy/SKILL.md)로 필요한 범위를 정리하고, 맥락 정리와 업무 완료를 구분한다.

기록 입력은 CLI의 stdin으로 전달한다. 저장용 입력 파일이나 기억 파일을 직접 편집하거나 사용자에게 관리하도록 요구하지 않는다. 현재 상태와 변경안은 기본적으로 대화에서 설명한다. 반복 사용할 사용법, 외부 계약이나 검증 절차만 갱신할 근거와 함께 문서로 남긴다. PR, 커밋과 기존 `.loom/` 기록은 당시의 이력이며 현재 설계로 자동 채택하지 않는다.
