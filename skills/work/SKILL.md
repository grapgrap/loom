# Work

## 이번에 어디까지 맡았는가

사용자가 이루려는 일을 한 장면으로 잡는다. 누가 어떤 조건에서 행동하고 어떤 차이를 확인하려는가? 질문이면 이해에 필요한 설명이, 설계면 사용자가 읽고 고칠 수 있는 제안이, 변경이면 실제 경로에서 확인한 동작이 결과다. 사용자가 지정한 책임 경계나 구현 방식과 기존 호출자에게 지킬 약속도 완료 조건에 넣는다.

사용자가 선택한 것, 아직 열어 둔 것, 에이전트에게 맡긴 것을 구별한다. 요청과 프로젝트에서 판단할 수 있는 일은 진행한다. 선택에 따라 제품 동작이나 사용자가 정한 경계가 달라지면 차이가 드러나는 예를 보여준다. 결정에 의존하지 않는 작업은 이어간다.

## 지금 필요한 일을 고른다

- 기존 동작과 책임을 읽는 일은 `$loom:understand`, 증상을 재현하거나 원인을 가리는 일은 `$loom:diagnose`로 진행한다.
- 외부 사례가 판단을 바꿀 때는 `$loom:explorer`, 어떤 역할과 상태 전이를 허용할지 정하거나 설계 모델을 검증할 때는 `$loom:architect`를 쓴다.
- 합의한 장면을 테스트와 코드로 옮기는 일은 `$loom:implement`, 합의와 테스트 또는 구현을 대조하는 일은 `$loom:review`로 진행한다. 독자가 판단할 문서나 PR 본문은 `$loom:write`가 다듬는다.

## 세션을 넘길 때와 작업을 마칠 때

다른 에이전트가 이전 대화 없이 프로젝트만 열었을 때 남은 작업을 이어갈 수 있는지 본다. 미완료라면 코드에서 읽히지 않는 결정과 이유, 현재 구현과의 차이, 다음에 확인할 장면을 관련 프로젝트 문서에 남긴다. 적당한 곳이 없으면 작업 가까이에 짧게 적는다. 새 세션은 현재 요청을 기준으로 그 기록을 코드와 테스트에 대조해 남은 곳부터 진행한다.

완료한 동작과 역할의 기준은 현재 코드다. 대표 장면을 실제로 실행하고 상태를 바꾼 역할을 따라가, 테스트로 어떤 약속을 다시 확인할 수 있는지 보여준다. 사용자가 직접 판단하기로 한 프로토타입은 같은 장면을 경험할 시작 방법을 건넨다. 관찰과 기대가 갈리면 구현을 고치고, 기대 자체가 바뀌면 설계로 돌아간다.

설계 합의서는 사용자가 확인한 버전의 TypeScript 도메인 모델과 TLA+ 흐름 모델, 검증 설정과 함께 다시 열 수 있게 보존한다. 구현과 테스트에서 복원할 수 있는 인계용 메모와 실험 초안은 정리한다. 이후 선택에 필요한 배경은 해당 결정의 PR이나 기존 문서에서 찾을 수 있게 한다. 결과를 보고할 때에는 확인한 조건·결과와 판단에 영향을 주는 미확인 사항을 밝힌다.
