# Work

맡긴 범위에서 근거 있게 판단하고 결과를 확인할 수 있게 한다. 프로젝트 지침과 사용자의 요청을 먼저 적용하고, [원칙](../../references/principles.md)의 적용 상황에서 현재 작업에 필요한 항목을 고른다.

## 작업을 판단한다

복잡한 요청에서는 조사 초기에 현재 이해한 문제, 확인한 근거에 따른 잠정 방향과 남은 쟁점을 짧게 공유한다. 추정은 추정으로 표시하고, 조사가 길어지거나 설계가 완성될 때까지 최초 설명을 미루지 않는다.

1. 누가 얻을 결과, 유지할 동작, 변경 범위와 관찰 가능한 완료 조건을 확인한다. 로컬 변경, 커밋, PR 등 맡긴 전달 지점도 구분한다. 이미 정해진 목표나 권한을 반복 확인하지 않는다.
2. 영향을 받는 도메인의 목적·용어·책임·제약과 현재 동작을 [understand](../understand/SKILL.md)의 방식으로 조사한다. 이미 확보한 근거는 재사용하고 부족한 부분만 확인한다.
3. 아래에서 경로를 선택한다. 변경 작업은 [변경 경로](references/change-routes.md)의 해당 절을 적용한다. 복합 작업은 결과별로 경로를 조합하고 선행 결과가 필요한 순서로 진행한다.

| 원하는 결과 | 먼저 확인할 것 | 구현과 완료 증거 |
| --- | --- | --- |
| 현재 상태의 이해·진단 | 코드와 실제 동작, 필요한 경우 이력 | 읽기 전용으로 설명하고 멈춘다. |
| 결함 복구 | 사용자가 겪는 현상의 재현과 원인 | 원인을 고치는 최소 변경 후 같은 조건에서 재현이 사라졌는지 확인한다. |
| 새 동작 | 사용자의 결과, 기존 계약, 바뀌는 책임 | 필요한 설계 후 구현한다. 새 동작과 유지할 동작을 실제 사용 경로에서 확인한다. |
| 동작 보존형 재구성 | 변경 전 관찰 가능한 동작 | 구조를 바꾸고 동등한 결과를 확인한다. |
| 성능 개선 | 재현 가능한 기준값과 병목 | 측정한 원인을 바꾸고 같은 조건에서 전후를 비교한다. |

복잡한 작업에서는 선택한 경로, 검증할 단위와 중요한 생략 이유를 실행 전에 짧게 공유한다. 각 단위의 결과와 증거를 작업 목록에서 연결한다. 대화나 기존 작업 도구로 관리할 수 없을 만큼 길거나 여러 세션에 걸치면 [실행 계획 템플릿](../../templates/execution-plan.md)을 사용한다. 작은 작업에 계획 파일을 만들 필요는 없다.

## 설계와 인간의 결정을 구분한다

책임의 배치나 외부 계약을 다시 정해야 하거나, 사용자 경험에 중요한 선택 또는 되돌리기 비싼 구조 선택이 있으면 [architect](../architect/SKILL.md)를 적용한다. 이미 정해진 패턴을 따르는 작은 확장은 `work`에서 변경 그림만 짧게 설명하고 진행할 수 있다.

- 관찰이나 실험으로 풀 수 있는 갈림길은 조사하거나 작은 시제품으로 확인한다.
- 목표와 판단 기준이 정해져 있다면 현재 그림과 변경 그림을 공유하고 진행한다. 공유는 승인 요청이 아니다.
- 도메인 의미, 제품 정책, 사용자 경험 또는 외부 계약에 관해 사람의 선택이 남아 있으면 대안과 영향을 제시하고 해당 선택에 의존하는 구현을 멈춘다.
- 사용자가 구현 전 확인을 요청했다면 멈춘다. 되돌리기 어려운 외부 작업도 실행 전에 확인한다.

새로 확인한 사실이나 사용자 피드백이 합의한 결과·책임 또는 설계 전제를 바꾸면, 이전 그림에서 달라진 부분과 다음 판단에 미치는 영향을 먼저 공유한다. 영향받는 부분만 다시 조사·설계하고 구현·검증에 반영한다. 세부 구현의 조정만으로 이미 확인한 방향을 반복 승인받지 않는다. 완료 조건을 만족시키기 위해 목표나 검증 기준을 임의로 완화하지 않는다.

## 구현하고 증명한다

선택한 설계를 검증 가능한 단위로 구현한다. 각 단위가 끝나면 실제 결과를 확인하고 다음 단위로 간다. 반복 변경이나 복잡한 비교를 사람이 다시 확인하기 어렵다면 기존 도구를 먼저 찾고, 필요한 최소 스크립트를 만든다.

검증이 실패하면 구현, 판단의 전제, 관찰 방법 중 무엇이 잘못됐는지 조사한다. 증거가 반박한 가설 때문에 자신이 추가한 변경은 걷어낸다. 사용자나 다른 작업의 변경은 보존한다. 범위 안의 문제는 수정하고 영향받는 조건을 다시 검증한다.

전달 전에 자신의 diff를 읽고 정리한다.

- 근거 없는 가드, 중복 검증, 불필요한 추상화와 흐름을 다시 설명하는 주석을 제거한다. 필요한 경계와 코드로 드러나지 않는 이유는 보존한다.
- 새로 만들거나 바꾼 이름에는 [Domain Vocabulary](../../references/principles.md#domain-vocabulary)와 [Intention-Revealing Names](../../references/principles.md#intention-revealing-names)를 적용해 도메인 의미와 의도가 읽히는지 확인한다.
- 변경한 공통 코드에는 [Essential vs Accidental Duplication](../../references/principles.md#essential-vs-accidental-duplication)을 적용해 서로 다른 변경 이유를 묶지 않았는지 확인한다.
- 변경한 함수와 유사한 흐름에는 [Single Level of Abstraction](../../references/principles.md#single-level-of-abstraction)을 적용해 표현의 차이가 실제 책임이나 동작의 차이를 반영하는지 확인한다.
- 오류 처리나 실패 계약을 바꿨다면 [Error Boundary Placement](../../references/principles.md#error-boundary-placement)와 [Meaningful Errors](../../references/principles.md#meaningful-errors)로 처리 책임과 전달되는 실패 정보를 확인한다.
- 변경한 내부 인터페이스의 호출자를 옮기고 구 경로와 남은 참조를 정리한다. 외부 계약에는 필요한 마이그레이션 경로를 둔다.
- 임시 진단 코드와 실험 잔여물을 정리하고 무관한 변경이 섞이지 않았는지 확인한다.

최종 상태를 [verify](../verify/SKILL.md)로 확인한다. 위험한 변경, 논쟁적인 설계 또는 요청받은 검토에는 [review](../review/SKILL.md)를 적용한다. 새 지적을 검증하고 범위 안의 결함을 고친 뒤 영향받는 검사를 다시 실행한다.

맡긴 전달 지점까지 완료한다. 커밋이나 PR을 요청받았다면 검증 가능한 변경 단위와 증거가 전달 순서와 설명에서도 이어지게 한다. 작업 권한을 자동으로 커밋·푸시·PR·병합 권한으로 확대하지 않는다.

결과에는 달라진 동작, 유지된 조건, 중요한 판단과 실제 증거를 연결한다. 남은 실패·미확인은 분명히 알리고 완료로 표시하지 않는다. 원칙은 선택을 바꾼 경우에만 이름과 영향을 밝힌다. 진행할 수 없다면 확보한 결과, 막힌 조건과 재개에 필요한 사실을 전달한다.

## 기록의 수명을 정한다

현재·변경 그림은 기본적으로 이 작업의 대화에서 설명한다. PR이나 커밋 설명은 당시의 판단과 증거를 남기는 기록이지 영구히 갱신할 현재 설계도가 아니다. 이후 작업자가 반복해서 의존할 사용법·외부 계약·검증 절차에만 살아 있는 문서를 만든다. 그 문서를 만들 때 갱신할 근거와 방법도 정한다. `.loom/` 문서의 생성·갱신은 기본 절차가 아니다. 기존 문서는 현재 코드의 근거와 대조할 역사 자료로만 취급한다.

서브에이전트는 기본 경로에 넣지 않는다. 사용자나 프로젝트의 위임 정책을 따르고, 명시적 요청 없이 위임하지 않는다. 사용자가 위임을 요청했지만 모델을 정하지 않았다면 모델 선택을 먼저 요청한다.
