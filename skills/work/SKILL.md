# Work

한 에이전트가 맡긴 범위에서 근거 있게 판단하고 결과를 확인할 수 있게 한다. 프로젝트 지침과 사용자의 요청을 먼저 적용한다. [원칙](../../references/principles.md)의 공통 설명과 적용 절차를 확인하고, 현재 작업에서 내려야 할 판단에 적용한다.

코드를 설계·작성·변경할 때는 [코드 규칙](../../references/rules.md)의 적용 절차에 따라 관련 항목을 고르고 해당 본문을 읽어 적용한다. 설명·문서·커밋 메시지·PR 본문을 작성하거나 다듬을 때는 [write](../write/SKILL.md)를 적용한다.

## 작업을 판단한다

복잡한 요청에서는 조사 초기에 현재 이해한 문제, 확인한 근거에 따른 잠정 방향과 남은 쟁점을 짧게 공유한다. 추정은 추정으로 표시하고, 조사가 길어지거나 설계가 완성될 때까지 최초 설명을 미루지 않는다.

1. 누가 얻을 결과, 유지할 동작, 변경 범위와 관찰 가능한 완료 조건을 확인한다. 로컬 변경, 커밋, PR 등 맡긴 전달 지점도 구분한다. 구현을 맡겼다면 조사·방법 발견·문서 작성을 원래 목표의 완료로 바꾸지 않는다. 조사만 맡겼다면 그 범위를 지킨다. 이미 정해진 목표나 권한을 반복 확인하지 않는다.
2. 착수하거나 작업을 다시 이어갈 때 [작업 맥락](references/context.md)에 따라 관련 기억·업무 상태·미처리 기록을 조회한다. 현재 요청과 프로젝트 지침에 맞는 내용을 재사용한다. 정리 필요 신호가 있으면 해당 규약의 담당자가 [tidy](../tidy/SKILL.md)를 실행한다. 실행 환경이나 저장 권한 문제는 작업 맥락의 복구 절차를 따른다.

   업무 ID나 원본 ref를 미리 알 수 없는 새 업무는 [관련 업무와 적용 조건을 찾는 절](references/context.md#관련-업무와-적용-조건을-찾는다)을 적용한다. 이미 유효한 업무·ref·근거를 알고 있으면 재사용하고 전체 검색을 반복하지 않는다.

   채택한 근거에 의존하는 중요한 판단이나 논리적 작업 단위 경계에서는 [채택한 맥락을 다시 확인하는 절](references/context.md#채택한-맥락을-다시-확인한다)을 적용한다.

3. 영향을 받는 도메인의 목적·용어·책임·제약과 현재 동작을 [understand](../understand/SKILL.md)의 방식으로 조사한다. 이미 확보한 근거는 재사용하고 부족한 부분만 확인한다.
4. 아래에서 경로를 선택한다. 변경 작업은 [변경 경로](references/change-routes.md)의 해당 절을 적용한다. 복합 작업은 결과별로 경로를 조합하고 선행 결과가 필요한 순서로 진행한다.

| 원하는 결과           | 먼저 확인할 것                        | 구현과 완료 증거                                                              |
| --------------------- | ------------------------------------- | ----------------------------------------------------------------------------- |
| 현재 상태의 이해·진단 | 코드와 실제 동작, 필요한 경우 이력    | 읽기 전용으로 설명하고 멈춘다.                                                |
| 결함 복구             | 사용자가 겪는 현상의 재현과 원인      | 원인을 고치는 최소 변경 후 같은 조건에서 재현이 사라졌는지 확인한다.          |
| 새 동작               | 사용자의 결과, 기존 계약, 바뀌는 책임 | 필요한 설계 후 구현한다. 새 동작과 유지할 동작을 실제 사용 경로에서 확인한다. |
| 동작 보존형 재구성    | 변경 전 관찰 가능한 동작              | 구조를 바꾸고 동등한 결과를 확인한다.                                         |
| 성능 개선             | 재현 가능한 기준값과 병목             | 측정한 원인을 바꾸고 같은 조건에서 전후를 비교한다.                           |

복잡한 작업에서는 선택한 경로, 검증할 단위와 중요한 생략 이유를 실행 전에 짧게 공유한다. [공통 업무 CLI](references/context-work.md)로 목표·범위·완료 조건을 정의하고 조건별 결과와 증거를 연결한다. 위임받은 업무는 이미 정의된 명세를 읽고 수행한다. 대화와 업무 CLI로 부족한 장기 계획에만 [실행 계획 템플릿](../../templates/execution-plan.md)을 사용한다. 작은 작업에 계획 파일을 만들 필요는 없다.

## 인터럽 뒤에도 맡긴 업무를 이어간다

착수할 때 원래 목표와 다음 행동을 [미완료 업무 규약](references/context.md#미완료-업무를-확인하고-재개한다)에 따라 저장한다. 진행 중 새 메시지는 기존 업무의 보완·순서 변경·별도 요청·보류·취소 중 무엇인지 판단한다. 짧은 상태 질문에는 중간 응답으로 답하고 작업을 계속한다. 별도 요청을 먼저 처리할 때는 원래 업무의 검증한 진행과 복귀할 다음 행동이 저장되어 있는지 확인하고 빠진 내용을 갱신한다. 일시적인 작업 전환만으로 원래 업무를 완료하거나 보류하지 않는다.

짧은 요청을 끝낸 뒤와 최종 응답 전에는 `recall`의 `unfinishedWorks`·`unreviewedWorks`·`awaitingReviewWorks`를 확인한다. `work show`의 현재 명세·선행 상태·남은 조건을 대조해 현재 맡긴 범위의 실행 가능한 업무를 이어간다. submitted는 검토 대기이므로 작업자가 다시 수행하지 않고 reviewer에게 결과를 반환한다. 단기 요청의 완료 보고로 전체 실행을 끝내지 않는다. 우선순위나 권한이 불명확하면 해당 선택만 확인하고, 확인할 필요가 없는 업무는 계속한다.

보류·막힘·취소는 이유와 재개 조건을 보존한다. 사용자 재개 지시가 필요한 보류나 취소한 업무를 임의로 실행하지 않는다. 프로젝트의 다른 대화에 속한 업무는 원문과 권한을 확인하고, 실행 중인 작업자에게 맡긴 업무는 중복 수행하지 않는다. 남은 업무가 없거나, 남은 업무 모두가 실제로 사용자 선택·권한·외부 조건을 기다리는 경우에 그 상태와 다음 행동을 전달한다.

## 위임받은 업무를 수행한다

다른 에이전트가 업무를 위임했다면 전달받은 업무 ID로 `work show`를 읽고 목표·범위·완료 조건·assignment·선행 결과와 작업 경로를 대조한다. 조율자가 지정한 worker ID를 actor로 사용한다. 전체 계획과 업무 간 조정은 메인 에이전트인 조율자가 맡고, 위임받은 에이전트는 맡은 범위의 세부 계획·수행·검증을 맡는다. 같은 워크트리의 다른 변경을 보존한다. 업무 간 충돌, 범위·완료 조건 변경이나 추가 위임이 필요하면 근거를 기록하고 조율자에게 요청한다.

수행 과정의 판단과 출처는 record에, 조건별 관찰·근거·남은 행동은 work report에 남긴다. 지정된 중간 결과와 막힘·전제 변경도 조율자에게 보고한다. 공유 기록의 정리 담당자가 지정됐다면 [작업 맥락의 정리 규약](references/context.md#정리-시점을-판단한다)을 따른다. 수행을 마치면 work submit으로 결과를 고정하고 submission.ref, 실제 검증 조건·결과, 변경 경로와 기록 ref를 지정된 반환 경로로 보고한다. 직접 complete하거나 자신의 결과를 수락하지 않는다. 보완 요청은 현재 명세와 지적 조건을 읽고 report·submit으로 다시 제출한다.

## 책임·계약을 바꾸는 판단 흐름

책임 배치나 외부 계약을 바꾸는 작업에서는 다음 흐름을 기본으로 삼는다. `work`는 전체 판단 흐름과 이번 작업의 범위를 잇는다. 이미 확보한 근거는 재사용하고, 작은 결함 복구나 단순한 이해 요청에서는 필요한 단계만 수행한다.

| 순서               | 판단과 다음 단계로 전달할 내용                                                                                                                                                                  |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 현재 구조 확인     | [understand](../understand/SKILL.md)로 판단·실행·상태 보관의 담당자를 실제 구현과 호출 관계에서 확인한다. 현재 구조의 형성 이유를 근거와 함께 설명하고, 확인하지 못한 이유는 미확인으로 남긴다. |
| 레퍼런스·대안 비교 | [architect](../architect/SKILL.md)로 같은 책임을 배치하는 대안과 관련 레퍼런스의 적용 전제를 비교한다. 각 선택에서 얻거나 포기하는 정보·보장과 전환 비용을 드러낸다.                            |
| 장기 방향 설정     | 도메인의 목적과 반드시 지킬 제약에서 목표 책임과 계약을 정한다. 현재 구현에서 비롯된 제약을 계속 유지할 이유는 별도로 판단한다.                                                                 |
| 이번 변경 구체화   | 지금 반드시 바꿀 부분, 유지할 구현과 미룰 문제를 나눈다. 구현 전에 실제 변경할 클래스·함수·계약, 전환 순서와 검증 조건을 구체화한다. 임시 구조에는 유지 이유와 해소 조건을 둔다.                |
| 실행·검증          | 선택한 범위를 구현하고 [verify](../verify/SKILL.md)로 목표와 보존할 동작을 실제 사용 경로에서 확인한다.                                                                                         |

현재 구조를 확인한 사실과 변경을 위한 설계 제안을 구분한다. 장기 방향과 이번 구현 범위도 별개의 판단으로 설명하며, 장기 방향에 대한 동의만으로 이번 범위를 확대하지 않는다.

## 설계와 인간의 결정을 구분한다

책임의 배치나 외부 계약을 다시 정해야 하거나, 사용자 경험에 중요한 선택 또는 되돌리기 비싼 구조 선택이 있으면 [architect](../architect/SKILL.md)를 적용한다. 이미 정해진 패턴을 따르는 작은 확장은 `work`에서 변경 그림만 짧게 설명하고 진행할 수 있다.

- 관찰이나 실험으로 풀 수 있는 갈림길은 조사하거나 작은 시제품으로 확인한다.
- 목표와 판단 기준이 정해져 있다면 현재 그림과 변경 그림을 공유하고 진행한다. 공유는 승인 요청이 아니다.
- 도메인 의미, 제품 정책, 사용자 경험 또는 외부 계약에 관해 사람의 선택이 남아 있으면 대안과 영향을 제시하고 해당 선택에 의존하는 구현을 멈춘다.
- 사용자가 구현 전 확인을 요청했다면 멈춘다. 되돌리기 어려운 외부 작업도 실행 전에 확인한다.

새로 확인한 사실이나 사용자 피드백이 합의한 결과·책임 또는 설계 전제를 바꾸면, 이전 그림에서 달라진 부분과 다음 판단에 미치는 영향을 먼저 공유한다. 영향받는 부분만 다시 조사·설계하고 구현·검증에 반영한다. 세부 구현의 조정만으로 이미 확인한 방향을 반복 승인받지 않는다. 완료 조건을 만족시키기 위해 목표나 검증 기준을 임의로 완화하지 않는다.

## 구현하고 증명한다

선택한 설계를 검증 가능한 단위로 구현한다. 각 단위가 끝나면 실제 결과를 work report의 조건 ID·관찰·판정·근거에 연결하고, 재개할 다음 행동을 갱신한다. 합의·판단·출처는 record에 남긴다. 조건이나 범위를 바꾸면 owner가 work revise로 정의를 갱신하고 무효화된 조건과 영향받는 업무를 확인한다. 이때 정리 필요 신호도 확인해 필요하면 tidy를 실행한다. 한 세션에서 오래 이어가는 작업에도 같은 절차를 적용한다. 반복 변경이나 복잡한 비교를 사람이 확인하기 어렵다면 기존 도구를 먼저 찾고, 부족한 부분에 필요한 스크립트를 만든다.

검증이 실패하면 구현, 판단의 전제, 관찰 방법 중 무엇이 잘못됐는지 조사한다. 증거가 반박한 가설 때문에 자신이 추가한 변경은 걷어낸다. 사용자나 다른 작업의 변경은 보존한다. 범위 안의 문제는 수정하고 영향받는 조건을 다시 검증한다.

전달 전에 자신의 diff를 읽고, 최종 변경이 선택한 설계와 작업에 적용되는 원칙을 충족하는지 확인한다. 임시 진단 코드와 실험 잔여물을 정리하고 무관한 변경이 섞이지 않았는지 확인한다.

최종 상태를 [verify](../verify/SKILL.md)로 확인한다. 위험한 변경, 논쟁적인 설계 또는 요청받은 검토에는 [review](../review/SKILL.md)를 적용한다. 새 지적을 검증하고 범위 안의 결함을 고친 뒤 영향받는 검사를 다시 실행한다.

맡긴 전달 지점까지 완료한다. 커밋이나 PR을 요청받았다면 검증 가능한 변경 단위와 증거가 전달 순서와 설명에서도 이어지게 한다. 작업 권한을 자동으로 커밋·푸시·PR·병합 권한으로 확대하지 않는다.

단독 업무는 전체 조건과 필수 하위 결과·선행 상태를 확인한 뒤 work complete로 완료한다. 위임받은 업무는 제출하고 조율자의 수락을 기다린다. 결과에는 달라진 동작, 유지된 조건, 중요한 판단과 실제 증거를 연결한다. 결과 판단에 영향을 주는 실패·미확인은 분명히 알린다. 필수 검사나 이번 완료 조건의 실패·미확인이 남으면 업무를 완료로 표시하지 않는다. 원칙은 선택을 바꾼 경우에만 이름과 영향을 밝힌다. 진행할 수 없다면 report에 막힌 조건·다음 행동을 저장하고 확보한 결과를 전달한다.

## 기록의 수명을 정한다

현재·변경 그림은 기본적으로 이 작업의 대화에서 설명한다. PR이나 커밋 설명은 당시의 판단과 증거를 남기는 기록이지 영구히 갱신할 현재 설계도가 아니다. 이후 작업자가 반복해서 의존할 사용법·외부 계약·검증 절차에만 살아 있는 문서를 만든다. 그 문서를 만들 때 갱신할 근거와 방법도 정한다. `.loom/` 문서의 생성·갱신은 기본 절차가 아니다. 기존 문서는 현재 코드의 근거와 대조할 역사 자료로만 취급한다.

일상 작업에서는 `record`로 이후 작업에 필요한 합의·제약·판단·관찰을 출처와 함께 추가한다. 이유와 적용 조건은 본문에 포함한다. 업무 CLI가 현재 정의·진행·검증·수락 상태를 소유한다. `tidy`는 그 원본을 대조해 프로젝트 기억과 그래프를 갱신하며 managed 업무 상태를 변경하지 않는다. 실행 방법과 기존 업무의 전환은 [작업 맥락](references/context.md)을 따른다. 업무 완료는 실제 검증 근거로 판단하며 기록 정리 시점과 구분한다.

기록 본문과 정리 결과는 CLI의 stdin으로 직접 전달한다. 저장용 입력 파일이나 기억 파일을 편집 도구로 작성하지 않으며, 사용자에게 기억 파일의 검토·관리를 요구하지 않는다.

서브에이전트는 기본 경로에 넣지 않는다. 사용자나 프로젝트의 위임 정책을 따르고, 명시적 요청 없이 위임하지 않는다. 사용자가 위임을 요청했지만 모델을 정하지 않았다면 모델 선택을 먼저 요청한다.
