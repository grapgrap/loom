# Implement

## 무엇을 검증할지 고른다

합의한 가장 작은 장면을 선택한다. 시작 조건, 행동, 기대 결과를 사용자 결정이나 기존 호출자의 계약에서 가져온다. 결함 수정이라면 증상이 드러난 조건이 출발점이다. 기대값을 쓰기 전에 약속을 어긴 구현 하나를 떠올리고 무엇을 관찰하면 걸러낼 수 있을지 정한다.

예시의 입력, 모델의 탐색 한도, 테스트 준비를 위한 가정에는 각각 용도가 있다. 한도 밖의 동작을 영구 테스트로 고정하려면 허용과 거부 어느 쪽이든 적용할 계약을 찾는다. 기존 진입점의 동작을 새 경로에서도 보장해야 하는지는 그 경로의 약속에서 확인한다. 합의한 장면만으로 작업을 마칠 수 있으면 열린 정책은 그대로 둔다. 위임된 구현 선택은 기존 구조를 따라 결정하고, 새 제품 결정이 작업을 좌우할 때 그 장면을 `$loom:architect`로 돌려준다.

## 장면 하나를 Red → Green → Refactor로 완성한다

1. **Red.** 조건과 기대 결과가 드러나는 테스트를 먼저 작성해 실행한다. 한 역할의 규칙은 그 역할에서, 역할 간 계약은 경계를 거쳐, 사용자가 보는 결과는 실제 진입점에서 관찰한다. 준비 오류와 의도한 실패를 가른다. 기존 테스트가 이미 같은 약속을 검사한다면 그 근거를 재사용한다.
2. **Green.** 기대 결과를 만족하는 코드를 작성하고 해당 테스트와 기존 동작을 검사한다. 실행 결과에 기대값을 맞추기 전에 합의가 바뀌었는지 확인한다. 상태나 순서의 차이가 중요하면 바로 그 차이를 드러내는 입력을 쓴다.
3. **Refactor.** 통과 상태에서 이름·타입·책임 배치를 다듬는다. 판단을 담당하는 역할을 코드에서 찾을 수 있고 같은 규칙을 한 곳에서 바꿀 수 있는지 본다. 같은 테스트를 다시 실행한다.

구현과 테스트의 설명은 이름과 구조로 표현하고 새 주석은 쓰지 않는다. 수정 범위의 기존 주석은 라이선스, 외부 제약의 이유, 공개 API 계약, 이슈로 추적하는 제약과 근거 있는 도구 지시문을 보존한다. 코드의 동작을 되풀이하거나 미완성 작업을 합리화하는 주석은 정리한다.

## 실제 경로에서 마친다

대표 장면을 처음부터 실행해 기대와 관찰을 대조한다. 사용자가 경계를 지정했다면 진입점에서 어느 역할이 판단하고 상태를 바꿨는지 짚는다. 실행 결과, 재현 방법과 관련 코드 위치를 `$loom:work`에 전달한다. 중단할 때는 남은 경로와 다음 검증을 인계 기록에 반영한다. 사용자가 체험할 프로토타입에는 시작 방법도 포함한다.
