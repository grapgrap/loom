# Implement

구현 코드와 테스트 코드에 주석을 작성하지 않는다. 테스트 이름에 조건과 기대 동작을 드러내고, 그 동작을 어기면 실패하는 검증문으로 의도를 표현한다.

## 시나리오 목록

`$loom:architect`가 정한 계약과 시나리오 목록에서 바꿀 동작과 보존할 동작을 확인한다. 각 흐름의 시작 조건, 호출자의 행동, 기대 결과를 살피고 다음 흐름 하나를 고른다. 내부 클래스나 메서드를 만드는 일은 완료 조건에서 제외한다.

목록 전체를 미리 테스트로 옮기면 첫 구현에서 배운 내용 때문에 뒤의 테스트까지 고쳐야 한다. 선택한 흐름만 실행 가능한 테스트로 표현한다.

## 1. Red

하나의 흐름은 하나의 테스트로 표현한다. 모든 테스트는 어떤 조건에서 무엇을 검증하는지 한 문장으로 설명할 수 있어야 한다. 호출자가 관찰할 결과를 먼저 정하고, 그 결과를 판별할 검증문에서 거슬러 올라가 호출 방법과 준비 조건을 정한다. 기존 테스트가 같은 흐름을 검증하면 재사용해 테스트 수를 최소로 유지한다.

변경 전에 테스트를 실행해 기대한 동작을 충족하지 못해 실패하는지 확인한다. 준비 과정에서 실패하면 원인을 바로잡고 다시 실행한다. 처음부터 통과하면 검증문이 실제 요청의 조건과 결과를 확인하는지 대조한다. 이미 동작을 보장한다면 통과 근거를 기록하고 다음 흐름을 고른다.

## 2. Green

선택한 테스트가 요구하는 동작을 구현한다. 결함은 재현한 경로에서 원인을 고친다. 해당 테스트와 기존 테스트를 실행해 새 동작과 보존할 동작을 함께 확인한다.

실제 출력을 기대값에 복사하거나 검증문을 약화하면 테스트가 같은 오류를 받아들인다. 기대값은 계약에서 도출한다. 구현 중 다른 흐름을 발견하면 목록에 추가하고, 구조 정리는 테스트를 통과한 뒤에 판단한다.

## 3. Refactor

테스트를 통과한 상태에서 의도를 읽기 어렵게 하거나 같은 규칙을 여러 곳에서 고치게 하는 구조를 찾는다. 개선할 부분이 있으면 동작을 유지하며 정리하고 같은 테스트를 다시 실행한다.

모양이 비슷한 코드도 서로 다른 이유로 바뀔 수 있다. 추상화를 추가하기 전에 함께 바뀌어야 할 규칙을 설명할 수 있는지 확인한다. 현재 흐름에서 개선할 점이 없으면 다음 시나리오로 넘어간다.

## 완료 판단

실제 결과를 확인한 항목만 목록에서 완료로 표시한다. 남은 흐름마다 같은 과정을 반복한다. 새로 발견한 흐름이 기존 계약과 충돌하면 해당 조건과 질문을 `$loom:work`에 돌려준다. 이번 범위의 항목을 모두 확인하면 시나리오별 결과와 검증 근거를 전달한다.
