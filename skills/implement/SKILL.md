# Implement

## 이번에 완성할 흐름

새 동작은 설계에서 선택한 가장 작은 사용자 흐름과 그 흐름에 꼭 필요한 규칙부터 구현한다. 결함은 증상이 나타난 조건과 회복할 계약에서 시작한다. 누가 어떤 조건에서 무엇을 했을 때 어떤 결과를 기대하는지 확인 기준으로 삼고, 기존 호출자가 의존하는 동작도 짚는다.

합의한 결과를 만족하는 구현 방법은 기존 코드의 역할과 관례를 보고 고른다. 구현 중 새로 발견한 사례가 기존 약속을 깨면 그 사례를 재현한다. 제품의 약속 자체를 정해야 하는 경우에는 결과가 갈리는 장면을 `$loom:architect`에 돌려준다. 뒤에 다룰 사례는 현재 흐름에서 분리한다.

## Red → Green → Refactor

1. **Red.** 사용자가 선택한 결과를 어기면 실패할 검증문부터 생각한다. 개인과 팀, 오늘과 다음 날처럼 기대를 가르는 조건을 실제 테스트에 넣는다. 한 역할의 판단은 단위 테스트로, 경계를 넘는 계약은 통합 테스트로, 사용자 진입점부터의 약속은 그 경로를 실행해 확인한다. 변경 전에 실행해 의도한 이유로 실패하는지 본다. 준비 단계에서 실패하면 조건을 바로잡는다. 기존 테스트가 이미 같은 약속을 확인한다면 통과 근거를 남기고 다음 동작으로 넘어간다.
2. **Green.** 해당 결과를 만족하는 만큼 구현하고 선택한 테스트와 기존 테스트를 실행한다. 기대값은 합의한 규칙에서 얻는다. 실행 결과에 맞춰 기대값을 바꾸면 잘못된 동작도 통과한다. 바뀔 수 있는 입력이나 사건 순서에서도 지켜야 하는 약속은 그것을 깨뜨릴 수 있는 조건에서 확인한다.
3. **Refactor.** 통과하는 상태에서 이름과 역할이 의도를 드러내는지, 같은 규칙을 여러 곳에서 고쳐야 하는지 살핀다. 같이 바뀌어야 하는 판단은 한 곳에 두고, 서로 다른 이유로 바뀌는 규칙은 독립적으로 표현한다. 동작과 의도에 필요한 요소만 남긴 뒤 같은 테스트를 다시 실행한다.

## 코드에 의도를 남긴다

구현과 테스트에 새 주석을 쓰지 않는다. 설명이 필요한 분기는 이름, 타입이나 책임 배치를 먼저 고쳐 의도와 유효한 상태를 코드에 드러낸다. 테스트 이름에는 조건과 기대 결과를 담는다.

수정한 범위의 기존 주석 중 라이선스, 바꿀 수 없는 외부 제약의 이유, 공개 API 계약, 이슈로 추적하는 제약, 근거 있는 린트 억제와 포매터 지시문을 보존한다. 동작을 되풀이하는 설명, 섹션 배너, 주석 처리한 옛 코드, TODO와 임시방편을 정당화하는 주석은 정리한다.

## 구현의 근거를 넘긴다

처음 합의한 조건에서 대표 흐름을 끝까지 실행해 기대와 관찰을 대조한다. 결함 수정은 처음 실패한 조건을 다시 거친다. `$loom:work`에 어떤 행동에서 무엇을 관찰했는지, 사용자가 확인할 실행 기록이나 재현 방법, 확인한 범위를 전달한다. 프로토타입은 직접 실행해 보고 사용자가 같은 장면을 경험할 시작 방법과 확인할 결과를 함께 건넨다.
