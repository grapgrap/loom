# Review

산출물과 확인 가능한 근거를 기준으로 판단과 검증의 빈틈을 찾는다. 작성자의 확신과 별개로 반례를 확인한다. 독립적인 검토 요청은 조사와 보고가 범위다. `work`의 일부로 수행하면 확인된 지적을 실행 책임자에게 전달한다.

검토의 판단 기준은 [원칙](../../references/principles.md)의 공통 설명과 적용 절차를 따라 정한다.

## 검토 범위를 정한다

사용자가 지정한 설계, 파일, diff, 커밋 또는 PR을 우선한다. 지정하지 않았다면 이번 작업의 변경 범위를 확인한다. 사용자 목표와 유지할 계약을 복원하되, 작성자의 설명을 산출물의 증거로 대신하지 않는다.

책임 배치나 외부 계약을 바꾸는 검토에서는 [설계](../architect/SKILL.md)의 장기 목표와 이번 변경 범위를 구분한다. 목표 구조의 타당성을 검토하는지, 이번 구현과 전환 단계의 충족 여부를 검토하는지 밝힌다.

## 무엇을 의심할지 고른다

사용자의 목표와 설계에서 보존하거나 바꾸기로 한 조건을 기준으로, 변경이 잘못된 결과를 만들 수 있는 경로와 근거가 부족한 판단을 고른다. 판단에 관련된 원칙을 적용해 설계·구현·검증이 그 조건을 충족하는지 확인한다.

책임·계약 변경에서는 다음 구분에서 현재 판단에 관련된 의문을 고른다.

- 현재 책임의 설명과 실제 구현·호출 관계가 맞는지, 제안한 담당자를 현재 담당자로 전제하지 않았는지 확인한다.
- 레퍼런스의 보장에 필요한 전제가 이번 설계에서도 성립하는지, 구조의 유사성만으로 같은 보장을 기대하지 않았는지 확인한다.
- 선택한 범위와 전환 순서가 목표·보존할 계약을 충족하는지, 받아들인 정보·보장의 손실과 전환 비용을 빠뜨리지 않았는지 확인한다. 임시 구조의 유지 이유와 해소 조건도 검토한다.

구현 중 드러난 사실이 전제를 반박했는데도 처음의 그림이나 완료 주장을 유지하고 있지 않은지 본다.

살아 있는 문서의 실제 불일치는 지적하되, 과거의 작업 기록을 현재 설계도처럼 갱신하라고 요구하지 않는다.

## 보고

제출 전에 지적을 반박해 본다. 이미 처리한 경로, 의도한 트레이드오프 또는 적용되지 않는 전제를 결함으로 오인하지 않았는지 확인한다. 가능한 경우 반례를 실행한다.

이번 구현을 검토할 때는 장기 목표와의 차이나 범위 밖의 기존 문제만으로 결함이라고 판정하지 않는다. 의도한 비용이나 미룬 문제라도 이번 목표·보존할 계약을 위반하면 근거와 함께 지적한다.

확인된 문제만 영향이 큰 순서로 적는다. 각 지적은 위치, 재현 또는 논증 가능한 근거, 사용자에게 미치는 결과를 포함한다. 근거가 모자라면 결함이라고 단정하지 말고 확인할 질문으로 분리한다. 문제가 없으면 검토 범위와 남은 검증 한계를 말한다. 형식적인 지적 수를 채우지 않는다.
