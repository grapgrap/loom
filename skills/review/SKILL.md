# Review

확인된 변경 산출물이 스스로 정당화되는지 적대적으로 검토한다.

기본적으로 산출물을 만든 세션에서 직접 수행한다. 세션 맥락은 검토 범위를 식별하는 데만 사용하고, 대화에서 들은 의도나 합의는 산출물의 정당성을 판정하는 근거로 삼지 않는다. 파일, 실제 변경 증거, `.loom` 문서에 기록된 근거로 평가 맥락을 재구성한다. 검증과 보고만 수행하고 산출물을 직접 수정하지 않는다. 최종 판단은 사용자가 한다.

## Step 0 — 검토 범위 파악

다음 순서로 검토 범위를 파악한다.

1. 사용자가 범위를 지정했다면 그 범위를 우선한다.
2. 그렇지 않으면 현재 세션의 실행 이력에서 생성·수정·삭제한 파일, 세션 중 만든 commit과 그 범위, untracked·ignored이지만 다룬 산출물을 파악한다. 대화에서 언급하거나 조회만 한 파일은 포함하지 않고 실제 편집·삭제·Git 동작으로 변경이 확인된 산출물만 포함한다.
3. `git status`와 staged·unstaged diff를 확인해 세션에서 파악한 범위에 빠진 변경이나 다른 작업의 혼입이 없는지 대조한다. `git status`만으로 범위를 만들지 않는다.

각 산출물의 실제 변화도 확보한다.

- tracked 미커밋 변경은 staged·unstaged diff를 읽는다.
- 세션 중 커밋한 변경은 해당 commit이나 session range의 diff를 읽는다.
- untracked 파일은 본문을 직접 읽는다.
- ignored 산출물은 현재 본문과 세션에 남은 편집 내용을 읽는다.

현재 대화에 산출물 생성 이력이 없다면 사용자가 지정한 commit·range·patch 또는 명시적 산출물 범위로 검토한다. 범위가 주어지지 않았거나, modified 산출물의 변경 전후를 복원할 수 없거나, 세션 이력과 Git 상태가 어긋나면 추정하지 말고 사용자에게 확인한다. 그렇지 않으면 확인된 범위를 검토한다. 대상 프로젝트의 `.loom` 경로도 확인한다.

## Step 1 — 산출물과 합의 재구성

1. 변경 산출물과 Step 0에서 확보한 diff·patch·commit range·본문을 읽는다. `.loom` 문서는 본문도 읽는다.
2. `.loom/index.md`를 읽어 산출물이 닿는 도메인과 흐름을 파악한다.
3. 변경 맥락에서 좁은 검색어를 만들고 `aeira search -s {프로젝트의 .loom 경로} "{검색어}"`로 관련 concept·flow·decision 후보를 찾는다.
4. 관련 concept이나 flow에 `aeira graph neighbors -s {프로젝트의 .loom 경로} --direction=incoming "{노드}"`을 실행해 이를 떠받치거나 변경한 decision 후보를 보강한다.
5. 후보 문서를 읽고 산출물에 관련된 합의만 선별한다. 같은 사안의 decision이 충돌하면 순번이 큰 것을 우선한다.

기록된 decision의 근거와 기각 사유도 받아들일 전제가 아니라 비판 대상으로 다룬다.

## Step 2 — 문서 작성 가이드 로드

Step 0에서 확정한 검토 범위에 Loom 문서가 포함되어 있으면 `../../references/document-authoring-guide.md`를 읽는다. Loom 문서가 없으면 이 단계를 건너뛴다.

가이드 로드는 검토 기준만 추가한다. 가이드를 적용하기 위해 확인된 범위 밖의 Loom 문서를 검토 대상으로 추가하지 않는다.

## Step 3 — 룰 카탈로그 로드

`.loom/rules/index.md`를 읽어 어떤 rule과 convention이 있는지 카탈로그를 인지한다.

rule은 이 프로젝트에서 항상 지켜져야 하는 강제적 합의, convention은 강하게 권장되지만 대체 가능한 형태이다. 인덱스로 항목 목록과 각 항목의 호출 상황을 파악한다. 본문은 검토 시점에 필요한 항목을 골라낸 뒤 로드한다.

## Step 4 — 비판

산출물이 정말 최선인지, 반례가 없는지, 더 단순한 길이 없는지, 숨은 결함이나 빠진 경로가 없는지 따진다. 있는 것의 정당성뿐 아니라 설계가 비운 경로와 다루지 않은 경우도 검토한다.

평가 기준에는 다음 위계를 적용한다.

### 1순위 — 프로젝트 합의

concept·flow·decision·rule을 가장 강한 기준으로 사용한다.

- concept이나 flow를 변경하거나 새로 세운 산출물은 변경의 근거가 충분한지, 대안이 충분히 탐색되었는지, 파급이 빠짐없이 반영됐는지 본다.
- 기존 결정을 뒤집은 산출물은 뒤집은 이유의 타당성을 먼저 보고, 뒤집은 사실의 기록 여부는 그다음에 본다.
- 구현 산출물은 concept의 책임·정책·경계와 flow의 단계를 충족하고 기존 decision을 위반하지 않는지 본다.
- rule과 convention은 도구 카탈로그처럼 활용한다.
  1. 산출물이 수행하는 행동을 명시한다.
  2. 카탈로그에서 그 행동에 적용될 항목을 고른다.
  3. 고른 항목의 본문을 읽어 정의를 파악한다.
  4. 산출물이 정의에 부합하는지 검증한다.

concept 경계의 이상은 다음 징후를 실마리로 비판한다.

- **비대화**: 분화해야 할 책임이 기존 concept에 눌어붙는다.
- **의미 흐려짐**: 변경 대신 예외와 단서로 경계를 감싼다.
- **데드 concept**: 쓰임을 잃은 concept이 방치된다.
- **과잉 분화**: 실제 쓰임 없이 concept을 쪼갠다.

#### Plan 산출물

Plan 산출물은 현재 구현의 조사 결과와 문제를 해결할 구현 방안을 구분하여 설명해야 한다. 구현 방안의 예상 영향을 검토하고 변경안에서 실행 작업을 도출해야 한다. concept·flow와 다른 의미나 경계를 전제로 한다면 해당 설계에 반영되었는지 확인한다.

변경안을 다음 기준으로 검토한다.

- 현재 동작과 문제 원인에 대한 설명을 관련 코드·문서·테스트와 대조한다. 확인한 사실과 가정이 구분되는지 확인한다.
- 구현 방안이 문제를 해결하고 원하는 결과를 만드는지 확인한다. 기존 구조의 유지 자체를 타당성의 기준으로 삼지 않는다. 선택에 따라 동작이나 구조가 달라지는 지점의 영향이 드러나는지 본다.
- 영향을 받는 사용처, 상태 변경과 실패 경로에 필요한 대응이 누락되지 않았는지 확인한다.
- 주요 변경의 코드 위치, 책임, 인터페이스, 호출 관계와 핵심 로직이 구현 초안에 있는지 확인한다. 목적과 완료 조건만으로 초안을 대신하지 않았는지 본다.
- 실행자가 새로 정해야 할 주요 설계를 남긴 범위가 실행 가능 상태로 확정되어 있으면 결함으로 판단한다. 검증 결과를 기다리는 범위는 별도로 구분되었는지 확인한다.
- 합의한 구현 초안과 부작용 대응이 실행 작업 및 검증 방법에 반영되는지 확인한다.
- 미확인 사항을 확인할 방법과 시점이 있으며, 그 결과에 의존하는 실행 전에 재검토할 수 있는지 확인한다.

구현이 진행된 plan의 변경 전 동작은 확보한 diff나 변경 전 코드와 대조한다. 이미 적용된 변경 때문에 현재 코드가 설명과 달라진 것을 plan의 오류로 판단하지 않는다.

산출물과 기록된 근거로 변경안을 평가한다. 사용자가 대화 중 주요 결정을 알아차렸는지 또는 실행 요약을 확인했는지는 산출물만으로 추론하지 않는다.

각 태스크의 결과 계약을 다음 기준으로 검토한다.

- 각 태스크가 목적, 수행할 변화, 완료 결과와 검증 방법을 모두 기술하는지 확인한다.
- 목적, 수행할 변화, 완료 결과와 검증 방법이 같은 결과를 가리키는지 확인한다.
- 완료 결과가 활동의 반복이 아니라 검증 가능한 상태, 산출물 또는 능력인지 확인한다.
- 완료 결과가 변경안을 실체화하거나 후속 태스크의 전제가 되는지 추적한다.
- 제외가 범위로 오해할 만한 인접 작업만 한정하는지 확인한다. 필요한 결과나 검증을 제외로 숨긴 경우에는 결함으로 판단한다.
- 임시 핸드오프가 있으면 현재 미완료 태스크 안에 있으며 재개 지점과 아직 끝나지 않은 작업만 담는지 확인한다. 태스크가 완료되었거나 확인된 변경 증거에서 핸드오프 작성 후 실행을 재개했는데도 남아 있으면 결함으로 판단한다. 사용자의 명시적 요청 여부는 산출물만으로 추론하지 않는다.

전체 결과 사슬을 다음 기준으로 검토한다.

- 각 결과 의존이 구체적인 선행 결과와 그 결과를 요구하는 후속 전제를 연결하는지 확인한다.
- 단순한 작성 순서나 선호하는 실행 순서를 결과 의존으로 기록하지 않았는지 확인한다.
- 필요한 선행 결과의 누락, 후속 전제가 없는 고아 결과 또는 순환하는 결과 의존이 있는지 확인한다.
- 모든 중간 결과가 Plan의 목적이 요구하는 최종 결과까지 이어지는지 확인한다.

실행 중 발견의 반영은 확인된 변경 증거를 기준으로 검토한다. 변경 증거에서 남은 실행을 제약하는 기술적 사실이 확인되면 영향받는 변경안·태스크·검증 또는 결과 의존에 그 사실이 반영되었는지 확인한다. 실행 중 발견을 시간순으로 누적한 전역 진행 맥락은 결함으로 판단한다.

주요 변경의 코드 구조·인터페이스·핵심 로직은 구현 초안으로 검토한다. 모든 코드 줄이나 함수 시그니처의 완성을 요구하지 않는다. task가 적용 가능성을 확인하며 조정할 수 있다는 이유로 주요 설계가 빠진 초안을 허용하지 않는다. 작업 견적이나 파일별 체크리스트가 없다는 이유만으로 비판하지 않는다. 내부 산출물이나 능력도 변경안을 실체화하거나 후속 태스크의 전제가 되면 정상적인 결과로 인정한다.

### 2순위 — Loom 문서 작성 가이드

검토 범위 안의 Loom 문서는 내부 문서 작성 가이드에 따라 평가한다. 프로젝트 합의가 설계와 구현 내용의 진실을 정한다면, 문서 작성 가이드는 그 내용을 Loom 문서에 배치하고 표현하는 기준을 정한다.

- 문서 유형별 책임과 내용 라우팅은 반드시 지켜야 하는 기준으로 적용한다.
- 위키링크가 문서 사이의 구조적 관계를 나타내는지 확인한다.
- 기술문서 작성 기준은 독자가 같은 사실, 제약과 책임 관계를 재구성할 수 있는지 판단하는 데 사용한다.
- 가이드보다 의미를 더 명확하게 전달하는 대체 표현은 위반으로 판단하지 않는다.

### 3순위 — 일반 표준

프로젝트 합의가 판가름하지 않는 영역에서는 해당 분야의 표준과 일반론으로 코드 결함, 엣지 케이스, 설계 약점을 검토한다. 표준적으로 받아들여지는 관행을 따른 산출물에 대한 트집은 같은 기준으로 기각한다.

## Step 5 — 비판 검증

제출 전에 각 비판을 자기반박한다.

- 정확한 파일과 프로젝트 문서, 문서 작성 가이드 또는 일반 표준으로 근거를 댈 수 없는 비판은 제출하지 않는다.
- 산출물이 이미 답한 것, 표준 관행을 트집잡은 것, 합의가 의도한 트레이드오프를 맥락 없이 결함으로 오인한 것을 걸러낸다.
- 관련 decision의 전제·제약·대안을 확인해 비판이 이미 고려된 비용을 반복하지 않는지 본다.
- 문서 작성 가이드에 근거한 비판은 정확한 가이드 항목을 특정한다. 의미 재구성을 방해하지 않는 표현 취향이나 가이드가 허용한 더 명확한 대체 표현은 제출하지 않는다.
- Plan의 구현 방안이 부족하다고 비판할 때에는 무엇이 빠졌으며 그 때문에 어떤 변경 영향이나 주요 선택을 판단할 수 없는지 코드 근거와 함께 특정한다. 단순히 더 상세한 명세나 파일별 작업 목록을 요구하지 않는다.
- 실행 중 발견의 반영 누락을 비판하려면 발견을 확인한 변경 증거와 그 발견이 영향을 주는 Plan 위치를 함께 특정한다.

검증을 통과한 비판은 모두 보고한다.

## Step 6 — 심각도

살아남은 비판에 심각도를 매긴다.

- **회귀**: 설계 수준의 재검토가 필요하다.
- **수정**: 구현 수준에서 해결된다.
- **관찰**: 문제는 아니지만 주목할 패턴이다.

심각도를 매긴 뒤 이론적 최악이 아니라 현실적 결과에서 그 등급에 값하는지, 완화 요인을 빠뜨리지 않았는지 다시 확인한다.

## Step 7 — 보고

보고 시작에 확인한 검토 범위와 그 범위를 입증한 변경 증거(diff·commit range·patch·본문)를 밝힌다. 복원하지 못했거나 사용자 확인에서 제외한 후보가 있으면 함께 명시한다.

각 비판을 다음 정보와 함께 보고한다.

- 문제의 내용
- 걸린 기준: 프로젝트 합의, Loom 문서 작성 가이드 또는 일반 표준
- 근거: concept·flow·decision·rule, 문서 작성 가이드 항목, 일반 표준 또는 파일 위치
- 심각도: 회귀·수정·관찰

심각도별로 비판을 정리하되 어느 비판도 묵살하지 않는다. 검증을 통과한 비판이 없으면 검토 범위와 기준을 밝히고 발견 없음으로 보고한다.
