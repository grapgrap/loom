## Outcome-Oriented Execution

사용자가 얻을 결과와 관찰할 완료 조건에서 작업을 역으로 구성한다. 조사 결과에 따라 수단을 바꾸되 목표나 성공 기준은 임의로 완화하지 않는다. 중간 결과가 최종 결과에 기여하는지, 맡긴 전달 지점까지 이어지는지 확인한다.

## Domain-First Design

목적·용어·책임·제약·경계를 정한 뒤 구조를 고른다. 상태나 규칙이 흩어지면 상태 모델, 타입, 표·레지스트리 또는 적절한 자료구조로 한곳에 표현한다. 실행 순서를 책임 경계로 오인하지 않는다. 선택한 구조가 중복 규칙·불가능한 상태·분기를 줄이는지 확인한다. 현재 코드가 명확하고 국소적이면 그대로 둔다.

## Domain Vocabulary

도메인의 사용자와 전문가가 쓰고 프로젝트에서 정한 용어를 코드의 이름과 인터페이스에도 일관되게 사용한다. 같은 개념을 여러 이름으로 부르거나 도메인의 의미를 일반 기술 용어로 치환하지 않는다. 다른 도메인의 표현과 현재 도메인의 의미가 다르면 만나는 경계에서 변환한다. 용어를 바꾸면 관련 호출자와 사용 예도 함께 맞춘다.

## Experience First

엔드유저와 기반 기술을 사용하는 개발자가 겪을 동작을 먼저 그린다. 호출 예에서 인터페이스를 도출하고 정상·실패 경로의 사용성을 확인한다. 구현 편의 때문에 호출자가 내부 규칙이나 불필요한 단계를 알아야 하는지 살핀다.

## Fix Root Causes

증상을 재현하고 실행 중 관찰로 원인과의 관계를 확인한다. 증거 없이 추가한 가드나 우회로 증상을 덮지 않는다. 가설이 틀렸다면 그 가설 때문에 자신이 만든 변경을 제거한다. 같은 재현 조건에서 실패가 사라졌는지 확인한다.

## Foundational Thinking

새 구조를 추가하기 전에 기존 코드와 그 조합으로 요구를 해결할 수 있는지 확인하고, 쓰이지 않는 경로·중복 검증·불필요한 층을 제거할 수 있는지 본다. 추상화가 다른 곳에 귀속되지 않는 입력·제약·역할을 소유하는지 확인한다. 현재 사용 사례와 확인된 제약을 근거로 도입하고 미래의 재사용 가능성만으로 층을 만들지 않는다. 문서도 실제 소비자가 의존할 내용에만 만든다. 가장 작은 정당한 변경은 목표 구조에 도달해야 한다. 줄 수를 줄이려고 필요한 계약이나 검증을 생략하지 않는다.

## Essential vs Accidental Duplication

코드 모양이 비슷하다는 이유만으로 합치지 않는다. 같은 변경 이유로 함께 바뀌어야 하는 본질적 중복에만 DRY를 적용한다. 변경 이유가 다르면 우연한 중복으로 보고 별도로 유지한다. 공통화가 서로 다른 정책을 묶거나 한쪽 변경을 다른 쪽에 불필요하게 전파하는지 확인한다.

## Draw Clear Boundaries

외부 입력은 CLI·설정·네트워크·저장 등의 진입 경계에서 해석하고 검증한다. 내부에서는 확보한 도메인 값과 계약을 사용하고 같은 검증을 반복하지 않는다. 외부 기술의 표현이 내부 책임이나 공개 인터페이스로 새지 않는지 확인한다. 도메인 밖의 소비자는 의도적으로 선택한 공개 계약으로 연결하고 필요한 동작과 값만 노출한다. 그 계약이 소비자를 내부 파일 구조나 구현 세부의 변경으로부터 분리하는지 확인한다. 프레임워크 연결과 도메인 판단을 나누되 실제 역할 없는 층은 만들지 않는다.

## Error Boundary Placement

실패를 잡기 전에 그 위치가 어떤 대응을 책임지는지 확인한다. 사용자에게 알림, 복구, 다른 흐름으로 분기 또는 롤백처럼 의미 있는 대응을 할 수 있는 경계에서 처리한다. 대응할 책임이 없는 곳에서는 실패를 상위로 전달한다. 오류 변환이나 정리를 위해 잡아도 원인과 실패 의미를 보존한다. 기록만 남기거나 임의의 빈값을 반환해 실패를 정상 결과처럼 숨기지 않는다.

## Meaningful Errors

처리자가 실패 종류를 구분하고 대응을 선택할 수 있도록 원인과 발생 맥락을 보존한다. 어떤 작업·대상·필드에서 실패했는지 드러내고, 가능하면 다음 대응이나 해결 방향을 제공한다. 오류의 타입·코드·반환 형태는 프로젝트의 계약을 따른다. 일반적인 실패 메시지로 원인을 지우거나 서로 다른 실패를 구분할 수 없게 만들지 않는다.

## Least Astonishment

기존 사용자와 호출자가 의존하는 동작을 변경 비용에 포함한다. 내부 API를 바꾸면 호출자를 옮기고 구 API와 참조를 함께 제거한다. 외부 소비자가 있는 계약에는 필요한 마이그레이션 경로를 제공한다. 전후 동작과 남은 호출자를 실제로 확인한다.

## Redesign From First Principles

여러 수정이 같은 전제에서 실패하거나 같은 우회가 반복되면 전제를 다시 조사한다. 새 제약이 처음부터 있었다고 보고 구조를 고른다. 기존 스케치를 지키기 위해 예외를 누적하지 않는다. 다시 설계한 판단을 반영한 구현과 검증 조건이 함께 바뀌었는지 확인한다.

## Minimize Reader Load

질문에서 답까지 거쳐야 할 층, 머릿속에 유지할 상태와 숨은 결합을 줄인다. 고유한 역할 없는 포장 함수와 중간 객체를 합치고 변경 가능한 상태의 범위를 좁힌다. 실제 책임이 있는 경계는 유지한다. 다음 사람이 흐름과 변경 이유를 더 적은 추적으로 이해할 수 있는지 확인한다.

## Intention-Revealing Names

함수·타입·상태·중간값의 이름에서 왜 존재하고 무엇을 하며 어떻게 쓰이는지 읽을 수 있게 한다. 호출 위치에 드러나는 맥락은 활용하되, 짧게 줄인 이름이 의도를 가리지 않게 한다. 일반적인 이름 때문에 본문을 읽어야만 책임이나 결과를 알 수 있다면 이름을 구체화한다. 명명으로 드러낼 수 있는 의도를 주석으로 대신하지 않는다.

## Single Level of Abstraction

한 함수 안에서 흐름을 조율하는 코드와 특정 단계의 세부 구현이 뒤섞여 의도를 가리지 않게 한다. 다른 함수·파일의 유사한 흐름에서도 같은 책임은 비슷한 수준으로 표현하고, 표현의 차이는 실제 책임·동작·제약의 차이를 반영하게 한다. 구문 모양이 아니라 도메인의 책임과 동작을 비교한다. 필요하면 함수를 추출하거나 인라인하되, 단순한 코드를 의미 없는 함수로 감싸거나 업무상의 분기·반복 자체를 불일치로 취급하지 않는다. 표현의 일관성이 구현의 공유를 요구하는 것은 아니다.

## Test Behavior, Not Implementation

소비자가 사용하는 진입점을 호출하고 관찰 가능한 결과를 판정한다. 기대값을 구현에서 다시 계산하거나 호출 횟수만 확인하여 검사가 결함을 놓치게 하지 않는다. 회귀 검사는 문제가 있는 상태에서 의도한 이유로 실패하고 수정 후 통과하는지 확인한다. 작동하지 않는 검사나 구현 문구를 고정하는 검사보다 직접 실행할 수 있는 작은 확인을 선택한다.

## Prove It Works

현재 산출물과 같은 사용 경로에서 직접 관찰한다. 다른 표면, 캐시된 값 또는 자기 보고로 성공을 추정하지 않는다. 검증이 실패하면 관찰 방법도 조사한다. 실행한 조건·결과·근거를 연결하고 닿지 못한 범위는 미확인으로 남긴다.

## Sequence Work into Verifiable Units

각 변경 단위가 확인 가능한 결과로 끝나고 후속 작업의 전제를 제공하게 한다. 선행 결과가 필요한 순서로 구현·검증·전달한다. 재구성은 각 단위에서 보존할 동작을 확인한다. 계획된 구조 이전에서는 목표에 필요 없는 임시 호환 계층을 만들지 않는다. 중간의 제한과 다음 확인 지점을 분명히 한다.

## Type System Discipline

허용할 상태와 연산에서 타입을 만든다. 함께 맞춰야 하는 불린과 선택 필드로 불가능한 조합을 허용하지 않는다. 필요하면 변형 타입으로 나누고 의미가 다른 값을 구별한다. 외부 값을 경계에서 해석하고 권위 있는 스키마의 형태는 그곳에서 도출한다. 강제 변환이나 내부 검사가 타입의 약점을 숨기는지, 새 상태를 추가하면 처리할 곳이 드러나는지 확인한다.

## Build the Lever

수작업을 반복하거나 복잡한 결과를 다시 비교해야 한다면 기존 도구를 먼저 사용한다. 부족하면 첫 단위에서 방법을 확인한 뒤 최소 변환·검사 스크립트를 만든다. 실제 결과와 대조하고 다시 실행해도 안전한지 확인한다. 한 번뿐인 작업도 도구가 증거를 재현하게 한다면 가치가 있다. 단순하고 눈으로 확인할 수 있는 수정에 프레임워크를 추가하지 않는다.

## Make Operations Idempotent

같은 요청의 재시도나 부분 실행 뒤에도 의도한 최종 상태로 수렴하게 한다. 완료와 중간 상태를 구별하고 필요한 식별·중복 방지·복구 방식을 도메인 계약에서 정한다. 정상 완료뿐 아니라 중간 중단 후 재실행을 확인한다. 반복 자체가 새 결과를 만드는 연산에는 그 계약을 먼저 구분한다.

## Separate Before Serializing Shared State

여러 실행자가 쓰는 대상과 불변 조건을 먼저 확인한다. 파일·브랜치·키·상태의 소유 범위를 나눌 수 있으면 나눈다. 공유가 실제 도메인 제약일 때만 직렬화나 동기화를 둔다. 격리가 성공 조건을 바꾸지 않는지, 필요한 공유에는 경쟁 조건 검증이 있는지 확인한다.

## Exhaust the Design Space

기존 방식과 새로운 방식을 사용 예·구조·비용으로 구체화한다. 중요한 선택에서는 같은 구조의 변형을 여러 대안으로 세지 않는다. 실행으로 답할 수 있는 차이는 작은 시제품이나 비교로 확인한다. 증거가 선택을 가르는지 확인하고, 사람의 제품·도메인·선호 판단이 남으면 그 선택을 드러낸다.
