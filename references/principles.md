## 끝그림과 설계 대안

도메인의 목적에 맞는 최종 상태를 먼저 정하고, 그 상태에서 설계 대안을 판단한다. 대안의 선택에는 관련된 도메인 책임, 소비자 경험과 복잡성의 기준을 적용한다.

| 원칙 | 적용 상황 |
| --- | --- |
| [Outcome-Oriented Execution](#outcome-oriented-execution) | 최종 상태를 정하고 현재 제약의 트레이드오프를 판단할 때 |
| [Redesign From First Principles](#redesign-from-first-principles) | 최종 상태가 기존 설계의 전제나 개념 범위를 바꿀 때 |
| [Exhaust the Design Space](#exhaust-the-design-space) | 전례 없는 설계의 대안을 선택할 때 |

### Outcome-Oriented Execution

가야 할 최종 상태를 먼저 구체적으로 제시한다. 그 최종 상태를 기준으로 현재 제약 때문에 지금 실현할 수 없는 부분을 식별하고, 무엇을 포기하거나 미룰지와 그 비용을 판단한다. 최종 상태와 이번 작업에서 도달할 상태를 구분하며, 수용한 트레이드오프의 근거와 이후 최종 상태에 도달할 방향을 명시한다. 현재 구현이나 당장 가능한 범위에 맞춰 최종 상태를 축소하거나, 시스템의 목적을 훼손하는 트레이드오프를 수용하지 않는다.

최종 상태가 기존 설계의 전제를 바꾸면 [Redesign From First Principles](#redesign-from-first-principles)로 그 상태에서 설계를 다시 판단한다. 최종 상태 자체를 찾는 탐색적 프로토타이핑에서는 미확인 부분을 밝히고 탐색한다. 외부 제약의 변화가 최종 상태 자체를 바꾸면 달라진 상태와 근거를 먼저 제시한 뒤 트레이드오프를 다시 판단한다.

### Redesign From First Principles

[Outcome-Oriented Execution](#outcome-oriented-execution)에서 제시한 최종 상태를 설계의 출발점으로 삼는다. 최종 상태가 기존 설계의 전제나 개념 범위를 바꾸면, 처음부터 그 최종 상태와 요구사항을 알았다면 어떤 설계를 선택했을지 판단한다. 기존 구조를 유지하기 위해 새 요구사항을 조건이나 예외로 끼워 맞추지 않고, 필요한 재설계가 이후 변경의 기반이 되게 한다.

기존 설계가 최종 상태를 자연스럽게 수용하면 유지한다. 변경의 영향이 극히 제한적이고 재설계 비용이 현저히 크면, 재설계를 미루는 판단을 최종 상태에 대한 트레이드오프로 명시한다.

### Exhaust the Design Space

전례 없는 설계는 구조와 사용 방식이 구체화된 대안을 비교한 뒤 선택한다. 기존 방식을 유지하는 안과 새롭게 설계하는 안을 함께 검토하고, 실제 책임이나 동작의 차이를 선택의 근거로 삼는다. 같은 구조의 작은 변형을 독립적인 대안으로 세지 않는다.

확립된 패턴을 적용하거나 제약상 선택지가 하나뿐인 경우에는 대안 탐색의 필요를 다시 판단한다. 탐색 비용은 결정의 영향 범위에 비례해야 한다.

## 도메인의 의미와 책임

도메인의 의미를 먼저 정하고 그 의미를 보존하는 책임과 계약을 구성한다. 같은 의미는 [코드의 이름과 표현](#복잡성과-코드의-표현)에서도 유지하며, 정한 책임은 [실패와 상태 변경](#실패와-상태-변경의-안전성)에도 이어진다.

| 원칙 | 적용 상황 |
| --- | --- |
| [Domain-First Design](#domain-first-design) | 문제의 개념과 책임을 구조로 표현할 때 |
| [Domain Vocabulary](#domain-vocabulary) | 도메인 개념의 이름과 인터페이스를 정할 때 |
| [Draw Clear Boundaries](#draw-clear-boundaries) | 검증 책임, 변경 이유와 관심사를 나눌 때 |
| [Earn Your Boundary](#earn-your-boundary) | 추상화의 독립성을 판단할 때 |
| [Type System Discipline](#type-system-discipline) | 허용하는 상태와 연산을 타입으로 표현할 때 |

### Domain-First Design

설계는 문제의 목적·개념·책임·제약·경계와 용어를 정하는 도메인 판단에서 시작한다. 기술 구조는 그 판단을 표현하는 수단이며, 구현 편의에서 도메인의 의미를 역으로 정의하지 않는다. 구조의 타당성은 도메인의 의미와 책임을 정확하게 반영하는지로 먼저 판단한다.

### Domain Vocabulary

도메인의 사용자와 전문가가 쓰고 프로젝트에서 정한 용어를 코드와 인터페이스에도 일관되게 사용한다. 같은 개념을 여러 이름으로 부르거나 도메인의 의미를 일반 기술 용어로 치환하지 않는다. 다른 도메인과 만나는 경계에서는 외부의 어휘를 현재 도메인의 의미로 변환한다.

### Draw Clear Boundaries

데이터의 검증 책임과 모듈의 변경 이유를 분명히 한다. 외부 입력은 경계에서 도메인 계약으로 해석하고 검증하며, 확보한 계약은 내부에서 신뢰한다. 서로 다른 변경 이유와 관심사를 한 모듈에 묶지 않고, 도메인의 판단을 외부 기술과 분리해 독립적으로 이해하고 검증할 수 있게 한다. 공개 계약은 필요한 동작과 값만 드러내 내부 구조의 변경으로부터 소비자를 분리한다.

경계가 아직 탐색 중인 초기 설계에서는 확인한 책임과 가정을 구분한다. 경계를 명확히 한다는 이유로 고유한 역할이 없는 층을 만들지 않는다.

### Earn Your Boundary

추상화의 독립성은 다른 추상화에 귀속되지 않는 입력·제약·역할을 소유하는지로 판단한다. 다른 추상화들의 조합으로 완전히 설명되거나 조합의 편의만 제공하는 경계는 분해한다. 기존 추상화를 제거하거나 흡수할 때도 그 추상화가 독립적으로 맡는 역할을 먼저 판단한다.

이름이나 등록 관계만으로 독립성을 정당화하지 않는다. 의사소통을 위한 별칭은 독립적인 추상화와 구분한다.

### Type System Discipline

타입은 도메인에서 허용하는 상태와 연산을 표현하고, 허용하지 않는 조합을 구조적으로 배제한다. 외부 값의 타입은 경계에서의 해석과 검증을 근거로 확보하며, 내부에서는 그 계약을 신뢰한다. 강제 변환이나 반복 검사로 불명확한 계약을 숨기지 않고, 상태와 계약의 변경이 영향을 받는 책임을 드러내도록 타입을 구성한다.

## 소비자의 경험과 계약

도메인 판단을 전제로 기술적 선택이 사용자와 호출자에게 주는 경험을 평가한다. 이 기준은 [끝그림과 설계 대안](#끝그림과-설계-대안)의 선택과 [인터페이스 변경](#migrate-callers-then-delete-legacy)에 함께 적용한다.

| 원칙 | 적용 상황 |
| --- | --- |
| [Experience First](#experience-first) | 기술적 선택이나 기능 범위가 사용자 경험에 영향을 줄 때 |
| [Least Astonishment](#least-astonishment) | 인터페이스의 동작과 계약을 정하거나 바꿀 때 |

### Experience First

도메인의 목적과 제약을 전제로, 기술적 선택의 최종 판단 기준은 엔드유저와 기반 기술을 사용하는 개발자의 경험이다. 구현 편의나 구조적 우아함과 경험이 충돌하면 경험을 우선한다. 더 적은 기능으로 경험이 개선된다면 기능 범위를 줄이는 선택을 검토한다.

경험 차이가 무시할 수준인 기술적 선택에서는 다른 관련 원칙을 기준으로 판단한다.

### Least Astonishment

인터페이스의 동작과 계약은 소비자가 이름과 사용 맥락에서 자연스럽게 예상하는 것과 일치해야 한다. 소비자가 구현의 내부 사정을 알아야 올바르게 사용할 수 있는 계약을 피한다. 인터페이스를 바꿀 때는 기존 소비자의 예상과 안정성을 변경 비용에 포함한다.

도메인 자체의 복잡성 때문에 이름만으로 전달할 수 없는 부분은 명시적인 계약과 문서로 보완한다. 외부 소비자가 있는 계약에는 소비자가 자신의 속도로 전환할 수 있는 마이그레이션 경로를 제공한다.

## 복잡성과 코드의 표현

구조를 추가할 필요, 추상화의 도입 시점과 구현을 공유할 이유를 구분해 판단한다. 선택한 구조는 [도메인의 어휘](#domain-vocabulary)와 일관된 표현으로 드러내 읽는 사람이 의미를 추적하는 비용을 줄인다.

| 원칙 | 적용 상황 |
| --- | --- |
| [Foundational Thinking](#foundational-thinking) | 새 구조의 필요와 그 기반을 판단할 때 |
| [Premature Abstraction Avoidance](#premature-abstraction-avoidance) | 추상화의 도입 시점을 판단할 때 |
| [Essential vs Accidental Duplication](#essential-vs-accidental-duplication) | 구현의 공유 여부를 판단할 때 |
| [Minimize Reader Load](#minimize-reader-load) | 구조와 관계를 이해하는 비용을 판단할 때 |
| [Intention-Revealing Names](#intention-revealing-names) | 이름으로 역할과 의도를 표현할 때 |
| [Single Level of Abstraction](#single-level-of-abstraction) | 함수와 유사한 흐름의 표현 수준을 정할 때 |

### Foundational Thinking

복잡성을 추가하기 전에 기존 구성과 그 조합으로 요구를 충족할 수 있는지 판단한다. 구조와 데이터 형태는 실제 사용 방식과 접근 패턴을 근거로 선택한다. 불필요한 것을 먼저 제거하고, 이후 변경들이 의존할 기반을 정한다. 필요한 책임과 계약을 생략한 채 변경량만 줄이는 것을 단순함으로 판단하지 않는다.

### Premature Abstraction Avoidance

추상화의 도입 시점은 실제 사용 사례와 확인된 공통 패턴으로 판단한다. 미래의 재사용 가능성만으로 경계를 만들지 않고, 사용 사례가 충분히 드러날 때까지 약간의 중복을 허용한다. 아직 알지 못하는 사용 사례를 하나의 계약에 묶는 비용을 도입 판단에 포함한다.

### Essential vs Accidental Duplication

같은 변경 이유로 함께 바뀌어야 하는 본질적 중복에만 DRY를 적용한다. 코드의 모양이 비슷하더라도 변경 이유가 다르면 별도로 유지한다. 공유의 타당성은 서로 다른 정책을 묶거나 한쪽 변경을 다른 쪽에 불필요하게 전파하는지로 판단한다.

### Minimize Reader Load

가독성은 읽는 사람이 목적과 변경 이유를 이해하기 위해 추적해야 하는 관계와 기억해야 하는 상태를 기준으로 판단한다. 고유한 역할이 없는 간접 계층과 숨은 결합은 줄이고, 실제 책임이 있는 경계는 보존한다. 표현을 짧게 만드는 선택이 의미를 이해하는 비용도 줄이는지 확인한다.

### Intention-Revealing Names

이름은 왜 존재하고 무엇을 하며 어떻게 쓰이는지 드러낸다. 호출 위치에 맥락이 보존되면 중복된 수식어를 줄이되, 짧아진 이름도 도메인의 의미와 역할을 표현해야 한다. 이름으로 드러낼 수 있는 의도를 본문 추적이나 주석에 의존하게 하지 않는다.

### Single Level of Abstraction

하나의 흐름은 각 단계의 의도와 순서가 일관된 수준으로 드러나도록 표현한다. 특정 단계의 세부 절차가 섞여 전체 흐름을 가리지 않게 한다. 서로 다른 함수·파일의 유사한 책임과 동작도 비슷한 수준으로 표현하며, 표현의 차이는 실제 책임·동작·제약의 차이를 드러내야 한다. 수준을 맞추는 선택이 의미 없는 경계나 탐색 비용을 늘리지 않는지 판단한다.

업무의 분기와 반복은 상위 흐름의 일부일 수 있다. 표현의 일관성과 구현의 공유는 구분하며, 공유 여부는 [Essential vs Accidental Duplication](#essential-vs-accidental-duplication)의 변경 이유로 판단한다.

### Error Boundary Placement

실패는 그 의미에 대응할 책임과 능력이 있는 경계에서 처리한다. 대응할 책임이 없는 곳에서는 실패를 해당 경계로 전달하며, 처리 위치를 분산시켜 책임을 모호하게 하지 않는다. 실패를 변환하거나 정리할 때도 원인과 실패 의미를 보존한다.

### Meaningful Errors

실패 정보는 원인과 발생 맥락을 보존해 소비자가 실패 종류를 구분하고 대응을 선택할 수 있게 한다. 해결 방향을 알 수 있으면 함께 제공한다. 일반적인 실패 신호로 서로 다른 원인과 필요한 대응을 구분할 수 없게 만들지 않는다.

### Make Operations Idempotent

상태를 변경하는 연산은 같은 요청이 반복되거나 중간에 중단돼도 의도한 최종 상태로 수렴하게 한다. 완료 상태와 중간 상태를 구분하며, 이전 실행의 잔여 상태가 최종 결과를 바꾸지 않게 한다.

반복 자체가 새 결과를 만드는 계약이거나 단일 트랜잭션 안에서만 실행되는 연산은 그 제약에 맞는 반복의 의미를 별도로 판단한다.

### Separate Before Serializing Shared State

동시 변경의 제어 방식은 상태의 소유 범위와 유지해야 할 불변 조건에서 도출한다. 독립적으로 소유할 수 있는 상태는 먼저 분리하고, 공유가 실제 도메인 제약일 때 동기화나 직렬화를 선택한다. 분리가 도메인의 계약을 바꾸지 않는지와 필요한 공유가 불변 조건을 지키는지를 함께 판단한다.

## 변경의 실행과 증명

### Fix Root Causes

결함의 수정 대상은 관찰한 증상을 만드는 근본 원인으로 정한다. 가드나 예외로 증상만 억제하지 않으며, 수정 범위는 발견된 한 건이 아니라 같은 원인에 영향을 받는 범위로 판단한다. 동일 패턴이 의심되면 코드베이스 전체에서 그 영향 범위를 확인한다.

외부 원인을 수정할 수 없는 경우에는 완화를 선택한 근거와 남은 원인을 명시한다. 원인 추적 비용이 증상 완화보다 현저히 크고 재발 가능성이 낮은 경우에도 완화를 선택한 근거를 명시한다.

### Sequence Work into Verifiable Units

각 변경 단위는 확인 가능한 결과로 끝나고 후속 변경이 의존할 근거를 제공한다. 순서는 단위 사이의 의존 관계와 각 단위에서 보존할 동작을 기준으로 정한다. 중간 상태의 제한과 최종 상태로 이어지는 조건을 분명히 해, 확인하지 않은 전제 위에 후속 변경을 쌓지 않는다.

### Build the Lever

수행 수단의 가치는 같은 작업과 관찰을 재현하고 반복 비용을 줄이는 데 있다. 반복 변경이나 복잡한 비교에는 기존 수단을 우선하며, 부족한 능력만 추가한다. 한 번의 작업이라도 증거의 재현성이 중요하면 도구를 사용할 이유가 있다. 도구를 만드는 비용과 복잡성은 얻을 재현성과 수행 비용의 감소로 정당화한다.

### Migrate Callers Then Delete Legacy

내부 인터페이스의 변경은 호출자의 전환과 이전 계약의 제거를 같은 작업에서 완결한다. 호환성을 이유로 서로 다른 내부 설계를 영구적으로 유지하지 않는다.

외부 소비자가 있으면 [Least Astonishment](#least-astonishment)에 따라 전환 경로와 호환 전략을 제공한다. 전환 범위가 이번 작업보다 크다면 남은 호출자와 이전 계약을 폐기할 조건을 명시한다.

### Test Behavior, Not Implementation

검사는 소비자가 사용하는 계약과 관찰 가능한 동작을 판정한다. 기대값은 확인하려는 요구에서 정하며, 구현의 논리를 다시 계산해 기대값으로 삼지 않는다. 회귀 검사의 타당성은 해당 결함을 구분하는 실패 이유와 수정 후의 관찰 결과로 판단한다.

구현의 내부 구성을 고정하는 선택은 소비자 계약을 보존하는 데 필요한지로 판단한다.

### Prove It Works

성공의 판정은 현재 산출물의 실제 사용 경로에서 관찰한 증거를 기준으로 한다. 주장하는 조건과 관찰한 결과를 연결하고, 다른 표면의 결과나 자기 보고로 확인을 대신하지 않는다. 관찰 방법 자체도 판단의 대상이며, 관찰하지 못한 범위는 미확인으로 남긴다.
