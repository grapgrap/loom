# Loom Document Authoring Guide

Loom 문서는 독자가 현재 설계, 결정의 맥락과 실행 작업을 서로 혼동하지 않고 재구성할 수 있게 작성한다.

## 적용

이 가이드는 Loom의 index, concept, flow, decision, plan, rule과 convention을 작성하거나 검토할 때 적용한다.

문서 유형의 책임과 내용 라우팅은 반드시 지켜야 하는 기준이다. 기술문서 작성 기준은 의미와 책임 관계를 분명하게 전달하기 위한 기본 형식이며, 더 명확한 표현이 있다면 대체할 수 있다.

문서의 책임을 벗어난 내용은 단서로 감싸서 남기지 않는다. 해당 내용을 책임지는 문서로 옮긴다.

## 공통 원칙

- concept과 flow는 현재 설계의 진실을 기술한다. 변경 과정과 선택의 근거는 decision이 기술한다.
- 현재 설계에 영향을 준 decision의 결과는 해당 concept이나 flow에도 반영한다. 독자가 결정 이력을 모두 읽어야 현재 설계를 알 수 있게 하지 않는다.
- 나중에 수행할 작업은 plan에 둔다. 미래 작업을 현재의 책임이나 정책처럼 기술하지 않는다.
- 구현 방식과 제어 상세는 코드에 둔다. 구현의 형태를 결정한 근거가 보존할 가치가 있으면 decision에 기록한다.
- 여러 도메인을 불러 조합하면 flow다. 한 도메인 안의 동작이나 여러 입력을 하나의 결과로 닫는 계산이면 concept이다.
- 각 문서는 다른 문서의 상세를 대신하지 않는다. 문서 자체의 핵심 의미를 이해하는 데 필요한 반복만 허용한다.

## 문서 유형별 책임

### Concept

Concept은 한 도메인의 현재 의미를 설명한다.

- 도메인의 목적, 책임, 정책과 경계를 기술한다.
- 한 도메인 안의 동작이나 여러 입력을 하나의 결과로 닫는 계산을 기술한다.
- 다른 concept 및 flow와의 정적인 관계를 기술한다.
- 여러 도메인을 호출하는 순서나 조율을 기술하지 않는다.
- 설계를 선택한 과정, 대안과 선택의 근거를 기술하지 않는다.
- 구현 세부, 일시적인 작업 순서와 미래 계획을 기술하지 않는다.

### Flow

Flow는 여러 도메인이나 하위 흐름을 불러 조합하는 경로를 설명한다.

- 트리거부터 결과까지 각 단계의 주체, 행동과 결과를 기술한다.
- 순서, 병렬, 분기와 되먹임을 포함한 도메인 간 조율을 기술한다.
- 각 단계는 하나의 concept이나 하위 flow가 맡는 마디로 둔다.
- 분기와 순회의 조건은 가드 이름으로 표현한다. 판정 규칙은 해당 concept이나 코드에 둔다.
- 한 도메인 내부의 책임과 정책을 기술하지 않는다.
- 구현 수준의 제어 상세와 설계 선택의 근거를 기술하지 않는다.

### Decision

Decision은 대안이 있던 선택과 그 선택이 설계나 구현에 미친 영향을 설명한다.

- 선택이 필요했던 맥락과 문제를 기술한다.
- 검토한 대안, 채택한 선택과 선택의 근거를 기술한다.
- 선택이 concept, flow 또는 구현에 가져온 결과와 제약을 기술한다.
- 다른 decision을 읽지 않아도 선택의 맥락과 근거를 이해할 수 있게 자기완결적으로 작성한다.
- 시간순을 보존하고 이전 decision을 수정하거나 삭제하지 않는다.
- 현재 명세만 반복하거나 이미 정해진 내용을 설명하는 문서로 사용하지 않는다.
- 버그 수정, 작업 순서, 우선순위와 자명한 명명은 설계 결정으로 기록하지 않는다.

Decision의 결과로 성립한 현재 설계는 해당 concept과 flow에 반영한다. Decision은 현재 설계를 대신하지 않는다.

### Index

Index는 프로젝트나 디렉토리를 탐색하는 지도다.

- 해당 범위의 목표, 항목 목록과 주요 관계를 요약한다.
- 각 항목이 맡은 책임을 한눈에 구분할 수 있는 설명을 제공한다.
- 개별 문서의 본문을 대신할 정도로 상세한 명세를 중복하지 않는다.
- 항목이 추가되거나 책임과 관계가 바뀌면 현재 상태에 맞게 갱신한다.

### Plan

Plan은 확정된 설계를 검증 가능한 결과를 가진 태스크와 결과 간 의존관계로 구조화하고, 실행 중 확인한 사실을 남은 실행 경로에 반영한다.

- 각 태스크의 목적, 수행할 변화, 완료 후 성립해야 하는 결과와 검증 방법을 기술한다.
- 범위로 오해할 만한 인접 작업이 있으면 이번 태스크에서 바꾸지 않을 대상을 `제외`로 기술한다.
- 태스크 간 의존관계는 선행 태스크의 결과와 그 결과를 필요로 하는 후속 태스크의 전제로 기술한다. 단순한 작성 순서는 의존관계로 기술하지 않는다.
- 진행 상태는 각 태스크의 실행 상태로 갱신한다.
- 실행 중 확인한 기술적 사실이 남은 실행에 영향을 주면 영향받는 태스크의 변화·결과·검증이나 태스크 간 의존관계에 반영한다.
- 사용자가 명시적으로 요청할 때만 현재 미완료 태스크에 임시 핸드오프를 작성한다. 재개 지점과 아직 끝나지 않은 작업만 기록하고, 태스크 실행을 재개하거나 태스크를 완료하면 제거한다.
- 현재 도메인의 책임과 정책을 정의하지 않는다.
- 기술적 선택의 근거를 보존하거나 코드에서 확인할 수 있고 남은 실행에 영향을 주지 않는 구현 상세를 중복하지 않는다.

### Rule과 Convention

Rule과 convention은 프로젝트에 적용되는 비기능 요구사항과 합의된 형태를 기술한다.

- Rule은 적용 범위에서 반드시 지켜야 하는 프로젝트 종속 요구사항을 기술한다.
- Convention은 정당한 사유가 있으면 대체할 수 있는 프로젝트 종속 형태를 기술한다.
- 적용 범위와 적용되는 상황을 명시한다.
- Loom 자체의 문서 작성 기준을 프로젝트마다 rule이나 convention으로 복제하지 않는다.

## 내용 라우팅

작성하려는 내용의 의미를 기준으로 목적지를 정한다.

| 내용 | 목적지 |
| --- | --- |
| 한 도메인의 현재 목적, 책임, 정책과 경계 | concept |
| 한 도메인 안의 동작이나 닫힌 계산 | concept |
| 여러 도메인이나 하위 흐름의 호출과 조율 | flow |
| 대안이 있던 선택, 근거와 설계·구현에 미친 영향 | decision |
| 프로젝트나 디렉토리의 목표, 항목 목록과 주요 관계 | index |
| 앞으로 수행할 태스크의 목적·변화·완료 결과·검증과 제외 | plan의 해당 태스크 |
| 선행 태스크의 결과와 그 결과를 필요로 하는 후속 전제 | plan의 결과 의존 |
| 태스크의 실행 상태 | plan의 해당 태스크 |
| 남은 실행을 제약하는 기술적 사실이나 선택의 결과 | 영향받는 plan 태스크나 결과 의존 |
| 사용자가 명시적으로 요청한 미완료 태스크의 재개 지점과 아직 끝나지 않은 작업 | plan 태스크의 임시 핸드오프 |
| 프로젝트에서 강제할 비기능 요구사항 | rule |
| 프로젝트에서 권장할 대체 가능한 형태 | convention |
| 구현 방식과 제어 상세 | 코드 |

내용이 두 문서에 필요한 경우에는 각 문서가 소유하는 의미를 구분한다. Decision은 선택의 맥락과 근거를 보존하고, concept과 flow는 그 선택으로 성립한 현재 설계를 기술한다. 비자명한 기술적 선택이 남은 실행을 제약하면 decision은 선택의 근거와 영향을 보존하고, plan은 영향받는 태스크나 결과 의존에 그 선택으로 성립한 제약을 반영한다.

## 위키링크

위키링크는 문장 속 용어 표기가 아니라 문서 사이의 구조적 관계를 기록한다.

- Index는 항목 목록과 관계에서 문서를 연결한다.
- Concept은 관계에서 관련 concept과 flow를 연결한다.
- Flow는 단계에서 호출하는 concept이나 하위 flow를 연결한다.
- Decision은 영향에서 영향을 받은 concept과 flow를 연결한다.
- Plan은 태스크의 근거와 범위를 한정하는 concept, flow와 decision을 연결한다.
- 목적, 책임, 정책, 경계, 맥락과 결정 본문에서는 문서 이름 대신 도메인 용어를 사용한다.

## 기술문서 작성

기술문서는 독자가 같은 사실, 제약과 책임 관계를 재구성할 수 있게 작성한다. 표현의 세련됨이나 압축보다 의미의 정확성을 우선한다.

### 사실과 양태

- 현재의 사실, 강제적인 제약, 허용, 수행 능력과 아직 확정되지 않은 가능성을 구분한다.
- 강제적인 제약은 의무로, 범위의 제외는 부정으로 명시한다.
- 허용을 기술할 때는 허용하는 주체를 밝힌다.
- 가능성을 현재의 사실이나 합의된 방향처럼 기술하지 않는다.

### 용어와 관계

- 하나의 개념에는 하나의 용어를 일관되게 사용한다.
- 소유, 포함, 사용, 결정, 호출과 변경을 서로 다른 관계로 표현한다.
- 주체의 행동과 결과를 드러내는 동사를 사용한다.
- `처리한다`, `관리한다`, `지원한다`, `관여한다`, `연계한다`처럼 결과가 드러나지 않는 포괄적인 동사는 구체적인 행동으로 바꾼다.
- 대상을 넓게 가리키는 표현은 문맥만으로 대상과 기준을 하나로 특정할 수 있을 때만 사용한다.

### 문장과 문단

- 한 문장에는 하나의 중심 주장을 둔다.
- 소유, 변경 권위, 책임과 상호작용을 설명할 때는 주체를 생략하지 않는다.
- 지시 표현은 선행 대상이 하나로 특정될 때만 사용한다.
- 복잡한 조건과 결과는 분리하여 각각 검토할 수 있게 한다.
- 한 문단에는 하나의 논증 역할을 둔다. 사실, 근거와 결론을 별도로 검토해야 하면 문단을 나눈다.
- 짧은 문장이나 문단 자체를 목표로 삼지 않는다. 의미에 필요한 조건, 주체와 인과관계를 보존한다.

### 목록과 반복

- 목록 항목 하나에는 책임, 정책, 단계 또는 근거 하나를 둔다.
- 같은 목록의 항목은 주체, 서술 형식과 양태를 병렬적으로 유지한다.
- 같은 문서 안에서 의미 없이 반복한 내용은 제거한다.
- 다른 문서를 읽지 않아도 핵심 의미가 닫히는 데 필요한 반복은 유지한다.
- 필요한 내용을 반복할 때는 같은 용어와 같은 관계로 서술한다.

## 책임 위반 판별

- 여러 도메인의 호출 순서나 조율이 concept에 있으면 flow로 옮긴다.
- 한 도메인의 현재 책임이나 정책이 flow에 있으면 concept으로 옮긴다.
- 대안과 선택의 근거가 concept이나 flow에 있으면 decision으로 옮긴다.
- Decision에만 존재하는 현재 책임이나 정책은 해당 concept이나 flow에도 반영한다.
- 미래 작업이 현재 설계 문서에 있으면 plan으로 옮긴다.
- 구현 상세가 Loom 문서에 현재 설계처럼 있으면 코드로 옮긴다. 보존할 가치가 있는 선택의 근거는 decision에 기록한다.
- 실행 중 발견을 시간순으로 누적한 전역 진행 맥락이 plan에 있으면 남은 실행에 영향을 주는 사실만 영향받는 태스크나 결과 의존에 반영하고 나머지는 제거한다.
- 사용자의 명시적 요청 없이 임시 핸드오프가 작성되었거나, 태스크 실행을 재개하거나 완료한 뒤에도 남아 있으면 제거한다.
- Index가 개별 문서의 상세를 반복하면 상세를 해당 문서에 남기고 index를 요약한다.
- 문서의 책임을 벗어난 내용을 예외나 단서로 감싸서 유지하지 않는다.
