# Consistent Expression

코드 전체에서 같은 맥락의 동등한 책임과 동작이 같은 방식으로 읽히게 한다. 이름, 처리 순서와 구성, 반환하는 단위에 나타난 차이는 실제 의미의 차이를 드러내야 한다.

## 설명

독자는 한 부분에서 이해한 읽기 방식을 이어지는 코드에도 적용한다. 같은 역할을 어떤 곳은 직접 구현하고, 어떤 곳은 여러 보조 함수를 거쳐 수행하거나 서로 다른 단위로 반환하면 매번 흐름을 다시 해석해야 한다. 비교할 범위는 한 함수의 분기와 연속된 단계, 관련 함수와 파일의 흐름까지 포함한다.

헬퍼는 같은 책임 안의 구현을 돕는 보조 함수다. 헬퍼를 나누는 목적은 전체 흐름을 일관되게 읽도록 만드는 것이다. 각 조각에 이름을 붙일 수 있거나 한 가지 일을 한다고 설명할 수 있다는 사실만으로 분리할 이유가 생기지는 않는다.

## 적용

- 먼저 비교할 전체 흐름과 동등한 역할을 확인한다. 이름, 동작의 구성과 순서, 입력·결과의 단위를 같은 방식으로 읽을 수 있는지 살핀다.
- 헬퍼는 전체 흐름의 표현 일관성을 만드는 데 필요할 때만 분리한다. 어떤 불일치를 해소하는지, 분리한 뒤 대응하는 처리가 어떻게 같은 방식으로 읽히는지 확인한다.
- 함수 분리와 인라인 표현을 함께 검토한다. 일부만 짧게 만드는 데 그치거나 하나의 흐름을 이해하기 위해 여러 함수를 오가게 한다면 분리 단위를 다시 판단한다.
- 실제 책임·동작·제약이 달라 다르게 구성해야 한다면 그 차이가 이름과 흐름에 드러나게 한다.

## 경계

함수 길이, 단계 수, 이름을 붙일 수 있음, 조건문·반복문이나 세부 절차가 보인다는 사실은 각각 헬퍼 추출의 근거가 아니다. 전체 흐름이 이미 일관되게 읽힌다면 단계를 더 나누지 않는다. 반대로 짧거나 한 번만 쓰이는 구현도 전체의 일관성을 만드는 데 필요하면 헬퍼로 둘 수 있다.

독립된 정책이나 계약을 소유하는 함수의 경계는 [Earn Your Boundary](earn_your_boundary.md)로 판단한다. 같은 책임의 구현 보조에 이름을 붙인 것을 새로운 책임의 근거로 삼지 않는다.

표현의 일관성과 구현의 공유는 별개의 판단이다. 대응하는 동작을 같은 방식으로 표현하더라도 변경 이유가 다르면 각자의 구현을 유지한다. 공통 헬퍼를 만들기 위해 서로 다른 규칙이나 반환 단위를 섞지 않는다.

## 예시

CSV와 JSON 내보내기가 모두 형식 변환 후 같은 파일 저장을 수행한다고 하자. 다음 구성에서는 같은 내보내기 역할을 서로 다르게 읽어야 한다.

```text
형식이 CSV이면:
    exportCsv(보고서, 경로)
형식이 JSON이면:
    내용 = encodeJson(보고서)
    writeFile(경로, 내용)
```

두 분기를 변환 과정으로 표현하고 저장을 이어서 수행하면, 내보내기 헬퍼를 추가하지 않아도 전체 흐름을 일관되게 읽을 수 있다.

```text
형식이 CSV이면:
    내용 = encodeCsv(보고서)
형식이 JSON이면:
    내용 = encodeJson(보고서)
writeFile(경로, 내용)
```

각 형식의 내보내기를 하나의 동작으로 읽는 구성이 전체 흐름에 맞는다면, 다음처럼 대응하는 헬퍼를 둘 수도 있다. 두 함수는 모두 변환부터 저장까지 같은 단위의 동작을 표현한다.

```text
형식이 CSV이면:
    exportCsv(보고서, 경로)
형식이 JSON이면:
    exportJson(보고서, 경로)
```

선택 기준은 헬퍼의 개수나 개별 분기의 길이가 아니라 전체 흐름을 읽는 방식이다. 어느 구성을 택하든 동등한 처리가 일관되게 읽히면 된다.

## 검토 질문

- 한 부분에서 이해한 읽기 방식으로 이어지는 분기·단계·관련 함수도 읽을 수 있는가?
- 추가한 헬퍼가 전체 흐름의 어떤 불일치를 해소하는가?
- 각 조각이 한 가지 일을 한다는 설명만으로 불필요한 분리를 정당화하고 있지 않은가?
- 함수 분리와 인라인 표현 중 어느 쪽이 대응하는 처리와 전체 흐름을 일관되게 보여주는가?
- 이름, 동작의 구성과 반환 단위의 차이가 실제 의미의 차이를 반영하는가?
