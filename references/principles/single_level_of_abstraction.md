# Single Level of Abstraction

코드를 읽는 사람이 유사한 동작을 유사한 방식으로 이해할 수 있도록 추상화 수준을 맞춘다.

## 설명

추상화 수준은 코드가 동작의 의도를 드러내는지, 그 동작을 실현하는 세부 절차를 드러내는지를 뜻한다. 여러 단계를 조율하는 함수는 각 단계의 의도와 순서를 보여주고, 각 단계를 구현하는 함수는 세부 절차를 보여준다.

독자는 코드의 표현에서 의미를 추론한다. 같은 맥락에서 유사한 책임을 수행하는 코드가 한쪽에서는 함수 호출로, 다른 쪽에서는 인라인 구현으로 표현되면, 독자는 그 차이가 책임이나 동작의 차이를 뜻하는지 확인해야 한다. 실제로 차이가 없다면 표현을 일관되게 맞춰 불필요한 해석을 줄인다.

이 기준은 한 함수 내부뿐 아니라 서로 다른 함수나 파일에 있는 유사한 흐름에도 적용한다. 비교의 기준은 코드의 모양이 아니라 도메인에서 수행하는 책임과 동작이다.

## 적용

- 하나의 흐름을 구성하는 단계들은 일관된 추상화 수준으로 표현한다. 특정 단계의 세부 구현이 섞여 흐름을 가리면, 그 구현을 의도가 드러나는 함수로 분리한다.
- 유사한 책임과 동작을 수행하는 코드는 함수 분리 여부와 세부 구현의 노출 수준을 일관되게 맞춘다.
- 함수의 이름은 해당 단계의 의도를 설명해야 한다. 흐름을 이해하기 위해 매번 함수 본문을 확인해야 한다면 이름과 분리 단위를 다시 검토한다.
- 책임이나 제약이 달라 표현을 달리해야 한다면, 그 차이가 이름과 구조에서 드러나도록 한다.

## 경계

일관성을 맞추는 방법에는 함수 분리와 인라인 표현이 모두 포함된다. 단순한 동작을 의미 없는 이름의 함수로 감싸면 코드 탐색만 늘어날 수 있다. 독자가 의도와 흐름을 쉽게 파악할 수 있는 쪽을 선택한다.

표현의 일관성이 구현의 공유를 요구하지는 않는다. 유사한 코드를 같은 수준으로 표현하더라도 변경 이유가 다르면 별도로 유지한다.

조건문이나 반복문이 있다는 이유만으로 추상화 수준이 낮다고 판단하지 않는다. 업무의 분기와 반복을 표현하는 제어문은 상위 흐름의 일부일 수 있다.

## 예시

주문 처리에서 고객 검증과 주문 항목 검증이 동등한 단계라면, 두 검증을 같은 수준으로 표현한다.

### Don't

```typescript
const submitOrder = async (params: SubmitOrderParams) => {
  validateCustomer(params.customer);

  if (params.order.items.length === 0) {
    throw new Error("Order must contain items");
  }

  await saveOrder(params.order);
};
```

### Do

```typescript
const validateOrderItems = (order: Order) => {
  if (order.items.length === 0) {
    throw new Error("Order must contain items");
  }
};

const submitOrder = async (params: SubmitOrderParams) => {
  validateCustomer(params.customer);
  validateOrderItems(params.order);
  await saveOrder(params.order);
};
```

## 검토 질문

- 유사한 책임과 동작이 이유 없이 서로 다른 추상화 수준으로 표현되어 있는가?
- 표현의 차이가 실제 책임이나 동작의 차이를 반영하는가?
- 흐름을 읽다가 특정 단계의 세부 절차를 해석해야 하는가?
- 함수로 분리한 단위와 이름이 세부 구현을 읽지 않고도 의도를 이해하는 데 도움이 되는가?
