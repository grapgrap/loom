# plan은 현재 구현을 근거로 변경 방법과 영향을 검토한다

## 맥락

기존 plan은 확정된 설계를 검증 가능한 결과와 의존관계로 분해했다. 구현 방법은 task에서 작업 직전에 사용자와 합의했다. 이 구성은 실행 관리에는 대응하지만, 사용자가 변경의 영향을 이해하면서 주요 결정을 발견하려는 목적을 충분히 반영하지 못했다.

사용자는 plan과 task에서 알아채지 못한 주요 결정을 에이전트가 먼저 확정했을 때 최종 리뷰에서 직접 수정해야 했다. 작업 목록과 완료 결과를 확인하는 것만으로는 그 목록에 포함된 선택과 부작용을 판단하기 어려웠다.

필요한 과정은 현재 코드를 파악하고, 변경 방법을 가정하고, 그 영향을 추적하면서 사용자와 판단을 조정하는 것이다. 해야 할 일과 실행 순서는 이 검토에서 도출된다.

## 결정

plan은 현재 구현을 근거로 변경 방법과 영향을 사용자와 검토하고 실행할 작업을 구성한다.

- 현재 동작과 문제의 원인을 조사하며 확인한 사실과 미확인 가정을 구분한다.
- 변경할 위치와 방법을 가정하고 변경 후 흐름, 기존 동작에 미치는 영향, 부작용과 대안을 검토한다.
- 사용자가 변경의 타당성과 주요 선택을 판단할 수 있을 만큼 구체화한다. 구현 수준이라는 이유로 필요한 논의를 task까지 미루지 않는다.
- 판단을 바꿀 발견이나 선택이 생길 때마다 공유한다. 완성된 작업 목록의 확인만으로 이 과정을 대체하지 않는다.
- 검토한 변경안에서 작업, 완료 결과, 의존관계와 검증 방법을 도출한다.
- task는 해당 단계의 실행 요약으로 시작한다. 전체 변경안에서 맡는 부분, 바꿀 내용과 예상 동작, 주의점과 검증, 선행 실행의 영향을 정리한다. 사용자의 확인을 받은 뒤 실행한다.
- 이미 합의한 구현 방향은 요약으로 이어받는다. 새 판단은 합의된 내용과 구분하여 논의한다.
- 예상과 달라도 기존 방향과 영향 판단이 유지되면 작업 중 해결한다. 주요 판단이나 후속 작업의 전제가 달라지면 관련 변경안과 작업을 사용자와 다시 검토한다.
- 도메인의 책임이나 조합 자체가 달라져야 하면 shape에서 해당 설계를 재검토한다.

shape는 개념적 책임과 도메인 간 조합을 정한다. plan은 실제 구현의 변경 방법과 영향을 검토한다. plan의 필요성은 태스크 수가 아니라 변경 영향 검토의 필요성으로 판단한다.

review는 변경안의 코드 근거, 문제 해결의 타당성, 영향 대응의 누락과 실행 작업의 정합성을 검증한다. 모든 구현 상세를 요구하지 않는다. 산출물만으로 사용자가 대화에서 무엇을 알아차렸는지 추론하지 않는다.

plan 문서에는 실행에 필요한 현재 동작의 요약, 변경안, 예상 영향과 미확인 사항을 남긴다. 선택의 근거는 decision에 보존한다. 개념적 설계는 concept과 flow에 반영한다. 탐색 과정 전체나 코드의 현재 상태를 복제하지 않는다.

### 전제 조건

- 구현을 조사하고 변경 영향을 추적하면 작업 목록만으로 드러나지 않는 판단을 발견할 수 있다.
- 사용자에게 변경 전후의 동작과 선택의 영향을 설명하면 모든 코드 줄을 합의하지 않고도 주요 판단을 함께 검토할 수 있다.
- 실행 중 새로운 사실이 나타날 수 있으므로 plan은 현재 근거에 따라 갱신되어야 한다.

## 대안

### 결과 중심 작업 분해와 태스크별 구현 합의를 유지한다

- 설명: plan은 완료 결과와 의존관계를 정하고 구현 방법은 task에서 논의한다.
- 트레이드오프: 결과 판정은 명확하지만 여러 작업에 걸친 변경 영향과 주요 선택을 전체 변경안으로 검토하기 어렵다.

### 주요 결정 목록만 추가한다

- 설명: 에이전트가 중요하다고 분류한 선택을 나열하여 사용자에게 확인받는다.
- 트레이드오프: 사용자가 변경 흐름을 이해하면서 에이전트가 놓친 결정을 발견하는 과정을 대신하지 못한다.

### 실행 시작 확인은 새로운 발견이 있을 때만 한다

- 설명: plan 합의 후 task는 새 판단이 있을 때만 사용자와 논의한다.
- 트레이드오프: 사용자가 현재 실행 단계와 내용을 확인할 기회가 줄어든다. 각 태스크의 실행 요약과 확인을 유지한다.

- plan 스킬과 템플릿 - 코드 조사와 변경 영향 검토를 작업 분해보다 앞에 둔다.
- shape 스킬 - plan 진입을 변경 영향 검토의 필요성으로 판단한다.
- task 스킬 - 실행 요약과 사용자 확인으로 시작하고 새 발견의 영향을 기준으로 재검토한다.
- review 스킬 - 결과 계약뿐 아니라 변경안의 근거와 영향을 검증한다.
- 문서 작성 가이드 - plan에 실행을 위한 변경안과 예상 영향을 배치할 수 있도록 책임을 조정한다.
- propose와 calibrate - 기존 책임을 유지한다.
