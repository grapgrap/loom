# plan 태스크를 검증 가능한 결과 중심으로 구성한다

## 맥락

plan은 설계를 실행 가능한 태스크와 의존관계로 분해하고, 초안의 확정 전에 각 태스크의 거시적 실행 가능성을 사용자와 함께 검증해 왔다. 그러나 태스크가 완료 후 성립시켜야 하는 결과를 필수로 요구하지 않아, 파일별 작업 목록과 작업 순서가 있어도 task가 무엇을 얻어야 하는지 재구성하지 못하는 경우가 생겼다.

이 공백을 메우기 위해 plan의 기술적 해상도를 높이면 인터페이스 형태, 데이터 흐름과 추상화 전략을 plan이 미리 결정하게 된다. 그러면 초기 plan이 거친 것은 자연스럽다는 전제와 충돌하고, task가 작업 직전에 구현 방향을 사용자와 합의하는 책임도 침범한다.

문제의 원인은 plan의 구현 세부가 부족한 데 있지 않다. 태스크가 만들어야 할 결과와 그 결과의 검증 방법이 명시되지 않은 데 있다. 구현 방법을 열어 두면서도 task가 무엇을 해야 하고 어떤 상태를 만들어야 하는지 알 수 있는 해상도가 필요하다.

## 결정

plan은 설계를 검증 가능한 결과를 가진 태스크로 분해한다.

- 각 태스크는 목적, 수행할 변화, 완료 후 성립해야 하는 결과와 검증 방법을 기술한다.
- 태스크 결과는 검증 가능한 상태·산출물·능력으로 기술한다. 내부 산출물이나 능력도 확정된 설계를 실체화하거나 후속 태스크의 전제가 되면 결과가 될 수 있다.
- 태스크 간 의존관계는 선행 태스크의 결과가 후속 태스크의 전제가 되는 관계로 기술한다. 단순한 작성 순서는 의존관계로 보지 않는다.
- plan의 해상도는 구현 세부의 양이 아니라 결과의 명확성과 검증 가능성으로 판단한다. 결과가 명확하고 구현 방법만 열려 있는 것은 정상적인 plan 상태다.
- plan 검증은 각 태스크의 결과가 명확하고 검증 가능한지, 결과 간 의존이 이어지는지, 전체 결과 사슬이 확정된 설계를 빠짐없이 실체화하는지를 사용자와 함께 확인한다.

결과의 명확성은 plan 태스크의 품질 기준이며 shape·plan·task의 라우팅 기준이 아니다. 라우팅은 무엇이 바뀌어야 하는지로 판단한다.

- concept이나 flow의 의미가 바뀌어야 하면 shape로 라우팅한다.
- concept과 flow의 의미를 유지한 채 태스크의 형태·순서나 진행 맥락만 바뀌면 plan을 갱신한다.
- concept과 flow의 의미와 태스크 결과를 유지한 채 구현 방법을 정하면 task가 사용자와 합의한다.

자의적 구현을 막기 위해 해상도가 부족한 태스크를 shape로 보낸 기존 목적은 유지한다. 다만 방향성 수준의 판단이 필요하다는 이유만으로 shape에 보내던 판별은 concept이나 flow의 의미가 바뀌는지로 좁힌다. 결과가 명확하더라도 concept이나 flow가 바뀌면 shape의 몫이며, 태스크 결과가 바뀌더라도 설계의 의미가 유지되면 plan의 몫이다.

### 전제 조건

- 구현 방법을 정하지 않고도 완료 후 성립해야 하는 결과를 명시할 수 있다: 같은 결과를 만드는 구현 대안이 여러 개일 수 있다.
- task는 확정된 설계와 태스크 결과를 입력으로 구현 방법을 사용자와 합의할 수 있다: 결과의 명시는 task의 방향성 합의를 대체하지 않는다.
- 결과 간 관계로 전체 실행 범위를 점검할 수 있다: 선행 결과가 후속 전제로 이어지지 않거나 최종 설계에 기여하지 않으면 누락이나 불필요한 태스크를 식별할 수 있다.

### 제약 조건

- 초기 plan이 거친 것은 자연스럽다. 모든 태스크에 기술 명세 수준의 해상도를 요구하지 않는다.
  - 제약이 없었다면: plan이 인터페이스와 데이터 모델까지 확정하여 실행 전 불확실성을 제거했을 것이다.
- plan 검증은 결과와 결과 사슬의 거시적 실행 가능성을 확인하는 수준에 머문다.
  - 제약이 없었다면: plan 검증에서 구현 방법까지 합의했을 것이다.
- plan은 실행 단계의 진행 맥락을 가볍게 누적하는 살아있는 문서다. 결과 중심 구조가 엄밀한 진행 기록 양식을 강제하지 않는다.
  - 제약이 없었다면: 각 결과의 상태 전이를 별도 형식으로 기록했을 것이다.

## 대안

### 현재 구조에 결과 항목만 추가한다

- 설명: 기존 태스크와 검증 구조는 유지하고 템플릿에 완료 결과와 검증 항목만 더한다.
- 트레이드오프: 결과는 기록되지만 해상도 품질과 라우팅 기준의 혼동이 남는다. 결과가 불명확하면 shape로 보내고 결과가 바뀌어도 shape로 보내는 과잉 라우팅을 막지 못한다.

### plan을 기술 명세 수준으로 구체화한다

- 설명: plan이 인터페이스, 데이터 모델과 파일별 변경을 확정하여 task가 바로 구현할 수 있게 한다.
- 트레이드오프: 실행 불확실성은 줄지만 모든 태스크의 작성 비용이 커지고, 초기 plan이 거칠 수 있다는 전제와 task의 구현 방향 합의 책임을 침범한다.

### 결과 정의를 task에 맡긴다

- 설명: plan은 활동과 의존관계만 구성하고, task가 구현 직전에 완료 결과와 검증 방법을 정한다.
- 트레이드오프: 구현 직전까지 완료 상태가 불분명하고, 한 태스크의 결과가 전체 plan에 미치는 영향을 큰 그림에서 검증하지 못한다.

## 영향

- [[plan]] - 목적·책임·정책·경계가 결과 중심 분해와 결과 간 의존관계를 반영한다.
- [[0013-resolution-check-through-shape]] - 자의적 구현 방지 목적은 유지하고, shape 라우팅 기준을 concept이나 flow의 의미 변경으로 좁힌다.
- plan 스킬과 템플릿 - 태스크의 결과와 검증 방법을 산출하고 결과 사슬을 사용자와 검증한다.
- task 스킬 - 태스크 결과를 구현 목표와 완료 판정 기준으로 사용한다.
- review 스킬 - 태스크 결과의 추적성과 결과 사슬의 완전성을 검증한다.
- 문서 작성 가이드 - plan 문서의 책임에 태스크 결과와 결과 간 의존관계를 반영한다.
