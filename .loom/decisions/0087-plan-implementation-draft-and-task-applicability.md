# plan에서 구현 초안을 검토하고 task에서 적용 가능성을 확인한다

## 맥락

plan은 문제와 원하는 결과를 확인하고 현재 구현을 조사하여 구현 방안과 영향을 사용자와 검토하도록 정의되었다. 그러나 구체화 수준을 사용자가 판단할 만큼으로만 요구하면, 공통화나 규칙 수립 같은 활동을 나열하고 실제 구조와 동작의 선택을 task에 남길 수 있었다.

사용자가 변경의 의도와 주요 선택을 확인하려면 책임 배치뿐 아니라 코드 구조, 주요 인터페이스와 핵심 로직까지 검토할 수 있어야 한다. 동시에 plan 작성 이후의 코드와 선행 작업 결과는 달라질 수 있다. task는 초안을 그대로 적용하기 전에 현재 구현에 적용 가능한지 확인해야 한다.

## 결정

plan은 주요 변경의 구현 초안을 사용자와 부분별로 검토하고 기록한다. task는 해당 초안의 적용 가능성을 확인하고 실제 적용 방안을 사용자와 합의한 뒤 실행한다.

- 구현 초안은 수정·추가·삭제할 코드 위치와 책임, 주요 함수의 입력·반환값과 데이터 타입, 호출자 변경 및 핵심 로직을 포함한다.
- 핵심 로직은 분기, 상태 변경과 실패 처리가 드러나는 수도코드 또는 코드 초안으로 제시한다.
- 관련 구현 조사, 해당 부분의 초안 제안, 사용자 검토, 연결되는 다음 부분 검토 순으로 진행한다. 전체 초안을 혼자 완성한 뒤 확인받지 않는다.
- 합의한 구현 초안에서 태스크를 도출한다. 각 태스크는 어느 초안을 어디에 어떻게 적용하는지 명시한다.
- 목적이나 완료 조건만으로 구현 초안을 대신하지 않는다. 책임 배치나 핵심 동작이 미결정인 범위는 실행 가능한 구현으로 확정하지 않는다.
- 검증 결과가 있어야 정할 수 있는 사항은 필요한 검증과 그 결과로 결정할 내용을 구분한다. 해당 구현은 결과를 반영하여 초안을 검토한 뒤 실행 대상으로 확정한다.
- task는 초안을 현재 코드와 선행 작업 결과에 대조한다. 적용 위치, 타입, 의존관계, 호출자와 핵심 로직의 적용 가능성을 확인한다.
- task는 확인 근거, 실제 적용 방안과 필요한 조정, 검증 방법을 사용자에게 요약하고 합의한 뒤 실행한다.
- 기존 설계 판단을 유지하는 조정은 task에서 합의한다. 책임 배치나 핵심 동작이 달라지면 관련 부분을 다시 플래닝한다. 도메인의 의미와 경계 변경은 shape에서 재검토한다.

모든 코드 줄이나 고정된 태스크 수를 요구하지 않는다. 현재 구현은 계속 문제 이해와 영향 분석의 대상이며 기존 구조 유지의 제약이 되지 않는다.

### 전제 조건

- 코드 구조와 핵심 로직의 초안을 검토하면 구현에 포함된 주요 선택을 사용자가 판단할 수 있다.
- 구현 초안과 실제 적용 시점의 코드에는 차이가 있을 수 있다. 적용 가능성 확인은 초안의 주요 설계를 새로 정하는 과정과 구분할 수 있다.

## 대안

### 책임 배치와 데이터 흐름만 합의한다

- 설명: plan은 책임과 흐름을 설명하고 코드 구조와 핵심 로직은 task에서 정한다.
- 트레이드오프: 실제 구현 형태를 결정하는 선택이 plan 검토에서 드러나지 않을 수 있다.

### task는 실행 내용을 요약한 뒤 바로 적용한다

- 설명: plan에서 합의한 방안을 요약하고 사용자 확인 후 구현한다.
- 트레이드오프: 초안이 현재 코드에 적용 가능한지 확인하지 않으면 적용 중에야 전제 차이와 필요한 조정을 발견한다.
