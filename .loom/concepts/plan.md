# Plan

설계를 검증 가능한 결과를 가진 태스크와 결과 간 의존관계로 구조화하고, 작성과 실행에 걸쳐 갱신되는 살아있는 문서.

## 목적

확정된 설계를 실체화하는 데 필요한 결과와 그 순서를 명시하고, 실행 중 확인한 기술적 사실을 남은 실행 경로에 반영하여 구현과 세션 간 인계를 가능하게 한다.

## 책임

확정된 설계를 독립적으로 실행 가능한 태스크로 분해한다. 각 태스크가 수행할 변화, 완료 후 성립해야 하는 결과와 검증 방법을 명시하고, 선행 태스크의 결과가 후속 태스크의 전제로 이어지는 관계를 의존관계로 구성한다. 초안의 확정 전에는 각 태스크의 결과와 전체 결과 사슬이 설계를 빠짐없이 실체화하는지 사용자와 함께 검증한다. 실행 단계에서는 코드에서 확인한 기술적 사실을 영향받는 태스크의 변화·결과·검증과 의존관계에 직접 반영한다. 사용자가 명시적으로 요청하면 현재 미완료 태스크에 임시 핸드오프를 남긴다.

## 정책

- 산출물이지 실행이 아니다 — plan 자체는 코드를 만들지 않는다.
- concept·flow·decision과 연관되지만 독립적으로 존재하며, 독자적 생명주기를 갖는다 — 엔티티의 수명과 결합되지 않는다.
- 하나의 concept이나 flow에서 여러 plan이 나올 수 있다.
- 태스크 결과는 완료 후 성립해야 하는 검증 가능한 상태·산출물·능력으로 기술한다.
- 각 태스크 결과는 확정된 설계나 후속 태스크의 전제로 추적할 수 있어야 한다.
- 의존관계는 선행 태스크의 결과가 후속 태스크의 전제가 되는 관계다 — 단순한 작성 순서는 의존관계가 아니다.
- 태스크의 해상도는 구현 세부의 양이 아니라 결과의 명확성과 검증 가능성으로 판단한다 — 결과가 명확하고 구현 방법만 열려 있는 것은 정상적인 plan 상태다.
- plan은 작성으로 끝나지 않고 task의 실행 내내 갱신되는 살아있는 문서다 — 가정이 현실과 어긋나면 task가 plan을 맹신하지 않고 남은 태스크·결과·검증·의존관계를 갱신한다.
- 실행 중 확인한 기술적 사실은 시간순으로 누적하지 않고, 그 사실이 영향을 주는 태스크나 의존관계에 반영한다.
- 비자명한 기술적 선택이 후속 실행을 제약하면 plan에는 선택의 결과를 반영하고, 선택의 근거는 decision에 기록한다.
- 임시 핸드오프는 사용자가 명시적으로 요청할 때만 현재 미완료 태스크에 작성한다. 사용자가 요청하지 않으면 task가 필요성을 추론하여 작성하지 않는다.
- 임시 핸드오프는 태스크 실행을 재개하거나 태스크를 완료하면 제거한다.
- 초안의 확정 전에 각 태스크를 사용자와 함께 검증한다 — 사용자가 변경 범위를 인지하고 그 정당성을 판단할 수 있어야 하므로, 에이전트 단독 점검으로 대체하지 않는다.
- 검증의 깊이는 각 결과의 명확성과 검증 가능성, 결과 간 의존의 연결과 변경 거점의 실재를 확인하는 수준에 머문다 — 결과를 만드는 구현 방법은 task에 남긴다.

## 경계

- 단일 작업이나 기계적 변환에는 plan을 작성하지 않는다 — shape의 완료 후 라우팅에서 판단한다.
- 확정된 concept이나 flow의 의미를 변경하지 않는다 — 이들이 바뀌어야 하면 shape로 돌아간다.
- 태스크 결과를 만드는 구현 전체를 명세하지 않는다 — 후속 실행에 영향을 주는 기술적 사실과 선택의 결과만 현재 실행 경로에 반영한다.
- 시간순 작업 일지나 구현 지식 저장소로 사용하지 않는다 — 남은 실행 경로에 영향을 주지 않고 코드에서 확인할 수 있는 사실은 중복하여 기록하지 않는다.
- 기술적 선택의 근거를 담지 않는다 — 왜 그렇게 결정했는가는 decision의 몫이다.
